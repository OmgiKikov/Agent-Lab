# Agent Lab: дизайн вокруг разбора ошибок

Рабочее предложение от 30 сентября 2026 года. Основание: ветка `claude/agent-lab-frontend-refactor-7l67ca`, commit `e1c3247`, работающий интерфейс на `:5899`, код и документация. Основного пользователя подтвердил автор продукта: **разработчик, который ищет причины ошибок**.

## Продуктовая позиция

Agent Lab помогает разработчику найти нарушения в поведении агента, проверить доказательства и подготовить повторяемую проверку исправления.

Первое полезное действие: открыть проблему и понять **какое правило нарушено, какой ответ это доказывает и каким сценарием это воспроизвести**. Это и должно определять интерфейс. Эмоция продукта: «я вижу, что происходит, и могу разобраться».

Дизайн продаёт здесь через демонстрацию этой способности. Сильный момент демо: человек открывает нарушение, сразу видит правило рядом с репликой, оспаривает сомнительную оценку или превращает доказанный случай в проверку. Аккуратная типографика, ясные действия и быстрые переходы усиливают этот момент.

Не стоит обещать, что Agent Lab сам исправляет агента, устанавливает истинную причину ошибки или выдаёт гарантированное разрешение на релиз. Он предоставляет наблюдения, аргументы судьи и средства проверки; вывод разработчика остаётся отдельным действием.

## Что уже работает в текущей ветке

- Последний рефакторинг уже связывает критерии, диалоги и проверку судьи. Это полезная основа нового поведения продукта.
- Правила имеют происхождение, а разговоры и вердикты позволяют проверить отдельное утверждение.
- Есть два самостоятельных источника полезного результата: реальные логи и симулятор. Анализ логов не требует запуска агента, но требует правил из собранного контекста агента.
- Есть повторные прогоны, варианты поведения клиента, второй судья и ручная проверка.
- Есть общий набор компонентов, токены и быстрый переход через `⌘K`.

## Что мешает первому пониманию

На просмотренном экране в ширине около 925 px главным элементом оказались **39%**, за ним — блок предварительной оценки и большой пустой график. Конкретные нарушения начинались внизу экрана. Разработчику приходится искать то, ради чего он пришёл. На широком экране список поднимается выше, но порядок акцентов остаётся тем же.

| Наблюдение | Последствие | Изменение |
|---|---|---|
| Основная страница называется «Критерии», но начинается с процента и графика | Сначала нужно интерпретировать показатель, затем искать работу | Главный вход «Разбор»: очередь наблюдаемых нарушений и выбранное доказательство |
| Две левые панели, плюс отдельная панель помощника | Узкий экран теряет место для чтения диалога | Одна навигация Agent Lab; Workshop как переход; помощник открывается по контекстному действию |
| Важный текст часто 11–12 px с низким визуальным весом | Длинные правила и цитаты трудно читать | Основной текст 14–15 px; спокойные, но читаемые подписи; моноширинный шрифт для идентификаторов и кода |
| Пустой график занимает заметную площадь | Продукт выглядит незавершённым и отодвигает доказательства | Динамику показывать, когда существует сопоставимое сравнение |
| Первый опыт описывает три обязательных шага | Полезность анализа логов откладывается | Два независимых намерения: найти ошибки в логах / проверить версию |
| Видимая версия сочетается с общим пулом текущих логов | Пользователь может приписать чужие наблюдения выбранной версии | Явно разделить оценку файла логов и конкретный запуск симулятора |
| В разборе блок «Почему так случается» пересказывает аргумент судьи | Описание нарушения выглядит установленной причиной | Назвать блок «Основание оценки»; гипотезы причины связывать с наблюдаемым контекстом, входами и вызовами инструментов |
| При переходе из прокрученного списка в критерий сохранилось положение прокрутки | Начало разбора и первая цитата оказываются выше видимой области | При открытии нового случая показывать начало разбора; при возврате восстанавливать список |

Это экспертные наблюдения по коду и интерфейсу; пользовательское исследование ещё не проведено.

## Три возможных направления

| Направление | Главный объект | Сильная сторона | Цена для MVP |
|---|---|---|---|
| Консоль прогонов | Запуск и технический трейс | Удобна для исследования исполнения | Требует понимать внутреннее устройство оценки до получения пользы |
| **Разбор нарушений — рекомендуемое** | Наблюдаемая проблема с доказательствами | Совпадает с задачей основного пользователя; быстро демонстрирует пользу | Нужны связанный разбор и аккуратная работа с неопределённостью |
| Отчёт качества | Сводка и динамика | Удобен для передачи результата руководителю | Требует корректных знаменателей, покрытия и сопоставимых версий; слабее для диагностики |

Основной интерфейс предлагаем строить вокруг разбора. Трейсы и отчёт останутся доступными в контексте текущего исследования. Цветовая тема — отдельное решение; она не определяет продуктовый сценарий.

## Принципы

1. **Один рабочий вопрос на экран.** «Что требует внимания?» сменяется «Почему это считается ошибкой?» и «Как проверить исправление?». У каждого состояния есть понятное продолжение.
2. **Доказательство рядом с утверждением.** Наблюдаемое нарушение, правило с происхождением и точная реплика видны в одном контексте. Полный трейс открывается глубже.
3. **Каждый вывод можно проверить.** Видны источник, выборка, основания судьи и ограничение наблюдения. Сомнительную оценку можно оспорить.
4. **Неопределённость — полноценное состояние.** «Нет данных», «не применимо» и «оценка предварительная» имеют собственное значение и следующий шаг.
5. **Частота направляет разбор.** «В 18 диалогах» полезнее придуманного значка Critical. Бизнес-тяжесть можно добавить после определения последствий ошибок с владельцем продукта.
6. **Настройка появляется по необходимости.** Адрес агента, модели и варианты симуляции открываются в момент запуска проверки. Анализ готовых логов не блокируется ненужной настройкой.
7. **Узкий экран сохраняет задачу.** Список сменяется разбором выбранного случая. Полный контекст остаётся доступным через возврат и раскрытие деталей.
8. **Завершение имеет результат.** Пользователь подготовил сценарий, подтвердил или оспорил оценку, либо получил отчёт с границами измерения. Изменение агента выполняется отдельно.

## Информационная архитектура

```text
Agent Lab · выбранный агент
├── Разбор                 очередь нарушений → правило + цитата + вердикт
├── Диалоги                исходные наблюдения → полный разговор / трейс
├── Сценарии               проверки поведения → запуск симулятора
└── Источники              правила / исходники / параметры подключения

Контекст оценки: файл логов ИЛИ конкретный запуск симулятора
Проверка судьи: действие внутри разбора и сводки текущей оценки
Отчёт: вторичное действие для текущей оценки
```

Три области рабочего экрана: небольшая навигация, список проблем, разбор выбранного случая. На первом экране короткая строка измерения, затем работа. Полная статистика раскрывается по запросу.

Смена выборки обновляет и список, и доказательство. Пустой результат фильтра показывает, что известно о выбранной выборке; он не означает, что агент исправлен.

## Как говорить о качестве честно

В просмотренной оценке 150 диалогов: 128 оценены, 22 остались без оценки, 50 — без обнаруженных нарушений. 39% — округлённая доля `50 / 128`, а не доля всех 150 и не вероятность успешного ответа в будущем.

Для первичного экрана подходит: «Оценено 128 из 150 диалогов · 50 без обнаруженных нарушений · 22 без оценки». Процент можно показать вторично вместе со знаменателем.

Есть три ограничения текущей реализации, которые нужно исправить при переносе концепта:

- [`criteria.ts`](../../workshop/app/src/lab/criteria.ts): критерий, который исчез из новой выборки, сейчас может стать «исправлен». Нужен отдельный исход «не проверен в этой выборке». Исчезновение наблюдения не доказывает исправления.
- [`useScope.ts`](../../workshop/app/src/lab/useScope.ts): реальные логи берутся из текущего `state.discover` и повторяются для разных выбранных прогонов. Изменение симулятора следует считать по сопоставимым сценариям, отдельно от логов с незафиксированной версией агента.
- [`judge.py`](../../lab/judge.py) и [`metric.py`](../../lab/metric.py): PASS возможен при наличии одного PASS и отсутствии FAIL, хотя другие правила UNKNOWN; UNMEASURED исключается из знаменателя. Корректное название — «без обнаруженных нарушений», полнота наблюдения показывается отдельно.

Для утверждения «исправлено» нужны наблюдения по тому же правилу в сопоставимых условиях. Для сравнения версий нужно показывать набор сценариев, варианты клиента, повторы, правила и судью. Когда сопоставимости нет, интерфейс объясняет ограничение.

В текущем списке несколько похожих правил о перенаправлении сформулированы отдельно для разных контекстов. Для устойчивого разбора нужна явная идентичность правила и область его применения. Объединять строки только по сходству текста опасно; пользователь должен видеть, оценивается общий запрет или отдельное поведение в сценарии.

## Визуальное направление

Спокойный графитовый рабочий экран. Поверхности различаются достаточно, чтобы читать границы областей без тяжёлых рамок. Текст диалога получает больше пространства и контраста, чем метаданные. Основной акцент используется для выбранного случая и следующего действия; цвет статуса дублируется словами.

Плотность нужна там, где сравнивают строки. Пространство нужно там, где читают и рассуждают. Выразительность продукта создаётся точной композицией доказательства и хорошей типографикой. В прототипе также можно проверить светлую тему как альтернативу для длительного чтения.

Полезные ориентиры по взаимодействию:

- [Linear Triage](https://linear.app/docs/triage): очередь входящих случаев с разбором перед включением в работу. Для Agent Lab заимствуем принцип приоритизации и действия в контексте проблемы.
- [Vercel Build Logs](https://vercel.com/docs/deployments/logs): связь состояния конкретного запуска с диагностикой и адресуемыми строками. Для Agent Lab заимствуем переход от вывода к точному месту доказательства.

Это наши проектные выводы из описанных паттернов, а не утверждение, что эти продукты решают задачу Agent Lab.

## Минимальный перенос в рабочий продукт

1. Перестроить главный экран вокруг текущих нарушений; сохранить существующую оценку, правила и API. Пустую динамику убрать, компактную сводку оставить.
2. Связать выбранное правило с примерами диалогов и происхождением в одном разборе. Сохранить ссылки на полные трейсы.
3. Добавить контекстные действия: оспорить оценку, проверить другим судьёй, открыть или подготовить сценарий. Учесть границы существующего API из таблицы ниже.
4. Устранить ложное «исправлено» при отсутствии данных и смешение выборок разных версий.
5. Перенести навигацию на узкие экраны и разделить первый вход на анализ логов и проверку версии.

Необходимый объём для следующей реализации — связанный рабочий сценарий из существующих объектов. Новые отчётные страницы, универсальная дизайн-система и декоративные графики не являются предпосылками этой проверки идеи.

| Действие концепта | Что поддерживается сейчас | Что требуется для переноса |
|---|---|---|
| Оспорить оценку | `/api/review` хранит согласие/несогласие по целому разговору симулятора | Отдельное решение для одного правила и для вердиктов по логам |
| Проверить другим судьёй | `/api/runs/{id}/rejudge` переоценивает весь прогон симулятора | Адресная переоценка выбранного случая, если она входит в MVP |
| Подготовить сценарий | Можно открыть существующую карточку; `/api/cards` пересобирает набор | Сохранение одного черновика с привязкой к диалогу и правилу |
| Выбрать оценку файла логов | Доступны последние `discover` и загруженные логи | История оценок и идентичность файла, если нужен выбор прошлых результатов |
| Посмотреть происхождение правила | Доступно для части правил из текущего контекста | Явное состояние при отсутствии ссылки; зафиксированный снимок для исторического сравнения |

В прототипе новые действия показываются как локальные черновики. Наличие их в макете не означает готовность backend.

## Что показывает прототип

[`agent-lab-concept.html`](./agent-lab-concept.html) — отдельный интерактивный макет с вымышленными примерами. Он проверяет композицию, переходы и язык. Он не подключён к моделям или API и не меняет реальные данные. Его локальные действия явно отмечены как действия макета.

Для проверки с разработчиками: попросить найти основание выбранной ошибки, сказать, что остаётся неизвестным, оспорить оценку и открыть сценарий повторной проверки. Измерить время и ошибки понимания. Успех — человек способен сделать это без экскурсии автора.
