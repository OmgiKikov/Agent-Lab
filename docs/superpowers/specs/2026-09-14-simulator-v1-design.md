# Симулятор пользователя v1 и промпт как MVP улучшения

Дата: 2026-09-14. База: master после PR #6 (`b3bb8be`, пакет 0.3.0, 202 теста). Язык документа: русский для текста, английский для кода и идентификаторов.

## 1. Цель

Продуктовая рамка владельца: подключить существующего агента, симулировать против него пользователей, оценить, понять, что улучшать; первый объект улучшения — промпт. Ответы команды AI Gateway в исходном Project Frame задают определение ценности симулятора: агент в диалоге отвечает по-разному, а задача пользователя — дойти до завершения через диалог. Значит, симулятор нужен там, где следующий шаг агента нельзя предсказать заранее: уточнения, восстановление после ошибки, смена намерения.

Эта итерация делает симулятор центром продукта и закрывает четыре разрыва, найденных при аудите 14 сентября:

1. Состояние пользователя задано двумя текстовыми полями (`facts`, `behavior`); внешний мир существует только для песочницы.
2. Качество самого симулятора измеряет одна модельная рубрика и четыре стилевые метрики; ни один провал симулятора не ловится кодом.
3. Ценность реактивного режима видна только как «проверки, провалившиеся в одном режиме»; нет учёта уточнений, которые агент реально задал, и нет парной дельты с интервалом в повседневном сравнении прогонов.
4. Цикл «подтверждённый провал → кандидат промпта → отдельная версия → тот же набор» работает для агентов с промптом в файле; для AIGW нет хука выпуска версии, кластеризация провалов молчит на одном провале, а кластер не указывает, какой фрагмент промпта сломался.

Ограничения владельца сохраняются: Pi — единственный интерфейс; методика встроена в код, схемы и промпты; человек утверждает черновик и проверяет результаты; синтетика допустима, но её доля всегда видна; простой вердикт сверху, исследовательская статистика ниже. Каждая новая функция обосновывается доказательством, которое она разблокирует.

## 2. Заветы Anthropic и как они встроены

Источник для человека: «Demystifying evals for AI agents» и «A statistical approach to model evaluations» (Anthropic). Ниже принцип → реализация в этой итерации. Ссылки не используются во время выполнения.

Код никогда не заменяется моделью там, где предикат объективен. |
| «Grade what the agent produced, not the path it took» | Проверки симулятора описывают факты реплик пользователя (сказал скрытое значение, повторил сообщение), а не «правильный ход мыслей». Итог агента по-прежнему определяют состояние, действия и рубрики; проверки симулятора не меняют `trial.outcome`. |
| Дайте модельному оценщику выход `unknown`; сделайте оценщиков устойчивыми к обходу | Сохраняется существующий протокол судьи 6. Кодовые проверки симулятора не подаются судье, чтобы не подсказывать ответ. |

У AIGW заглушка SBE получает переопределение фикстур на конкретный запрос. |
| Многошаговые агенты: проверяемый конечный результат плюс рубрики завершения задачи и качества взаимодействия; второй LLM играет пользователя | Ценность симулятора считается по карточкам: где агент задал уточнение, где только реактивный пользователь довёл до завершения, где только он нашёл провал, и сколько из этого подтвердил человек. |
| Читайте транскрипты; провал должен выглядеть справедливым | Каждая кодовая проверка симулятора цитирует `seq` события и конкретное значение. Кластер провалов цитирует дословный фрагмент промпта, который управлял сломавшимся поведением, либо говорит, что такого фрагмента нет. |
| Capability и regression наборы; 0% чаще означает сломанную задачу, а не слабого агента | Существующие ступени `smoke/regression/frontier` сохраняются. Прогон, где симулятор нарушил карточку в более чем четверти реактивных диалогов, получает доверие не выше среднего с названной причиной. |

| Начинайте с 20–50 задач из реальных провалов | Проверка на AIGW делается тремя рукописными golden-карточками из наблюдённых ситуаций пилота 12 сентября, а не сгенерированной синтетикой. |

## 3. Термины

- **User state** (состояние пользователя): структурированная часть карточки: `knows` (что пользователь знает и может сказать), `cannotKnow` (чего он знать не может), `answers` (ответы на ожидаемые уточнения). Дополняет `goal`, `facts`, `behavior`, не заменяет их.
- **External state** (внешнее состояние): `initialState.external`, произвольный JSON для тестового контура агента: карты, договоры, статусы, фикстуры инструментов. Симулятор его не видит; адаптер обязан применить и подтвердить.
- **Hidden literal** (скрытое значение): скалярное значение из `initialState.records` или `initialState.external`, которого нет в известных пользователю полях. Если симулятор произнёс его раньше агента, это утечка.
- **Simulator check** (проверка симулятора): кодовый предикат над репликами симулированного пользователя одного диалога: `leak`, `fabrication`, `loop`. Хранится отдельно от проверок агента и не влияет на исход диалога.
- **Simulator scorecard** (карточка симулятора): сводка по прогону: сколько реактивных диалогов, сколько отмечено каждой проверкой, что сказал судья по рубрике верности, что сказал человек, сколько уточнений агента получили ответ.
- **Clarification** (уточнение): реактивный диалог, в котором симулятор отправил хотя бы одну ответную реплику после первого ответа агента.
- **Mode value** (ценность режима): по карточке: исход в каждом режиме; карточки, которые завершил только реактивный режим; карточки, которые провалил только он; подтверждения человека.
- **Paired family delta** (парная дельта по семействам): для двух сравнимых прогонов доля прошедших карточек по семейству «после» минус «до», среднее по семействам и bootstrap-интервал.
- **Release hook** (хук выпуска): команда в подключении, которую Agent Lab выполняет перед прогоном внешнего агента, чтобы развернуть проверяемую версию; идентичность версии по-прежнему сообщает адаптер.
- **Prompt quote** (цитата промпта): дословный фрагмент промпта агента, который кластер провалов называет ответственным за сломавшееся поведение.

## 4. Архитектура

Швы не меняются: `Runtime` для моделей, `TargetSession` для испытуемого, `ExperimentLab` для фаз, чистые функции над записью для статистики, расширение Pi для человека. Новый модуль `src/simulator.ts` содержит кодовые проверки симулятора и его статистику, чтобы `comparison.ts` не превысил 1000 строк.

```
карточка (user state + external) ──► evaluation.ts: цикл диалога
        │                                   │ после цикла, только reactive
        │                                   ▼
        │                          simulator.ts: simulatorChecks(scenario, trial)
        │                                   │ trial.simulatorChecks
        ▼                                   ▼
адаптер получает initialState.external   comparison.ts / simulator.ts:
и подтверждает resetConfirmed            simulatorSummary · modeValue · delta
                                                    │
                                          evidenceSummary(record) — единый снимок
                                                    │
                                  доска Pi · HTML · Markdown · JSON · CLI diff/pilot
```

Поток одного прогона не меняется: подготовка → review → evaluating → results_review. Перед `runSuite` для внешнего испытуемого с `target.release` выполняется хук выпуска.

## 5. Карточка: состояние пользователя и внешний мир

### 5.1 Схема

`userSchema` получает три необязательных поля с пустыми значениями по умолчанию:

```ts
knows: z.array(text.max(300)).max(20).default([])        // атомарные факты, известные пользователю
cannotKnow: z.array(text.max(300)).max(20).default([])   // чего пользователь знать не может, словами
answers: z.array(z.strictObject({ ifAsked: text.max(300), reply: text.max(1000) })).max(20).default([])
```

`facts` и `behavior` остаются обязательными: `facts` — контекст своими словами, `knows`/`answers` — точные значения. Элементы `knows` уникальны без учёта регистра. `answers[].ifAsked` описывает вопрос агента словами, `reply` — реплика пользователя целиком.

`worldSchema` получает `external: z.record(z.string(), z.unknown()).optional()`; сериализованный размер не более 20 000 символов, проверка в `.superRefine`. Песочница поле игнорирует. Значение попадает в `initialState` каждого запроса к http/command адаптеру и в `createSession` модульного адаптера без изменений протокола: адаптеры уже получают `initialState` целиком.

Все три поля входят в хеши черновика и измерения автоматически, потому что хешируются карточки. Старые записи и наборы загружаются с пустыми значениями. `goldenCaseSchema` принимает те же поля и передаёт их в `goldenToScenario`.

### 5.2 Что видит симулятор

`runtime.userTurn` получает `goal`, `facts`, `behavior`, `opening`, `maxFollowUps`, `persona`, `characteristics` и новые `knows`, `cannotKnow`, `answers`. `initialState`, включая `external`, симулятору не передаётся; регрессионный тест с sentinel-значением в `external` проверяет, что оно не попадает в запрос.

`SIMULATOR_ROLE` дополняется правилами: значения из `knows` и `answers[].reply` использовать дословно; на вопрос, который не покрыт `knows`, `facts` или `answers`, отвечать, что не знаешь, или переспросить, но не выдумывать; ничего из `cannotKnow` не утверждать и не предполагать.

### 5.3 Что генерирует модель

`cardsRole` требует для каждой карточки: `knows` с точными значениями, которые пользователь может назвать; `cannotKnow` с тем, что относится к backend или к правильному ответу; `answers` для каждого уточнения, которое агент вероятно задаст; `facts` остаётся коротким контекстом. Для внешнего агента без контракта состояния `external` не выдумывается: генератор оставляет его пустым, если материалы не описывают тестовые данные. `EXTERNAL_CARDS_CLAUSE` получает соответствующую строку.

`validatePreparation` проверяет сгенерированные карточки: токены-значения из `answers[].reply` (правило токенов в разделе 6.2) должны встречаться в `knows`, `facts` или `opening`; иначе карточка отклоняется с указанием значения как выдающая пользователю неизвестное, и модель получает шанс исправить ответ через существующий цикл repair. Golden и production карточки через это правило не проходят: их поля задал владелец или реальный диалог. Значение из `initialState`, которое пользователь законно знает, например собственный номер записи, остаётся в `knows` и не считается скрытым.

Демо-runtime (`demo.ts`) заполняет `knows` и `answers` для своих карточек: карточка уточнения получает `answers: [{ ifAsked: 'appointment ID', reply: 'My appointment ID is A103.' }]`, карточка смены намерения — `knows` с обоими временами. Демо-симулятор отвечает из `answers`, а не из регулярного выражения по `facts`.

### 5.4 Редактор и доска

В редакторе карточки появляются поля «Знает», «Не может знать», «Ответы на уточнения» и «Внешнее состояние» (JSON). Ошибка ввода сохраняет текст для исправления, как у остальных полей. `agent_lab_edit` принимает те же поля через `patch.scenarios`.

## 6. Проверки симулятора кодом

### 6.1 Где и когда

`src/simulator.ts` экспортирует `simulatorChecks(scenario, trial): SimulatorCheck[]`. Вызывается в `evaluateTrial` после завершения цикла и до `grade`, только когда `simulatorWasUsed(trial)`: режим `reactive` и есть хотя бы одно событие `simulator`. Для static и scripted массив пуст. Результат сохраняется в `trial.simulatorChecks` (схема: массив, по умолчанию `[]`; старые записи читаются).

```ts
export interface SimulatorCheck { id: 'simulator.leak' | 'simulator.fabrication' | 'simulator.loop'; description: string; passed: boolean; evidence: string; seq?: number; heuristic: boolean }
```

Проверки не меняют `trial.outcome`, `trial.checks`, оценки судьи и не подаются судье. Они попадают в экспорт, на доску и в сводку.

### 6.2 Алгоритмы

Реплики симулятора: события `type: 'user'` с `seq` больше первого пользовательского события диалога. Текст ответов агента до реплики: события `type: 'assistant'` с меньшим `seq`.

Известный пользователю текст: `opening`, `facts`, `knows`, `answers[].ifAsked`, `answers[].reply`, `persona`, `characteristics`, `script`, `goal`, `behavior`.

Токен-значение: максимальная последовательность символов из класса `[A-Za-zА-Яа-яЁё0-9:./-]`, содержащая хотя бы одну цифру, длиной не менее 3 после отрезания завершающих `.`, `,`, `:`; сравнение без учёта регистра. Примеры: `4321`, `A103`, `14:00`, `202-7`, `7701234567`, `11.03.2024`.

- **leak.** Скрытые значения: все скалярные листья `initialState.records` и `initialState.external` (строки и числа; булевы и null исключены), строковая форма длиной не менее 3, из которых убраны значения, встречающиеся в известном пользователю тексте. Проверка отмечена как непройденная, если реплика симулятора содержит скрытое значение, которого не было ни в одном ответе агента с меньшим `seq`. Доказательство: `seq`, значение. Проверка не создаётся, если множество скрытых значений пусто; `heuristic: false`.
- **fabrication.** Токены-значения реплики симулятора, которых нет ни в известном пользователю тексте, ни в ответах агента с меньшим `seq`, ни в более ранних репликах пользователя этого диалога. Первый такой токен даёт непройденную проверку с `seq` и токеном; описание прямо называет это подозрением. `heuristic: true`. Проверка создаётся для каждого реактивного диалога с хотя бы одной репликой симулятора.
- **loop.** Нормализация: нижний регистр, удаление всех символов, кроме букв и цифр. Реплика симулятора, совпавшая после нормализации с любой более ранней репликой пользователя того же диалога и длиннее двух символов, даёт непройденную проверку с обоими `seq`. `heuristic: false`.

### 6.3 Влияние на вердикт и код выхода

`verdictSummary.simulatorFlagged` считает диалоги, в которых непройдена хотя бы одна кодовая проверка симулятора или рубрика верности судьи вернула `fail`. Если таких диалогов больше четверти реактивных, `confidence` не выше `medium` с причиной «симулятор нарушил карточку в K из N реактивных диалогов; их оценки требуют проверки» и шагом «откройте отмеченные диалоги». `evaluationExitCode` сохраняет правило: отмеченный симулятор — неполное измерение, код 2; правило действует только для реактивных диалогов, поэтому сохранённые static-наборы в CI не затрагиваются.

### 6.4 Ручной разбор

`humanReviewInputSchema.checkId` принимает идентификаторы проверок симулятора; `addHumanReview` проверяет, что идентификатор есть в `trial.checks` или `trial.simulatorChecks`. Вердикт человека по проверке симулятора учитывается в карточке симулятора как подтверждение или опровержение, не меняя кодовый результат. На доске в карточке результата строки проверок симулятора идут отдельным блоком «Симулятор», вердикт ставится через существующее `v`.

## 7. Ценность симулятора

### 7.1 Карточка симулятора

`simulatorSummary(record)` в `src/simulator.ts`:

```ts
export interface SimulatorSummary {
  reactiveDialogues: number;
  checks: { id: SimulatorCheck['id']; dialogues: number; flagged: number; heuristic: boolean; examples: { trialId: string; seq?: number; evidence: string }[] }[];
  judge: { applicable: number; pass: number; fail: number; unknown: number; missing: number };
  human: { reviewed: number; confirmed: number; rejected: number };
  clarifications: { dialogues: number; answered: number };
  disengaged: number;
  notes: string[];
}
```

`judge` считает результаты рубрики `user_fidelity` по реактивным диалогам; `human` — последние вердикты человека по этой рубрике и по проверкам симулятора; `clarifications.dialogues` — реактивные диалоги, где агент дал больше одного ответа; `answered` — из них те, где симулятор отправил непустую ответную реплику; `disengaged` — диалоги, завершённые `done: true` без сообщения до достижения цели. Примеры ограничены тремя на проверку. `notes` объясняют пустые части: «реактивных диалогов нет», «рубрика верности не применялась».

### 7.2 Ценность режима

`modeValue(record)` в `src/simulator.ts`:

```ts
export interface ModeValue {
  cards: { scenarioId: string; title: string; familyId: string; outcomes: Partial<Record<UserMode, 'pass' | 'fail' | 'unknown' | 'missing'>>; clarification: boolean }[];
  reactiveOnlyCompleted: string[];   // scenarioId
  reactiveOnlyFailed: string[];
  humanConfirmed: { completed: number; failed: number };
  measuredModes: UserMode[];
  notes: string[];
}
```

Исход карточки в режиме: `pass`, если все оценённые повторы прошли по `automaticTrialResult`; `fail`, если хотя бы один провалился; `unknown`, если есть неопределённые; `missing`, если попыток нет. `reactiveOnlyCompleted` — карточки с `pass` в reactive и `fail` во всех остальных измеренных режимах; `reactiveOnlyFailed` — обратное. Если измерен один режим, оба списка пусты, а `notes` говорят об этом. `humanConfirmed` считает последние решающие вердикты человека на реактивных попытках этих карточек. Существующий `pilotSummary` не меняется; `modeValue` дополняет его.

### 7.3 Парная дельта в сравнении прогонов

`compareRuns` получает поле `delta`:

```ts
delta: { families: number; mean: number | null; interval: [number, number] | null; note: string } | null
```

Считается только для сравнимых прогонов. Для каждого семейства доля прошедших карточек «после» минус «до» по спискам `cards`; `mean` — среднее по семействам; `interval` — существующий `clusterInterval(familyDeltas, seed)` при двух и более семействах, иначе `null`. `note`: «Описательная парная дельта по семействам; вердикт определяется списками карточек». Карточки без `familyId` образуют семейство по своему `scenarioId`. CLI `diff`, HTML и Markdown показывают дельту после списков «сломалось/исправлено».

### 7.4 Где показывается

`evidenceSummary` получает `simulator: SimulatorSummary` и `modeValue: ModeValue`. Доска: секция «Статистика» показывает блок «Симулятор» и блок «Ценность режимов» после существующих режимов; карточка результата показывает проверки симулятора. Отчёты HTML, Markdown, JSON берут те же данные из снимка. `agent_lab_inspect` и CLI `export` возвращают их автоматически. `pilot` печатает `pilot` и `modeValue`.

## 8. Внешний мир в тестовом контуре

### 8.1 Контракт адаптера

Документируется в REFERENCE.md: `initialState.external` приходит в каждом запросе http/command и в `createSession` модуля. Адаптер, применивший его к тестовой среде, ставит `resetConfirmed: true` в первой реплике; иначе `resetConfirmed` отсутствует или `false`. Если карточка задала `external`, а первая реплика не подтвердила сброс, `trial.reason` получает суффикс «; внешнее состояние карточки не подтверждено адаптером», проверки состояния остаются невалидными по существующему правилу, а в `limitations` прогона один раз добавляется строка об этом.

Тестовая фикстура `test/fixtures/stdio-agent.mjs` получает режим `external`: отвечает перечислением `external.cards` и подтверждает сброс. `examples/echo-agent.py` описывает поле в docstring и по-прежнему подтверждает сброс; копировать `external` в `records` не требуется, это разные вещи: `records` — наблюдаемый итог, `external` — заданная среда.

### 8.2 aigw-local

Изменения в локальном слое `~/Desktop/aigw-local/local`, банковский код сервиса не трогается:

- `mocks/server.py`: `POST /mock/overrides` с телом `{ "trace_id": "...", "sbe": { "tools": { ... } } }` сохраняет переопределение мира SBE для запроса с таким `x-trace-id`; не более 1000 записей, старые вытесняются. `sbe_execute` сначала ищет инструмент в переопределении, затем в `sbe.json`; в журнал пишется `override: true|false`. `GET /mock/overrides` показывает число записей. `DELETE /mock/overrides` очищает.
- `agent_lab_target.py`: перед каждым запросом, если `initialState.external.sbe` задан, регистрирует переопределение для сгенерированного `x-trace-id`; при ошибке регистрации возвращает `measurementError`. Ответ адаптера дополняется `resetConfirmed: true` на первом ходу (новый `conversation_id`, переопределение применено), `eventsComplete: true` с `eventScope: ["idp_search", "sbe_*", "agent_outcome"]` (полнота журнала уже проверяется по курсору и эпохе), `sessionId`, `turn`, `version` (короткий хеш HEAD локального репозитория плюс маркер режима заглушки GigaChat из `/mock/health`) и `promptHash`, если сервис загрузил промпт из MLS-кэша: sha256 от JSON-строки полного текста файла `agent_doc_type_prompt.json`, совпадающий с `fingerprint(prompt)` Agent Lab.
- `test_agent_lab_target.py`: тесты на переопределение по trace_id, на непереопределённый инструмент, на поля ответа.

## 9. Промпт как MVP улучшения

### 9.1 Хук выпуска версии

`targetSchema` для http, module и command получает необязательное `release`:

```ts
release: z.strictObject({ command: text.max(4000), args: z.array(text.max(4000)).max(50).default([]), cwd: absolutePath.optional(), timeoutMs: z.number().int().min(1000).max(600000).default(120000) }).optional()
```

`ExperimentLab.launch` выполняет хук один раз перед `runSuite` для внешнего испытуемого, до первого запроса. Переменные окружения процесса: `AGENT_LAB_RUN_ID`, `AGENT_LAB_TARGET_VERSION`, а при `promptFile` — `AGENT_LAB_PROMPT_FILE` и `AGENT_LAB_PROMPT_HASH`. Ненулевой код завершения или таймаут переводит прогон в `error` с хвостом stderr. Хвосты stdout и stderr (до 4000 символов) сохраняются в `record.releaseLog`. Идентичность версии по-прежнему приходит от адаптера в `version`; хук её не подменяет. Preflight проверяет исполняемость команды хука так же, как у command-таргета. `doctor` хук не выполняет. `portableTarget` и `resolveTarget` относительные пути хука разрешают как у command.

Для AIGW добавляется `local/release.sh`: копирует `AGENT_LAB_PROMPT_FILE` в `local/mls_prompts/<repository>/<project>/<model>/<version>/agent_doc_type_prompt.json`, перезапускает сервис с `MLS_CLIENT_ENABLED=True`, ждёт `/health`. Это доказывает механику на настоящем сервисе; расширение на промпты, зашитые в код, требует отдельного локального патча и остаётся за рамками.

### 9.2 Кластеризация и цитаты промпта

`nameFailureModes` вызывается при одном и более провалившемся диалоге. Если у испытуемого известен промпт — содержимое `target.promptFile` для внешнего агента или `revision.spec.instructions` для песочницы, — он передаётся роли `FAILURE_MODES_ROLE` как `prompt`. Схема кластера получает `promptQuotes: z.array(text.max(300)).max(5).default([])`; `validateFailureModes` проверяет, что каждая цитата дословно содержится в промпте, и отклоняет цитаты, когда промпт не передавался. Роль получает правило: цитировать только фрагменты, которые управляют сломавшимся поведением, либо оставлять список пустым и говорить об этом в `mechanism`.

Цитаты показываются в блоке провалов на доске и в отчётах. `agent_lab_prompt propose` в скилле получает указание опираться на них при формулировке гипотезы.

## 13. Границы и не-цели

- Не генерируется расширенная static-корзина под равный бюджет; сравнение режимов остаётся описательным при равных карточках, стоимость по режимам показывается.
- Не обучается симулятор; заземление остаётся промптом и профилями из логов.
- Не строится веб-интерфейс, очередь, коннекторы к логам.
- Не расширяется набор инструментов песочницы.
- Кандидат промпта не применяется к сервису автоматически: хук выпуска запускается только внутри подтверждённого человеком прогона отдельной версии.
- Эвристика выдумки помечена как подозрение; её ложные срабатывания подлежат ручному опровержению, а не автоматической фильтрации.
