## 1. Что не так

- **Модели вызываются из 11 мест, и каждое устроено по-своему.** `discover` (темы и раскладка), `judge` (диалоги и
  прогоны), `tone`, `severity`, `cards`, `agents/world`, `simulate` (клиент и первое сообщение), `tone_advice`. В каждом
  свой промпт, своя сборка запроса, свой разбор и своя проверка ответа. На вопросы «какой инструкцией получен вердикт»,
  «сколько стоила проверка» и «почему судьи разошлись» код не отвечает: вызовы нигде не записываются.
- **Смена инструкции судьи не меняет отпечаток оценки.** `history.evaluation_fingerprint` учитывает только имена
  моделей. Если между двумя проверками изменился промпт судьи, «было → стало» всё равно сравнит их как сделанные «теми
  же моделями».
- **`store.py` (790 строк) и хранит, и решает.** Что сбрасывать при новой выгрузке, когда переносить итог в историю —
  это правила продукта, а лежат они в слое хранения. Ради них `store` импортирует `accuracy_history`, тот — `discover` →
  `judge` → `llm` → `gateway` → снова `store`. Получается цикл из 11 модулей, и держится он на отложенных импортах
  внутри функций. Из 40 модулей 20 обращаются к `store` напрямую.
- **`api.py` (804 строки) — все маршруты вперемешку со сборкой процессов.** Проверка точности, tone of voice, прогон,
  переоценка и серьёзность собираются прямо в обработчиках.
- **Настройки читаются при импорте.** `settings.py` и `llm/__init__.py` берут окружение при загрузке модуля, и тесты
  подменяют атрибуты модулей.
- **Документы целиком.** Ответ человека переписывает весь итог и не хранит автора. Открытие одного разговора разбирает
  всю выгрузку, а `/api/state` отдаёт итоги целиком на каждый опрос.

## 2. Решение: процесс с ролями, а не автономный агент

Agent Lab — измерительный прибор: по его числам решают, хорош ли агент. Числа должны воспроизводиться и объясняться.
Поэтому порядок шагов задаёт код (workflow), а модели исполняют **роли** с типизированным контрактом. Автономный агент,
который сам выбирает следующий шаг, здесь вреден. При двух запусках он сделал бы разные шаги, и числа разошлись бы
по причине, которую никто не назовёт.

Настоящий цикл с моделью в Lab один — синтетический клиент, который разговаривает с проверяемым агентом. Он остаётся
циклом, но внутри процесса: лимит ходов, остановка, запись разговора один раз в конце (как сейчас в `simulate`).

Слои и направление зависимостей:

```
api/        HTTP: маршруты по разделам, проверка входа, ответ
  │
flows/      процессы продукта: проверка точности, tone of voice, сценарии, прогон, переоценка,
  │         серьёзность, чтение кода агента, выгрузка. Здесь же правила «что сбрасывает что»
  ├──────────────┬──────────────────┬──────────────────────────────┐
roles/         domain/            storage/                        agents/
роли моделей   правила без        SQLite: входы, итоги, прогоны,   проверяемый агент: HTTP,
  │            ввода-вывода:      история, ответы людей,           запуск из кода, мир заглушек
  │            цитаты, вердикт,   разговоры, журнал вызовов
  │            метрика, история
models/        доступ к моделям: OpenRouter и любой OpenAI-совместимый endpoint, шлюз банка;
               повторы, лимит параллельности, журнал вызовов
```

Правило: стрелки идут только вниз. `domain` не импортирует из Lab ничего. `storage` не знает о процессах, ролях и
моделях. `roles` знают только `models` и `domain`. Направление проверяет тест (п. 11).

## 3. Роль модели

Роль — значение, а не класс с состоянием: имя, инструкция, тип ответа. Вызов — одна функция.

```python
@dataclass(frozen=True)
class Role(Generic[Reply]):
    """One job a model does in the Lab: its instructions and the shape of its answer."""

    name: str  # 'judge.log'
    instructions: str  # the system prompt
    reply: type[Reply]  # a Pydantic model

    @cached_property
    def version(self) -> str:
        """Changes with the instructions or the shape of the answer: a check made by another version of a role is
        not compared as made by the same models (history.evaluation_fingerprint)."""
        schema = json.dumps(self.reply.model_json_schema(), sort_keys=True)
        return hashlib.sha256(f'{self.instructions}\n{schema}'.encode()).hexdigest()[:12]


async def ask(
    role: Role[Reply],
    payload: dict,
    *,
    check: Callable[[Reply], Reply] = lambda reply: reply,
    model: Endpoint | None = None,
) -> Answer[Reply]:
    """One answer of a role: the payload as JSON, the reply parsed into its type and checked by the caller's rule
    (grounding, coverage), asked again once when unusable. Every call goes to the journal."""
```

Пример — судья диалога:

```python
JUDGE_LOG = Role('judge.log', prompts.JUDGE_LOG, JudgeReply)

async def log_verdict(rules: list[dict], shown: list[dict], model: Endpoint | None = None) -> Verdict:
    answer = await ask(JUDGE_LOG, {'expectations': rules, 'conversation': shown},
                       check=lambda reply: covered(reply, rules), model=model)
    rows = checked(answer.value.rules, rules, log_words(shown))
    return Verdict(rows, verdict_of(rows), answer.model, JUDGE_LOG.version)
```

Роли, которые уже есть в коде:

| Роль | Сейчас | Ответ | Проверка ответа |
|---|---|---|---|
| `planner` — темы и критерии | `discover.PLAN` | темы с критериями | цитата есть в коде (`quotes.found`), разложено не меньше 90% разговоров |
| `router` — раскладка новых разговоров | `discover.ASSIGN` | раскладка | известные разговоры и темы |
| `judge.log` — вердикт по диалогу | `prompts.JUDGE_LOG` | `JudgeReply` | ровно один вердикт на критерий, цитата из слов агента |
| `judge.run` — вердикт по прогону | `prompts.JUDGE_RUN` | `JudgeReply` с целью клиента | то же и цель клиента |
| `tone.criteria` — критерии из правил | `tone.PROMPT` | критерии | цитата есть в правилах, цитаты не повторяются |
| `severity` — серьёзность ошибок | `severity.PROMPT` | предложения | известные критерии |
| `scenario` — сценарий из разговора | `prompts.CARD` | карточка | есть имя и ситуация |
| `world` — данные заглушек | `prompts.WORLD` | мир | инструменты по именам |
| `customer` — синтетический клиент | `prompts.SIMULATOR` | реплика | конец разговора по `[КОНЕЦ]` |
| `customer.opening` — первое сообщение в манере | `prompts.PERSONA_OPENING` | текст | — |
| `tone.advice` — правка и уточнение | `tone_advice` | предложение | числа, даты и контакты не изменились |

Вторая модель — та же роль у другой модели, а не отдельная роль.

**Журнал вызовов.** Каждый вызов записывается в базу агента: роль, версия, модель, начало, длительность, токены,
стоимость (если модель её назвала), исход (ответ принят, не разобран, отказ, сбой), к какой проверке или прогону
относится. Тексты разговоров в журнал не пишутся: они уже лежат в итоге. Журнал отвечает на вопросы «сколько стоила
проверка», «какой версией судьи получен вердикт», «где модель отказывает чаще».

**Версии в отпечатке оценки.** `evaluation_fingerprint` учитывает версии ролей, которые судили. Следствие: после
перехода первая проверка один раз скажет «Изменились модели проверки». Это честно: прежние проверки делались
инструкциями, версия которых не записана.

## 4. Процессы

Процесс — модуль, который собирает роли, хранение и правила в одну операцию продукта. Только он открывает транзакции
и решает, что сбрасывать. Обработчик HTTP проверяет вход и вызывает процесс, задание (`jobs`) даёт ему прогресс и
остановку.

- `flows/accuracy.py` — выборка → темы (`planner` или `router`) → вердикты двух судей → сводка → история →
  предложения о серьёзности.
- `flows/tone.py` — правила → критерии (из кода правил или `tone.criteria`) → выборка → вердикты → сводка → история →
  предложения.
- `flows/scenarios.py` — разговоры с ошибками и контроли → `scenario` → колода.
- `flows/simulation.py` — прогон (мир заглушек, сессия с агентом, `customer` до конца, `judge.run`) и переоценка
  (всё или ничего).
- `flows/severity.py`, `flows/sources.py` (чтение кода агента), `flows/export.py` (выгрузка).
- `flows/inputs.py` — правила «что сбрасывает что» при замене выгрузки, кода или правил общения. Сейчас они в
  `store.replace_inputs`.

## 5. Хранение

`storage/` делится по тому, что хранится, с одним соединением и одной схемой (`user_version`):

| Модуль | Что | Изменение |
|---|---|---|
| `documents` | входы, черновики, итоги проверок | итог остаётся неизменяемым JSON |
| `dialogues` | разговоры выгрузки строками с индексом по id | разговор открывается без разбора всей выгрузки, выборка не читает лишнего |
| `runs` | прогоны | как сейчас |
| `history` | сохранённые проверки обеих проверок | одна таблица вместо двух похожих |
| `reviews` | ответы людей строками: проверка, разговор, критерий, решение, вердикт и цитата, кто, когда | запись ответа за O(1), журнал и автор |
| `calls` | журнал вызовов моделей | новое |
| `registry` | агенты | как сейчас |

`/api/state` отдаёт сводки и штампы. Итоги экраны просят отдельно, по штампу, как уже просят детали.

## 6. Настройки и подключения

`config.Settings` — одна Pydantic-модель: папка данных, модели, шлюз, лимиты. Строится один раз в `lifespan` и
передаётся через контекст (как сейчас `store.AGENT`). При импорте окружение не читается, тест строит свои настройки
явно.

`models/` — один вход `ask_model(endpoint, system, messages)` и два адаптера: `openai_compatible` (OpenRouter, любой
endpoint) и `gateway` (шлюз банка). Повторы, лимит параллельности и журнал — один раз, над адаптерами.
`agents/` — то, с чем разговаривает клиент: HTTP-агент, агент из кода, мир заглушек, сессия.

## 8. Что не делаем

- **Фреймворк для агентов не подключаем.** PydanticAI, LangGraph и похожие решают выбор инструментов моделью и
  автономные циклы, а Lab выполняет фиксированный процесс. Шлюз банка с mTLS и своим форматом всё равно потребовал бы
  своего адаптера. Слой ролей занимает около 150 строк и убирает дублирование из 11 мест. Правило из
  `docs/backend.md` остаётся: библиотека приходит, когда удаляет больше кода, чем добавляет.
- **Классы не множим.** Роль — замороженное значение, вызов — функция, процесс — модуль функций. Класс — только для
  ресурса, который открывают и закрывают (сессия агента, соединение).
- **DI-контейнер не вводим.** Зависимости — параметры функций и контекст агента. Фейки моделей и агента подставляются
  в тестах так же, как сейчас.

## 9. Где агентность понадобится по-настоящему (не в этом переходе)

- **Разбор причины.** По проблеме модель с инструментами (прочитать файл, найти по коду) ищет место в коде агента,
  которое даёт ошибку. Сейчас эту работу делает «Задача для разработчика» руками разработчика.
- **Проверка правки.** Цикл «предложить правку промпта → сыграть сценарии проблемы → судья» (evaluator-optimizer).
  Число попыток ограничено, каждый шаг пишется.

Обе строятся поверх ролей и процессов. Если цикл с инструментами станет сложнее нескольких десятков строк, это повод
пересмотреть п. 8.

## 10. Порядок перехода

Каждый шаг — отдельный PR. Тесты зелёные, сквозной прогон проходит, поведение продукта не меняется, если не сказано
иное.

1. **Тест направления импортов и `config.Settings`** — около 1 дня. Нынешние нарушения записаны в тесте списком
   исключений, список только сокращается.
2. **`roles/` и `ask`** — около 2 дней. 11 мест вызова переходят на роли, журнал вызовов (схема 6), версии ролей в
   отпечатке оценки. Видимое изменение: одно «Изменились модели проверки» после перехода.
3. **`flows/`** — 1–2 дня. Правила «что сбрасывает что» уходят из `store` в `flows/inputs.py`, цикл импортов исчезает,
   исключения из шага 1 уходят. Процессы выносятся из обработчиков `api.py`.
4. **`storage/`** — около 2 дней. `store.py` делится по таблице п. 5, ответы людей и разговоры становятся строками
   (схема 7, перенос данных при открытии базы).
5. **`api/` по разделам и лёгкий `/api/state`** — около 2 дней, вместе с экранами: итоги приходят отдельно по штампу.
6. **Оценка судьи по ответам людей** — около 1 дня. `python -m lab.eval judge` считает, как часто люди соглашаются с
   судьёй по каждой роли и версии. Ответы людей становятся набором для проверки самого прибора.

Всего около 9–10 дней работы. Шаги 1–3 можно делать без изменений на экранах.
