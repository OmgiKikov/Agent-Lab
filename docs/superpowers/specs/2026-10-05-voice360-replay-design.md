# Повтор разговоров Voice360 с трейсами: спека

Дата: 5 октября 2026. Основание — схема «LLM judge (RAG)» с доски и выгрузка Voice360 (866 диалогов агента эквайринга).
PoC только для агента эквайринга: общий контракт «агента под тестом» сознательно отложен.

## 1. Что не так сейчас

- Выгрузка Voice360 — это диалог одной строкой `CLIENT … AGENT …` и статус-коды по агентам. В ней нет того, что
  нужно для оценки RAG: какой запрос агент отправил в IDP, что IDP нашёл, по какому промпту сгенерирован ответ.
  Восстановить это из логов нельзя.
- Lab оценивает реальные логи только по тексту диалога (`judge.log_verdict`), а прогоны — с «трейсами» из журнала
  заглушек (`/mock/calls`: запрос и id статьи). В боевом контуре с настоящим IDP трейсов нет вовсе.
- Lab шлёт агенту только `content.user_input`. Агент не хранит переписку, поэтому видит одну последнюю реплику.

## 2. Решение

Проигрываем диалоги из Voice360 через живого агента эквайринга шаг за шагом и на каждом шаге записываем, что
происходило внутри агента. Судья оценивает новый ответ агента вместе с трейсом.

```
Voice360 .xlsx ──(logs.py)──► диалоги U/A
        │
        ▼
  Повтор (Lab, replay.py)
   для каждого диалога, для i = 1..n реплик клиента:
     history = реплики из лога до i-й реплики клиента
     ──► агент эквайринга (локальное подключение: local-code или local-http, aigw-local)
            ответ + status_code
            трейс шага ◄── GET /local/agent-lab/trace/{x-trace-id}
     шаг = {реплика клиента, ответ прода, новый ответ, трейс}
        │
        ▼
  Судья: тон + промпты + RAG ──► по каждому критерию PASS/FAIL/… + пояснение + цитата
```

### 2.1 Режим повтора: «дословно + история из лога»

На шаге i агент получает историю **из лога** (реплики клиента и ответы прода до i-й реплики клиента) и i-ю реплику
клиента. Его ответ сравнивается с ответом прода на этом шаге. Так каждый шаг честен, даже если агент на предыдущем
шаге ответил иначе: следующая реплика клиента из лога отвечает на ответ прода, а его агент и видит в истории.

Шаги одного диалога идут последовательно в одном `conversation_id`: агент хранит в Postgres «доску» флагов
по разговору (новый ли разговор, повторный вопрос). Эти флаги копятся из ответов повтора, а не прода; для PoC это
допустимо.

### 2.2 Сторона агента (aigw-local, только `local/`)

Бизнес-код агента не меняется. `local/agent_lab_app.py` (уже подменяет MLS при старте) дополнительно записывает трейс:

- **Ключ трейса.** Middleware кладёт `x-trace-id` запроса в contextvar. `asyncio.create_task` копирует контекст, поэтому
  фоновая задача IDP попадает в тот же трейс.
- **LLM.** Обёртка над `LoggingGigaChatWrapper.ainvoke/invoke`: `chain_name` из `config["configurable"]`, отрендеренные
  сообщения (system/user), ответ модели. Подменяется метод класса — цепочки держат ссылку на один объект-обёртку.
- **IDP.** HTTP-хуки request/response на `APP_CTX.idp_client` (объект мутируется, не заменяется: модули связали его при
  импорте): `query`, `filter`, `stuff_system_prompt`, источники (`sberhelp_uuid`, `passage_index`, оценки
  retrieval/reranker, текст), сгенерированный ответ.
- **SBE.** Те же хуки на `APP_CTX.sbe_client` / `sbe_tool_client`: инструмент и аргументы.
- **Выдача.** Трейсы в памяти с ограничением по числу и времени; `GET /local/agent-lab/trace/{trace_id}` → 404, если
  трейса нет.

Формат трейса:

```json
{"traceId": "…",
 "chains": [{"name": "idp_input_chain", "messages": [{"role": "system", "content": "…"}], "output": "…", "seconds": 1.2}],
 "rag": [{"query": "…", "filter": "*Эквайринг*", "systemPrompt": "…",
          "passages": [{"article": "uuid", "passage": 3, "text": "…", "retrieval": 0.71, "reranker": 0.93}],
          "answer": "…", "reason": null}],
 "systems": [{"tool": "getLkkTariff", "arguments": {}, "status": 200}]}
```

Работает одинаково на заглушках (этот ноутбук) и с настоящими IDP и GigaChat (рабочий компьютер): запись идёт внутри
процесса агента.

### 2.3 Запрос Lab к агенту

При повторе `local_request` передаёт историю: `content.phrases[]` (`speaker_type` CUSTOMER/ROBOT, `time` по порядку,
`phrase_id`) и `trigger_phrase_id` последней реплики клиента; `user_input` — текст этой реплики; `sender` —
`GIGAASSISTANT`, как у чата в выгрузке (`agentCode` содержит `AGENT_GIGACHAT`). Трейс шага Lab запрашивает только
при повторе (`HttpAgent.say` с историей); обычные симуляции не меняются и трейс не запрашивают.

Что агент делает с историей (`utils/common_utils.py`, `form_dialog_parts_from_phrases`): для отправителей-ассистентов
(`GIGAASSISTANT`, `TEXTASSISTANT`) реплики ROBOT отбрасываются, и агент видит все реплики клиента. Так же он работает
в проде, поэтому ответы прода в истории нужны Lab и судье, а не агенту.

Проверено 5 октября на заглушках: с `sender=GIGAASSISTANT`, `surface_mode=CHAT` и `time` вида
`2026-01-01T00:00:01+00:00` агент отвечает 200, а в промпт `idp_input_chain` попадают все реплики клиента без реплик
ROBOT.

### 2.4 Повтор в Lab (`backend/lab/replay.py`)

Отдельная задача в `jobs`, как `discover` и `tone`.

1. **Диалоги.** Выборка из импортированной выгрузки (`logs.json`) с фиксированным seed (`discover.sample`). Тема
   диалога — из последней проверки «Точность»; диалог вне её раскладывается по темам `discover.keep_topics`.
2. **Шаги.** По одному на каждую реплику клиента. Диалоги идут параллельно (до 4), шаги внутри — последовательно.
3. **Запись шага:**
   ```
   {index, customer, prodReply,
    reply: {text, status, options, seconds},
    trace: {chains, rag, systems},
    rules: [...], status, second, error}
   ```
4. **Критерии шага** — объединение:
   - **тон:** активные правила `tone.py`;
   - **промпты:** правила темы из проверки «Точность»;
   - **RAG:** фиксированный набор в `backend/lab/rag.py`, `observation: 'rag'`:
     1. запрос в RAG верно передаёт вопрос клиента с учётом истории;
     2. найденные фрагменты относятся к вопросу;
     3. ответ опирается на найденное и не додумывает;
     4. ответ отвечает на вопрос клиента;
     5. если RAG не нашёл ответа, агент не отвечает по существу (202-7 или перевод на оператора).
5. **Судья.** Новый промпт `JUDGE_REPLAY`, один вызов на шаг. Payload:
   `{expectations, history, customerMessage, agentReply, trace}`. Оценивается только новый ответ агента; история из
   лога — контекст; ответ прода не оценивается. Второй судья (`judge.second_opinion`) спрашивается одновременно
   с основным, как в `judge.evaluate`.
   Судье уходит сжатый трейс: имена и выходы цепочек без промптов, RAG целиком, вызовы систем.
6. **Проверка цитат** (`judge.checked`): для `rag` цитата должна дословно быть в тексте RAG-трейса (запрос, фрагменты,
   ответ). Если на шаге не было вызова RAG (бизнес-пайплайн без IDP), RAG-критерии — `NOT_APPLICABLE`.
7. **Итог.** Статус шага — `judge.verdict_of`. Диалог — FAIL, если провален хотя бы один шаг; иначе PASS, если пройден
   хотя бы один шаг; UNMEASURED, если ни один шаг не измерен. Метрика — PASS / (PASS + FAIL) по шагам, отдельно
   по семействам «тон», «промпты», «RAG»: в семействе шаг — FAIL, если провален хотя бы один его критерий этого
   семейства, PASS — если пройден хотя бы один и ни один не провален; шаг без PASS и FAIL в семействе не считается.
8. **Хранение.** Документ `replay.json` в БД агента (последний повтор), через `store`. Рядом — крошечный
   `replay-summary.json` с `{id, finishedAt}`: его читает `/api/state` (опрос раз в 1,5 с), а весь `replay.json` —
   только `GET /api/replay`.

### 2.5 Интерфейс

Раздел «Повтор разговоров» (`/replay`) рядом с «Тон», «Точность», «Симуляции»; переиспользуем существующие компоненты.

- **Запуск:** число диалогов из выгрузки и подключение; работает только с локальным агентом (`local-code`, `local-http`;
  в `/api/state` у них `local: true`), иначе — объяснение. Прогресс по шагам.
- **Итог:** точность по трём семействам, список диалогов со статусами.
- **Диалог:** лента шагов. В шаге — реплика клиента; ответ прода и новый ответ рядом; раскрываемый трейс (запрос в RAG
  → статьи и фрагменты с оценками → ответ RAG → цепочки → вызовы систем); вердикты по критериям с пояснением, цитатой
  и вторым судьёй.

## 3. Ошибки

| Ситуация | Поведение |
|---|---|
| Агент недоступен / HTTP 5xx на шаге | шаг `UNMEASURED` с текстом ошибки, повтор идёт дальше |
| `GET /local/agent-lab/trace` → 404, ни один шаг повтора ещё не получил трейс | повтор останавливается: «Обновите aigw-local: агент не отдаёт трейс» |
| Трейса нет у шага, когда другой шаг повтора уже получил свой | шаг `UNMEASURED` («Агент не отдал трейс этого шага.»), без судьи; повтор идёт дальше |
| Судья не ответил | шаг `UNMEASURED` с текстом ошибки, критерии — `UNKNOWN` (RAG без вызова — `NOT_APPLICABLE`), как в `discover` |
| Выгрузка без колонок Voice360 | существующие сообщения `logs.py` |
| Подключение не локальное (`prod`) | повтор не запускается, объяснение в интерфейсе |

## 4. Тесты

Fakes вместо `mock.patch`.

- **aigw-local:** один шаг на заглушках (`local/mocks`) — в трейсе есть вызов `idp_input_chain`, RAG-запрос
  с фрагментами; трейс фоновой задачи IDP попадает в тот же `traceId`.
- **Lab `tests/test_replay.py`:** разбиение диалога на шаги (префикс истории, `phrases`, `trigger_phrase_id`); повтор
  с `FakeAgent` (заготовленные ответы и трейсы) и fake-судьёй — шаги сохраняются, статус диалога агрегируется.
- **Lab `tests/test_evaluation.py`:** `checked` для `observation='rag'` — цитата ищется в RAG-трейсе; без RAG-трейса —
  `NOT_APPLICABLE`.
- **Вручную:** 3 диалога из выгрузки на заглушках на этом ноутбуке.

## 5. Не входит в v1

- Общий контракт «агента под тестом» и адаптеры других агентов.
- Оценка ответа прода теми же критериями («было/стало» по шагам).
- Трейсы в подключении `prod`.
- История повторов (храним последний).
