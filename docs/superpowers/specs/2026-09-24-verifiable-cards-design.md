# Верифицируемый эталон в карточке сценария

Дата: 2026-09-24 · Ветка: `feature/verifiable-cards` · Статус: дизайн согласован, ждёт ревью спеки

## Проблема

Карточка сценария, собранная из логов, часто не содержит проверяемого результата. У RAG-агента правильное
поведение — сходить в конкретную статью базы знаний или сказать конкретный факт, но сейчас это проверить нельзя:

- `tool_called` смотрит только имя инструмента, аргументы не проверяются;
- найденные RAG-фрагменты (`retrievals`) видит только судья, детерминированные проверки их не читают;
- нет связи «факт в ответе ↔ статья, из которой он взят»;
- нет места в карточке, где лежит эталон, и нет правил, откуда он берётся.

Контракт адаптера, который отдаёт внутренности агента (`events`, `retrievals`, флаги полноты), уже есть в коде
(`src/targets.ts`, `externalReplySchema`), но не описан для автора адаптера и без него каждый адаптер
придумывается заново.

## Цель

В карточку можно занести эталон — идентификатор источника и/или ожидаемый текст, — и Lab проверяет его
детерминированно там, где это наблюдаемо, и судьёй там, где нужен смысл. То, что не наблюдалось, остаётся `unknown`.

Вне рамок: калибровка судьи, ProductView (самостоятельное тестирование по запросу сценария) — отдельные темы.

## 1. Эталон в карточке

В сценарий добавляется необязательное поле `references` (до 8 элементов):

```ts
reference = {
  id: identifier,
  origin: 'assessor' | 'log' | 'proposed' | 'owner',
  source?: { doc: string; chunk?: string },   // эталон-идентификатор: стабильный id статьи (и чанка)
  text?: string,                              // эталон-текст: факт или фраза, которую агент должен передать
  confirmed: boolean,                         // proposed → false до подтверждения человеком
}
// Инвариант: задан хотя бы один из source / text.
```

Происхождение:

| `origin` | Откуда | Подтверждён при создании |
|---|---|---|
| `assessor` | разметка асессора в импорте | да |
| `log` | tool-вызовы / retrieval из лога успешного диалога | да |
| `proposed` | предложен LLM по базе знаний | нет |
| `owner` | вписан пользователем в `agent_lab_edit` | да |

Проверки выводятся из эталона автоматически, руками не пишутся — знание об ожидаемом результате живёт в одном месте:

| Эталон содержит | Детерминированная проверка | Метрика судьи |
|---|---|---|
| `source` | `source_retrieved` | — |
| `text` | `answer_reference_tokens` (только если в тексте есть значимые токены) | `reference_match` |
| оба | обе выше + при приёмке: `text` должен встречаться в чанке `source`, иначе эталон битый | `reference_match` |

Выведенные проверки получают `stage`: `source_retrieved` → «поиск», `answer_reference_tokens` и
`reference_match` → «ответ».

Совместимость: поле необязательное, старые карточки и записи открываются и переоцениваются без миграции.

## 2. Как эталон попадает в карточку

```
диалоги ──► импорт ──► сборка карточек ──► приёмка человеком ──► прогон
             │              │                    │
      разметка асессора   LLM предлагает     owner добавляет / правит /
       → assessor         эталон по базе     удаляет эталон (agent_lab_edit)
      лог с tool/RAG      знаний, если
       → log              других нет → proposed
```

1. **Импорт.** Формат импорта диалогов получает необязательную разметку на уровне диалога
   `expected: [{ doc?, chunk?, text? }]` → `origin: 'assessor'`. Если в логе есть retrieval или tool-вызовы
   поиска, id статьи берётся только из успешных диалогов (ошибочное действие агента — не эталон) → `origin: 'log'`.
2. **Предложение LLM.** Если эталона нет, но загружена база знаний (`sourceKind: 'knowledge'`), роль сборки
   ищет статью и цитату, отвечающие на запрос карточки. Цитата обязана дословно встречаться в материале — то же
   правило grounding, что для требований; невалидная цитата отбрасывается, а не «чинится».
3. **Приёмка.** Эталоны видны с меткой происхождения. `proposed` с `confirmed: false` блокирует приёмку
   карточки, пока человек его не подтвердит или не отклонит. Отклонённый удаляется.
4. **Правка.** `agent_lab_edit` получает операции `add_reference` / `update_reference` / `remove_reference`.
   После правки выведенные проверки пересобираются.

Если нет ни разметки, ни базы знаний, ни ручного ввода — эталона нет, карточка проверяется как сейчас.

## 3. Контракт наблюдаемости адаптера

Один источник правды: всё найденное в базе знаний адаптер кладёт в `retrievals`, даже если агент получил это
через tool-вызов. `source_retrieved` смотрит только в `retrievals`.

Уровни наблюдаемости:

| Уровень | Адаптер отдаёт | Становится измеримым |
|---|---|---|
| 0 | `reply` | `answer_*`, `answer_reference_tokens`, `reference_match` |
| 1 | + `events`, `eventsComplete`, `eventScope` | `tool_called`, `tool_not_called`, `tool_count`, `fresh_read_before_update` |
| 2 | + `retrievals` (`source` — стабильный id статьи, `chunkId?`), `retrievalsComplete` | `source_retrieved`, RAG-рубрики |
| 3 | + `records`, `resetConfirmed` | `state_equals` |

Изменение контракта — только добавление: `retrievals[].chunkId?: string`. В документе закрепляется, что
`source` — стабильный id из базы знаний, не URL и не заголовок.

Поставка:

1. `docs/adapter-contract.md` — протокол (command JSON-lines и HTTP), поля, семантика флагов полноты, лесенка
   уровней, типичные ошибки («слова агента — не событие», «`*Complete: true` только если полнота доказана кодом»).
2. `examples/ADAPTER-BUILDER-PROMPT.md` — готовый промпт для coding-агента, который пишет адаптер к новому
   агенту: образец — `examples/agent-oc-adapter.py`; порядок: точка вызова агента → где агент пишет tool-вызовы,
   RAG-чанки, логи → отображение в поля контракта → флаги полноты; чек-лист максимальной детализации (каждый
   tool с args/result, каждый чанк с `source`/`chunkId`/`content`/`score`, состояние, версия, usage);
   финальная проверка — ожидаемый уровень в `agent_lab_connection`.
3. Референсный адаптер: сначала TS (`examples/adapter-reference.mjs`), затем Python-хелпер
   `examples/agent_lab_adapter.py` (dataclasses `Reply`, `Retrieval`, `ToolEvent` + цикл протокола; автор пишет
   одну функцию `ask(session, message) -> Reply`).
4. `agent_lab_connection` после пробного ответа показывает уровень по фактически полученным полям, а не по
   заявлению адаптера: «Уровень 2: ответ ✓ · инструменты ✓ · статьи ✓ · состояние ✗ — проверки состояния
   будут `unknown`».
5. `examples/agent-oc-adapter.py` поднимается до уровня 2: Agent OS отдаёт логи, действия и найденные чанки —
   адаптер пробрасывает всё наблюдаемое с максимальной детализацией.

## 4. Оценка и отчёт

- `source_retrieved`: pass — `doc` (и `chunk`, если задан) есть в `retrievals` любого хода; fail — статьи нет и
  адаптер подтвердил `retrievalsComplete: true` во всех ходах; иначе `unknown`.
- `answer_reference_tokens`: все значимые токены эталона (`valueTokens()`: суммы, сроки, коды, даты) есть в
  последнем ответе агента, с нормализацией как у `answer_contains`.
- `reference_match`: судья получает эталон-текст и, если есть в trial, чанк `source`; вердикт «ответ передаёт тот
  же факт, что эталон, и не противоречит ему» — pass / fail / unknown по общей механике метрик, включая повторы.
  Добавляется только если у эталона есть `text`.
- Вердикт карточки — по общим правилам: особой логики для эталонов нет.

Диагноз по `stage`:

| Поиск | Ответ | Диагноз |
|---|---|---|
| fail | — | не найдена нужная статья |
| pass | fail | статья найдена, агент её не использовал |
| fail/unknown | pass | ответ не подтверждён источником |

Переоценка: эталоны можно добавить к записанным прогонам через `reassess`; trial не меняется, проверки считаются
по сохранённым `retrievals` и ответам.

## 5. Проверка

Unit-тесты (fake-адаптеры, без моков):

- `source_retrieved`: pass / fail / `unknown` без `retrievalsComplete` / совпадение по чанку;
- `answer_reference_tokens`: нормализация; эталон без значимых токенов → проверки нет;
- вывод проверок из `references` и пересборка после `agent_lab_edit`;
- `proposed` без подтверждения блокирует приёмку;
- битый эталон (`text` не встречается в чанке `source`) отклоняется при приёмке;
- импорт разметки асессора; невалидная цитата LLM отбрасывается;
- старая запись без `references` открывается и переоценивается без изменений.

Живая проверка на Agent OS (`agent_oc`):

1. Адаптер на уровне 2; `agent_lab_connection` показывает «статьи ✓».
2. 3–5 карточек с эталонами: минимум по одному `assessor`/`owner`, `log`, `proposed`.
3. Прогон → в отчёте видны все три диагноза из таблицы выше.
4. Намеренно неверный `doc` в одной карточке → честный fail, не pass.
5. `reassess` старого прогона Agent OS с новыми эталонами → проверки посчитаны по сохранённым данным.

## Открытые вопросы

- Где в результате `harness_core.run_turn` у Agent OS лежат id найденных чанков — выясняется первым шагом
  реализации; если их нет в результате, источник берётся из логов агента.
- Есть ли RAG с id статей у агента эквайринга — неизвестно; его адаптер пишется по `ADAPTER-BUILDER-PROMPT.md`
  отдельно.
