# База знаний в «Повторе разговоров»: разбивка по критериям

Дата: 7 октября 2026. Продолжение `2026-10-05-voice360-replay-design.md` (оценка RAG по шагам повтора) и
`2026-10-06-acquiring-replay-service-design.md` (сервис повтора, критерий `replay:match`).

## 1. Что не так сейчас

- **Одна цифра на группу.** Результат повтора показывает по RAG одну карточку «База знаний»: долю шагов, где все пять
  критериев RAG прошли. Где ломается RAG — в запросе, в поиске, в опоре на найденное, — по ней не понять. На доске
  «LLM judge (RAG)» выход оценки — вектор «КР1 – 1, КР2 – 1, КР3 – 0 … → 0/1 + пояснение» по каждому критерию, а в
  интерфейс он не выведен.
- **От цифры не дойти до примеров.** Ошибки одного критерия разбросаны по разговорам. Чтобы их найти, приходится
  раскрывать разговоры по одному.
- **Не видно, на что опирается цифра.** Сколько шагов вообще обращались к базе знаний и на скольких из них повтор
  совпал с продом, на странице нет. А выводы по трейсу повтора относятся к проду только там, где ответы совпали.

## 2. Решение

RAG оценивается отдельно от тона и промптов: у него свои метрики. На странице повтора вместо карточки «База знаний»
стоит блок «База знаний» во всю ширину. Карточки «Tone of voice» и «Точность» остаются как есть.

```
База знаний — 84%, без найденных ошибок 135 из 161 шага
С обращением к базе знаний — 161 шаг из 640, из них с продом совпали 120 · ▸ 31 отличаются

Запрос в базу знаний            148 из 161 (92%)   ▸ 13 с ошибкой
Найдено нужное                  114 из 161 (71%)   ▸ 47 с ошибкой
Ответ опирается на найденное    135 из 161 (84%)   ▸ 26 с ошибкой   · не удалось проверить: 3
Ответ на вопрос                 142 из 161 (88%)   ▸ 19 с ошибкой
Нет ответа в базе знаний         20 из 21  (95%)   ▸ 1 с ошибкой
```

### 2.1 Как считаем

- **Шаг с обращением к базе знаний** — шаг, в трейсе которого есть хотя бы один вызов `rag`, включая ответ из кэша
  IDP (`rag.called`). Остальные шаги в блок не входят.
- **Общая цифра** — существующая `metric.rag` (спека от 5 октября, §2.4 п. 7): «без найденных ошибок
  `pass` из `pass + fail` шагов», где шаг пройден, если ни один критерий RAG не провален и хотя бы один пройден. Не
  меняется. Её знаменатель может быть меньше числа шагов с обращением к базе: шаги, где модель не ответила, в него не
  входят.
- **Критерий:** «N из M», где N — шаги с PASS, M — шаги с PASS или FAIL по этому критерию. «Не относится»
  (`NOT_APPLICABLE`) в счёт не входит. «Не удалось проверить» (`UNKNOWN`) в счёт не входит и показывается отдельным
  числом. Процент — только рядом со счётом. Если M = 0, процента нет.
- **Совпадение с продом** — по критерию `replay:match` на шагах с обращением к базе: «совпали» — PASS, «отличаются» —
  FAIL, «не удалось сравнить» — `UNKNOWN`, он показывается в строке отдельным числом. Критерии RAG не пересчитываются
  по совпавшим шагам: строка показывает, на какую долю повтора можно опираться, и открывает шаги, где повтор
  отличается от прода.
- **Считаются оценки основной модели**, как в `metric`. Мнение второй модели видно в самом шаге.

### 2.2 Переход к примерам

«▸ N с ошибкой» у критерия и «▸ M отличаются» у строки совпадения раскрывают под блоком плоский список шагов. Строка
списка: реплика клиента, объяснение и цитата модели по этому критерию (у совпадения — по `replay:match`). По клику
строка разворачивается в существующий вид шага (`StepView`): ответ прода, ответ повтора, трейс, все оценки. Открыт
один список за раз. Шаги идут в порядке разговоров и шагов; постраничности нет.

### 2.3 Бэкенд

- `backend/lab/rag.py` — `summary(dialogues: list[dict]) -> dict`. Знание о критериях RAG уже здесь; правило подсчёта
  ложится рядом. Возвращает:

  ```json
  {
    "steps": 640,
    "called": 161,
    "match": {"same": 120, "different": 31, "unknown": 10,
              "differentSteps": [{"dialogueId": "d-1", "step": 2}]},
    "criteria": [
      {"id": "rag:relevant", "name": "Найдено нужное", "pass": 114, "fail": 47, "unknown": 0,
       "failed": [{"dialogueId": "d-1", "step": 0}]}
    ]
  }
  ```

  `criteria` — в порядке `rag.CRITERIA`, все пять всегда. Ссылки на шаги отдаёт бэкенд, чтобы решение «какой шаг
  провалил критерий» жило в одном месте.
- `GET /api/replay` (`api.py`) возвращает сохранённый результат и поле `knowledgeBase` = `rag.summary(dialogues)`.
  Считается при каждом чтении, в `replay.json` не пишется: разбивка есть и у уже сохранённого повтора. Модели не
  вызываются.

### 2.4 Фронтенд

- `frontend/src/lab/types.ts` — тип `KnowledgeBaseSummary`, поле `knowledgeBase` в `ReplayResult`.
- `frontend/src/sections/replay/KnowledgeBase.tsx` — блок: общая цифра, строка совпадения, пять строк критериев,
  раскрывающийся список шагов. Шаг находится по ссылке `{dialogueId, step}` в уже загруженном результате.
- `frontend/src/sections/replay/ReplayPage.tsx` — вместо карточки «База знаний» блок; карточки тона и точности как
  были.

## 3. Пограничные случаи

| Ситуация | Что показываем |
|---|---|
| Ни на одном шаге агент не обращался к базе знаний | Заголовок «База знаний» без числа и текст «На шагах этого повтора агент не обращался к базе знаний.» вместо строк |
| Модель не ответила: у критерия 0 PASS и 0 FAIL | «не удалось проверить: K» без «N из M» и процента; общая цифра — «Не удалось проверить» |
| Критерий не относился ни к одному шагу (например, «Нет ответа в базе знаний», когда база всегда что-то находила) | «таких шагов не было» без чисел |
| Модель не ответила о совпадении (только «не удалось сравнить») | «Сравнить с продом не удалось: K.» без числа совпавших |
| Совпадение не проверялось (повтор до `replay:match`) | «Совпадение с продом не проверялось.» без чисел |
| Сотни ошибок у критерия | Список целиком, в порядке разговоров |

Тексты проходят `bin/copy_check.py` по `docs/WRITING.md`.

## 4. Тесты

**`backend/tests/test_rag.py`** — fake-результаты повтора, без `mock.patch`:
- шаг с ответом из кэша считается обращением к базе, шаг без вызова — нет;
- у критерия PASS, FAIL и «не удалось проверить» считаются отдельно; «не относится» в счёт не входит;
- `failed` ссылается ровно на шаги с FAIL по этому критерию;
- совпадение: `same`, `different`, `unknown` и `differentSteps`;
- пустой повтор и повтор без обращений к базе: `called` = 0, у критериев нули.

**`backend/tests/test_api.py`** — `GET /api/replay` отдаёт `knowledgeBase`.

**Фронтенд** — lint, prettier, сборка; проверка в браузере на подложенном результате: цифры, раскрытие списка,
разворот шага, «не удалось проверить».

## 5. Не делаем

- Разбивку по критериям для тона и промптов: у них свои проверки на тех же разговорах.
- Пересчёт критериев RAG только по шагам, совпавшим с продом.
- Повтор всей выгрузки: лимит остаётся 200 разговоров.
- Историю повторов и сравнение «до → после»: следующей задачей.
- Постраничность списка шагов.

## 6. Условие, без которого цифр не будет

Модель-судья должна отвечать. Сейчас на ноутбуке у Pi нет ключа OpenRouter, и все критерии получают «не удалось
проверить». Для настоящих цифр по RAG нужен ещё настоящий IDP (рабочий компьютер или стенд): на ноутбуке заглушка IDP
отдаёт найденные фрагменты вместо ответа. Это не часть этой задачи, но без этого блок покажет только «не удалось
проверить».
