# Технический справочник Agent Lab

Основной путь описан в [README](../README.md). Этот документ фиксирует входные форматы, подключение настоящего агента и границы доказательств.

## Материалы владельца и логи

`task.json` задаёт задачу и документы, из которых можно извлекать ожидания:

```json
{
  "task": "Проверить ответы агента поддержки по правилам владельца.",
  "mode": "live",
  "workflow": "evaluate",
  "materials": [
    { "name": "policy.md", "content": "Заявка создана только после появления номера." },
    { "name": "agent-prompt.md", "kind": "prompt", "content": "Не подтверждай действие без наблюдаемого результата." }
  ]
}
```

Ожидания берутся из `materials`, а не из поведения текущего агента и не из старого результата. Каждое требование хранит цитату источника. Противоречие или пробел остаётся вопросом владельцу.

Диалоги принимаются массивом JSON или по одному объекту на строку JSONL:

```json
{
  "id": "dialogue_17",
  "messages": [
    { "role": "user", "content": "Заявка уже создана?" },
    { "role": "assistant", "content": "Да, всё готово." }
  ]
}
```

`goal` и `outcome` необязательны. Старый `outcome` не считается правильной меткой. Для discovery действуют пределы: 300 диалогов, 60 сообщений на диалог, 8 000 символов на сообщение, 2 000 000 символов содержимого и 4 МБ на файл. Lab не подключается к системам логирования и не деидентифицирует данные за владельца.

## Discovery

Discovery работает в два масштаба:

1. Из материалов владельца извлекаются требования.
2. Диалоги читаются ограниченными порциями; сохраняются короткие наблюдения и точные ссылки на реплики.
3. Из повторяющегося кандидата выбираются до трёх характерных и до двух контрольных примеров.
4. Полные выбранные разговоры проверяются по исходному требованию.
5. Только подтверждённое повторяющееся поведение становится одной гипотезой и вопросом «Проверим?».

До первого модельного вызова показываются число порций и верхние границы вызовов и времени. Discovery не выдаёт accuracy всей выборки. Сохранённый `fromRunId`, текст гипотезы и ссылки на события образуют точную передачу в построение одного теста; свободная переформулировка не должна менять найденную проверку.

## Подключение настоящего агента

`target` поддерживает `http`, `module` и `command`. Каждый диалог получает новую `TargetSession`. Для локального процесса запрос и ответ передаются JSON-строками; HTTP получает тот же объект POST-запросом:

```json
{
  "sessionId": "run_case_repeat",
  "scenarioId": "missing_application_number",
  "initialState": { "records": {}, "writableFields": [], "transientFailures": 0 },
  "messages": [{ "role": "user", "content": "Заявка уже создана?" }],
  "message": "Заявка уже создана?"
}
```

Минимальный ответ — JSON-строка или объект:

```json
{
  "reply": "Номер заявки пока не появился, поэтому создание не подтверждено.",
  "events": [],
  "records": {},
  "resetConfirmed": true,
  "eventsComplete": true,
  "version": "acquiring-agent-2026-09-16"
}
```

- `reply` — ответ пользователю.
- `events` — наблюдаемые вызовы инструментов `{tool,args,result}`.
- `records` — итоговое состояние, сообщённое адаптером. Для внешнего агента это reported state, а не независимо наблюдённое состояние.
- `resetConfirmed` подтверждает применение исходного состояния именно к этому диалогу.
- `eventsComplete` подтверждает полноту событий в заявленной области.
- `version` идентифицирует реально запущенную версию агента.
- `measurementError` завершает попытку как ошибку измерения, даже если вместе с ним пришёл текст ответа.

Секреты HTTP передаются только через переменные окружения, названные в `headersEnv`, и не сохраняются. Ответ ограничен 200 000 байтами. Таймаут или сломанный контракт дают ошибку измерения, а не провал агента.

## Один тест

После согласия с гипотезой Lab строит ровно один тест. До принятия показываются:

- цель и начальная реплика пользователя;
- известные и недоступные пользователю факты;
- ответы на допустимые уточнения и лимит продолжений;
- исходное состояние;
- каждая точная проверка;
- каждая модельная рубрика с условиями `pass`, `fail` и стадией;
- цитата требования и происхождение теста.

Изменение теста меняет его hash. Принять можно только показанную версию hash; принятие не открывает `TargetSession`. Запуск требует отдельного подтверждения и использует один режим пользователя: `reactive`, `scripted` или `static`.

## Наблюдаемый результат

Точные проверки могут сравнивать финальное состояние, факт/число вызовов инструмента и буквальный текст ответа. Они не делают вывод о ненаблюдаемом действии. Если адаптер не подтвердил состояние или полноту событий, соответствующий результат — `unknown`.

Модельные рубрики оценивают смысл ответа и достижение цели по полному диалогу. Судья не получает человеческий вердикт как подсказку и обязан ссылаться на реальные события. Два независимых вызова должны совпасть; иначе результат `unknown`. Это не измерение repeatability или reliability судьи.

`simulatorChecks` — кодовые подозрения к репликам симулированного пользователя: утечка скрытого значения, выдуманный факт или цикл. Они показываются в полном диалоге рядом с доказательством и не превращаются в оценку агента. Неразрешённое подозрение делает попытку непригодной для сравнения.

## Сохранение и сравнение

`save-suite` создаёт новый versionable JSON и никогда не перезаписывает существующий файл. Сохраняются требования, тест, подключение и настройки; результаты и старое разрешение запуска не переносятся. `evaluate` запускает то же определение заново.

`diff` сравнивает только совпадающие карточки и попытки при одинаковых требованиях, настройках, режиме пользователя и протоколе судьи:

- `fixed`: раньше был решающий fail, теперь решающий pass;
- `regressed`: раньше был решающий pass, теперь решающий fail;
- без изменения: решающий результат совпал;
- `incomparable`: изменились условия либо нет достаточной пары.

Пропавшие, невалидные и `unknown`-попытки не превращаются в улучшение. Модельные оценки остаются предварительными; спорный случай можно отдельно отдать человеку, не размечая весь прогон.
