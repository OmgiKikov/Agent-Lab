# Agent Lab: аудит архитектуры harness — 22 сентября 2026

Да, в проекте есть обходные решения, которые стоит заменить предметными инструментами и ясными контрактами. Основная проблема — разговорный адаптер одновременно интерпретирует намерение пользователя, устанавливает авторство данных, выбирает черновик, собирает изменения, запускает перепроверку и управляет фоновой работой. Генератору тоже поручена часть структуры, которую должен задавать код. Поэтому очередная ошибка превращается в дополнительный regex, поле, инструкцию или цикл исправления.

При этом ядро уже содержит полезные примитивы: операции библиотеки, проверку ожидаемой версии, единственного писателя, восстановление публикации, неизменяемые принятые наборы и ограниченный контроллер пользователя. Их можно использовать для упрощения. Оснований переписывать весь проект на другой агентный фреймворк по этому аудиту нет.

Аудит выполнен по текущим рабочим исходникам и сохранённым результатам предыдущего живого прохождения Pi. Во время самого архитектурного аудита исходники не менялись, сборки, тесты и новые прогоны через провайдеров не запускались. Статические выводы ниже отделены от наблюдавшихся ошибок. Это включает критический разбор исправлений, сделанных в предыдущем цикле этой же задачи.

## 1. Прямые инструменты нужны, но их предметная логика должна быть общей

**Наблюдалось в живом прохождении:** просьба изменить бизнес-цель и условия группы привела к выделению группы, повторным правкам пользовательской цели карточки и предложению ненужного объединения. После появления прямого `edit_group` внешний Pi выбрал нужную операцию; одна исправленная карточка прошла новую проверку. Это локальный успешный пример, а не измеренное улучшение на независимой выборке.

Сейчас `agent_lab_scenarios` содержит перечень операций, множество независимо необязательных аргументов и `patch`/`request` с `Type.Any`: [agent-lab.ts:1044](../extensions/agent-lab.ts#L1044), [agent-lab.ts:1078](../extensions/agent-lab.ts#L1078). Допустимые сочетания снова выясняются в диспетчере. Предметная discriminated union уже существует ниже: [scenario-contracts.ts:140](../src/scenario-contracts.ts#L140).

Кроме того, разговорный путь автоматически перепроверяет изменения, board предлагает нажать отдельную клавишу, а CLI просто применяет patch. Значения по умолчанию для варианта, выбор редактируемого черновика и выделение группы реализуются отдельно: [agent-lab.ts:1189](../extensions/agent-lab.ts#L1189), [agent-lab.ts:1251](../extensions/agent-lab.ts#L1251), [agent-lab.ts:2293](../extensions/agent-lab.ts#L2293), [agent-lab.ts:2366](../extensions/agent-lab.ts#L2366), [cli.ts:186](../src/cli.ts#L186).

**Замена:** общий модуль предметных команд поверх существующего `ExperimentLab`, начиная с редактирования карточки и группы. Он разрешает ссылку на показанную ревизию, выбирает черновик, вычисляет затронутые карточки, строит diff, определяет необходимость подтверждения и возвращает план перепроверки. Политика перепроверки задаётся явно: автоматическая или отложенная. Pi, board и CLI собирают входные данные и показывают результат.

Пример небольшого интерфейса, а не требование нового фреймворка:

```ts
prepare(command, viewRef) -> { previewRef, scope, diff, requiredDecision }
apply(previewRef, hostAuthority) -> { revision, affectedIds, assessmentPlan }
```

У модели остаются компактные команды `edit_card`, `edit_group`, `create_variant`, `resolve_question`, `accept`; у каждой собственная схема. Общий raw patch можно оставить в совместимом техническом адаптере, убрав его из обычного выбора модели. Расширенные схемы генератора и диагностики не обязательно держать активными на каждом шаге: установленный Pi уже предоставляет `getActiveTools`/`setActiveTools`. Статус и остановка должны оставаться доступны независимо от режима.

**Что удаляется после перехода:** параллельные пути «удобные аргументы или patch», повторная проверка вида операции в адаптерах, дублирование default-значений и запуска перепроверки. Простой перенос большого `switch` в новый файл упрощением не считается. `edit_group` — правильная операция; её нынешняя реализация внутри большого диспетчера — промежуточное решение.

## 2. Авторство и право принять решение нельзя выводить из похожих слов

В [conversation.ts:25](../extensions/conversation.ts#L25) слова сокращаются до основ; [conversation.ts:67](../extensions/conversation.ts#L67) задаёт порог совпадения 0.6. Авторизация ищет похожий текст среди всех прежних сообщений владельца и известных текстов карточки: [conversation.ts:168](../extensions/conversation.ts#L168). Короткое «не» отбрасывается при построении основ. Поэтому противоположное по смыслу утверждение может сохранить полное лексическое совпадение. Это вывод из кода; отдельный новый живой эксперимент с таким отрицанием в этом аудите не проводился.

Здесь смешаны два разных утверждения: «владелец попросил модель отредактировать текст» и «владелец лично сообщил этот факт». Для обычной обратимой правки формулировки достаточно первого; происхождение нового факта оно не доказывает. Новые исключения для модальных просьб и служебных `factId` исправили реальные отказы, но продолжают расширять собственный интерпретатор языка.

Есть и расхождение адаптеров: Pi запрещает raw `resolve_finding(s)` и запрашивает native-решение, тогда как CLI `scenarios --operation edit` принимает тот же library patch напрямую: [agent-lab.ts:1417](../extensions/agent-lab.ts#L1417), [agent-lab.ts:1467](../extensions/agent-lab.ts#L1467), [cli.ts:185](../src/cli.ts#L185). Это не доказательство удалённой уязвимости: прямой человеческий CLI может быть намеренно доверенным. Но различие доверия не представлено в общем контракте, а модель с доступом к shell может использовать другой маршрут. Добавление `--yes` само по себе этого не исправляет.

**Замена:** отдельно хранить автора предложения, ссылку на пользовательскую просьбу, происхождение факта и подтверждение конкретного diff. Доверенный хост передаёт решение владельца общему модулю команд; аргумент модели `approved: true` таким решением не является. Если нужна настоящая защита от модели с произвольной записью файлов, граница должна обеспечиваться правами хоста, а не только объектом внутри процесса.

**Что удаляется:** лексическое совпадение как сертификат авторства, списки «полей с настоящими словами клиента», отдельные запреты patch в каждом адаптере. Языковые эвристики могут помогать интерфейсу, но не удостоверять источник факта. Защиту явно запрещённых пользователем объектов нельзя просто удалить: она остаётся до появления эквивалентного механизма связывания команды с разрешённой областью. Исторические записи авторства не переписываются задним числом.

## 3. Модельное предложение и основание его проверки должны быть разными объектами

Схема предложения содержит одновременно модельные утверждения, редактируемые ссылки и поля `sourceCoverageRequired`/`sourceCoverageBasis`, которыми должен владеть harness: [scenario-contracts.ts:64](../src/scenario-contracts.ts#L64). Из-за этого транспорт исключает поля, подготовка удаляет и заново проставляет их, а правки и производные варианты специально сохраняют: [pi.ts:504](../src/pi.ts#L504), [scenario-preparation.ts:17](../src/scenario-preparation.ts#L17), [scenario-library.ts:486](../src/scenario-library.ts#L486), [scenario-library.ts:607](../src/scenario-library.ts#L607).

Недавние защиты необходимы: без них редактирование ссылки могло менять саму обязанность сохранить продолжение диалога. Но большое количество правил сохранения показывает, что основание лежит не в том объекте.

**Замена:** неизменяемый `GenerationEvidence` с hash импорта, исходными диалогами, обязательными событиями и manifest выбранных материалов. Модель возвращает только `ModelScenarioProposal`, который код связывает с этим основанием. Вариант ссылается на свидетельства и родительскую версию; он не копирует и не переопределяет их полномочия. Содержательное решение владельца добавляет отдельное подтверждённое основание, сохраняя исходную историю.

Особенно важно передавать manifest независимому проверяющему. Сейчас его источники выбираются по требованиям, на которые сослалась сама сгенерированная карточка: [scenario-work.ts:28](../src/scenario-work.ts#L28). Статья без извлечённого/указанного требования может исчезнуть из проверки, даже если содержит ограничение применимости или альтернативную процедуру. Это зависимость проверки от проверяемого предложения, а не доказательство, что каждый такой случай уже дал ложный `ready`.

Сначала следует сохранять текущие выбранные/прочитанные/исключённые материалы и передавать их проверке, сохраняя полные статьи, когда они помещаются. Затем можно улучшать поиск и ограниченное ранжирование. Эвристика русского заголовка в [scenario-sources.ts:37](../src/scenario-sources.ts#L37) удаляется только после проверки полноты поиска; новая векторная база для этого не обязательна. Не поместившийся источник должен оставлять явное незавершённое чтение, а не исчезать из массива.

**Что удаляется:** повторные strip/restamp и preserve-ветки, вычисление обязательности по нескольким редактируемым полям, восстановление всего набора доказательств только из цитат генератора. Миграция начинается с новых черновиков; старые принятые снимки и их hashes остаются неизменными.

## 4. Проверять нужно разные утверждения, а не многократно одно имя поля

Проверка бизнес-контекста по источникам и проверка принадлежности группе сейчас возвращают одинаковый адрес `{variantId, path: businessScenarioId}`. Код подсчитывает вклады и консервативно выбирает худший статус: [scenario-work.ts:49](../src/scenario-work.ts#L49), [scenario-work.ts:108](../src/scenario-work.ts#L108). Это правильная защита от перезаписи блокировки положительной группировкой. Удалять её ради сокращения вызовов нельзя.

Но две смысловые обязанности остаются разными. Поле интерфейса — не идентичность проверяемого утверждения. Дополнительно hash каждого задания включает общий смысловой hash библиотеки, поэтому правка одной карточки инвалидирует и незатронутые локальные задания: [scenario-library.ts:160](../src/scenario-library.ts#L160), [scenario-work.ts:75](../src/scenario-work.ts#L75). После финализации в актуальном `semanticAssessment` остаётся сводка без частичных результатов заданий; исторические снимки могут сохранять прежние результаты: [scenario-work.ts:142](../src/scenario-work.ts#L142).

**Замена:** явный план проверок `claim-grounding`, `source-coverage`, `checkpoint-applicability`, `group-membership` с предметом, конкретными зависимостями, версией проверяющего и hash фактического входа. Сохранять результаты всех заданий; готовность — производный итог наличия удовлетворительных результатов для всех обязательных проверок. Привязка к полю остаётся способом показать замечание пользователю.

**Что удаляется:** специальное объединение разнородных результатов по одному пути, различие между временными результатами и финальной сводкой как единственным доказательством, заведомо лишняя глобальная инвалидация. Экономия вызовов пока не измерена. Ошибочно узкие зависимости опаснее повторной проверки: при неизвестной зависимости результат следует инвалидировать.

## 5. Общий lifecycle устранит реальную дыру в stop/progress; resume требует отдельного контракта

Подготовка и прогон регистрируются в `boardRun`, смысловая проверка — в `activeCheck`: [agent-lab.ts:454](../extensions/agent-lab.ts#L454), [agent-lab.ts:518](../extensions/agent-lab.ts#L518). Команда остановки смотрит только на `boardRun` и при его отсутствии говорит, что работа не идёт: [agent-lab.ts:1826](../extensions/agent-lab.ts#L1826), [agent-lab.ts:1844](../extensions/agent-lab.ts#L1844). Значит, активную смысловую проверку нельзя остановить этой командой, хотя ядро умеет отменять активную работу. Аналогично расход и принадлежность операции могут показываться по сохранённому, а не текущему состоянию. Это статически установленный дефект; новой runtime-репродукции в этом аудите нет.

**Замена:** один `OperationHandle` с `operationId`, `kind`, `snapshot`, `done`, `cancel` и один сессионный координатор отображения. Существующий [ExperimentLab.launch](../src/experiment.ts#L1290) сохраняет исполнение, бюджет, отмену и запись результатов. Координатор объединяет таймеры, передачу работы в фон, уведомления и закрытие writer lease. Прерывание интерфейсного вызова и явная остановка остаются разными действиями. Успешная автоматическая перепроверка не должна порождать лишний платный ход внешней модели.

Возобновление подготовки — другой пробел. `prepareScenarioLibrary` создаёт новую библиотеку и начинает обработку заново; `assessLibrary` продолжает только смысловую оценку, не извлечение pending-диалогов: [scenario-preparation.ts:27](../src/scenario-preparation.ts#L27), [experiment.ts:785](../src/experiment.ts#L785). Поэтому ещё одна тулза с названием resume сама по себе не поможет.

Нужен небольшой сохраняемый план подготовки: неизменяемые входы, стабильные единицы работы, выбранные материалы, результаты завершённых стадий, остаток попыток и отметка активного платного вызова. Начальная и возобновлённая подготовка используют один исполнитель. Неоднозначно прерванный вызов нельзя автоматически повторять, сбрасывая стоимость; существующий `resumeDiscovery` уже показывает соответствующий подход: [experiment.ts:542](../src/experiment.ts#L542). Старые снимки без достаточных checkpoint-данных остаются явно невозобновляемыми.

## 6. Условное наблюдение клиента нуждается в собственном представлении

Сейчас модель должна сообщить наблюдение, возникшее после действия агента, через `missing` или `clarify`, потому что `answer` требует исходно известный факт: [scenario-contracts.ts:35](../src/scenario-contracts.ts#L35), [scenario-library.ts:353](../src/scenario-library.ts#L353), [prompts.ts:100](../src/prompts.ts#L100). В живом примере исходное условное наблюдение сохранялось, но несовместимое представление «изученный факт плюс ответ» блокировалось. Менять только ярлык действия — обход недостаточной модели данных.

**Замена:** части реплики вида `known-fact`, `observed-response`, `missing-answer`, связанные с исходными событиями и условием появления. Одна реплика может содержать несколько таких частей. Небольшой компилятор переводит их в существующий конечный контроллер. Изменение факта тогда работает со ссылками и зависимостями, а не ищет его текст подстрокой внутри произвольного payload: [scenario-variants.ts:114](../src/scenario-variants.ts#L114).

Существующий контроллер полезен: он ограничивает достижимые действия и выдаёт сохранённый payload, не позволяя симулятору свободно сочинять ответы: [user-controller.ts:44](../src/user-controller.ts#L44), [user-controller.ts:72](../src/user-controller.ts#L72). Его стоит сохранить. Новое представление вводится сначала для узкого случая условного наблюдения и только для новых черновиков. Текущий отказ от изменения одного факта внутри составного раскрытия безопаснее автоматического разрезания текста без такого контракта.

## 7. Повторы и исправления должны иметь одного владельца бюджета

Транспорт вручную чинит несколько видов JSON и допускает до пяти попыток: [pi.ts:290](../src/pi.ts#L290), [pi.ts:371](../src/pi.ts#L371). Подготовка независимо допускает три предложения после структурных ошибок и затем смысловое переписывание: [scenario-preparation.ts:97](../src/scenario-preparation.ts#L97), [scenario-preparation.ts:141](../src/scenario-preparation.ts#L141). До смысловой проверки получается теоретический путь до `3 × 5` транспортных попыток, затем до пяти для переписывания. Общий лимит вызовов продолжает действовать; это не утверждение, что реальные прогоны использовали все двадцать.

**Замена:** единый исполнитель структурированной задачи с идентификатором задания/попытки, общим остатком бюджета и различимыми исходами `syntax`, `schema`, `domain`, `semantic`, `transport`. Поддерживаемый провайдером структурированный ответ стоит использовать через существующий адаптер; для остальных сохраняется ограниченный JSON fallback. Включать поддержку схем вслепую для всех провайдеров нельзя. Смысловое исправление — ограниченное изменение конкретной версии, после которого проверяются затронутые утверждения.

Начать можно с общего журнала попыток, не меняя поведение. Затем удалить вложенные независимые счётчики и полную регенерацию ради одного поля. Сырые ответы, неудачные попытки, отмена и глобальный `beforeCall` остаются. Отдельно исправить смешение единиц: размер UTF-8 в байтах сейчас сравнивается с токенным окном модели в [pi.ts:165](../src/pi.ts#L165); нужны раздельные ограничения байтов и оценки токенов.

## 8. Тесты хорошо проверяют выбранную команду, но не выбор команды моделью

В [conversation.test.ts:22](../test/conversation.test.ts#L22) разговорный путь описан как «слова владельца → вызов инструмента → хранилище», но сам инструмент и аргументы выбирает тест. Семантический runtime там детерминированный: [conversation.test.ts:34](../test/conversation.test.ts#L34). Живой smoke вызывает `ExperimentLab` напрямую, выбирает готовые карточки и принимает их программно: [scenario-lab.ts:11](../test/live/scenario-lab.ts#L11), [scenario-lab.ts:24](../test/live/scenario-lab.ts#L24). Это полезные и честно ограниченные проверки, но внешний Pi они не испытывают.

Именно поэтому большой зелёный набор регрессий совместим с живым провалом просьбы изменить группу. Нужен небольшой отдельный eval реального внешнего агента: обычная просьба, действующие схемы инструментов, исходное состояние и проверка конечного diff. Набор должен включать изменение группы, перефразирование без новых фактов, запрет менять другую карточку, составное раскрытие, остановку смысловой проверки и неудачную подготовку. Оценивать следует выполненное действие, область изменений, лишние вызовы и необходимость содержательной коррекции владельцем; число зелёных unit-тестов этого не заменяет.

Для воспроизводимого тестирования расширению также нужна явная фабрика/инъекция лаборатории. Сейчас тест глобально подменяет приватный `ExperimentLab.prototype.runtime`, хотя сам конструктор уже поддерживает runtime: [conversation.test.ts:49](../test/conversation.test.ts#L49), [experiment.ts:263](../src/experiment.ts#L263). Это небольшой реальный seam между хостом и предметным модулем; отдельный универсальный контейнер зависимостей не нужен.

## Порядок работ и критерий упрощения

1. **Первый вертикальный срез: команды карточки/группы.** Общая подготовка изменения, scope/diff, политика авторства и применение через существующий writer. Подключить Pi, board и CLI; сохранить совместимый перевод старых CLI-команд. Сразу добавить проверку выбора инструмента внешним агентом. Успех: одинаковый предметный результат и правила во всех трёх интерфейсах, удалены прежние независимые ветки.
2. **Небольшой независимый срез: status/stop любой операции.** Объединить реестр и жизненный цикл, сохранив executor. Успех: длительная смысловая проверка видна и останавливается, Esc продолжает означать передачу в фон, завершение приходит один раз, writer не освобождается преждевременно.
3. **Отделить свидетельства от предложения.** Сначала новые черновики и сохранение manifest источников; затем результаты смысловых заданий с явными зависимостями. Успех: правка предложения не уменьшает обязанности по исходным событиям; проверяющий получает независимый набор свидетельств; старые принятые наборы идентичны.
4. **После этого менять представление реплик и repair/resume.** Начать с условного наблюдения и общего журнала попыток. Resume реализовывать лишь после достаточного checkpoint-контракта. Успех: то же исходное продолжение компилируется без смены смыслового ярлыка, повторы объяснимы, прерывание не обнуляет расход.

Общий критерий: новая граница должна позволять удалить старое принятие решений в нескольких местах. Если после появления `CommandService` адаптеры по-прежнему отдельно решают, что разрешено, какой черновик менять и когда перепроверять, сложность только переехала.

Сохранить: single writer/CAS и восстановление публикации ([store.ts:35](../src/store.ts#L35)); неизменяемые импорты и версии ([scenario-store.ts:30](../src/scenario-store.ts#L30)); отдельные принятие и запуск; атомарное решение по выбранной группе замечаний; невозможность снять `blocked` простым согласием; ограниченный контроллер; фактические наблюдения TargetSession и честное `unknown` при неполных данных. Они защищают реальные инварианты.

## Проверки и текущий сохранённый результат

Это проверка той реализации, а не доказательство корректности предлагаемых здесь изменений; рефакторинг ещё не выполнен. Исходный `dist` остался неизменным: сверены 84 файла. Живое прохождение сохранено на одной исправленной карточке `ready`, без принятия и запуска; второй исходный диалог не завершён после сбоя провайдера. Этот частичный результат не выдаётся за успешный генератор или завершённую продуктовую приёмку. Подробности предыдущего цикла — в [отчёте живого прохождения](owner-path-audit-2026-09-22.md).
