# Phase 2 — UI Design Contract

> Visual and interaction contract for the terminal surfaces of phase 2. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **This product has no web UI.** Every surface is text inside Pi (`@earendil-works/pi-coding-agent` 0.85.1 + `@earendil-works/pi-tui` 0.85.1) or plain CLI text. The template's web notions are translated as follows: px spacing → terminal columns and rows; font sizes → emphasis roles; hex colors → Pi `Theme` semantic tokens; components → pi-tui primitives and Pi `ctx.ui` dialogs.
>
> **Autonomous run.** The user was asleep and asked for no questions. Every choice below that upstream artifacts did not settle is recorded in `## Decisions Log` with its reason.
>
> **Scope markers.** `[BASE]` = the shared terminal design contract that phases 3–6 extend (glyphs, token map, spacing, wrap rules, key registry). `[P2]` = locked only for phase 2 (failure explanation, not-measured list, expectation sheet). Phase 4 may restyle `[P2]` layouts, but must keep the wording and row order.

**One source of text.** Every row in `[P2]` formats is produced once as plain text by pure functions (`src/explain.ts` for explanations, `src/quality.ts` `expectationSheet` for the sheet, `src/result-view.ts` for the not-measured rows). S3 maps `role` → token. This avoids guessing colors from string prefixes.

## Spacing Scale `[BASE]`

The terminal unit is one character cell. The px column is a nominal equivalent (1 column = 8 px wide, 1 row = 16 px high) for the checker only. All values are multiples of 4 px.

| Token | Terminal value | px equiv. | Usage |
|-------|----------------|-----------|-------|
| xs | 1 column | 8px | Gap after a glyph (`✗ `, `? `, `▸ `); space around `·` and `—` separators |
| sm | 2 columns | 16px | Indent of the detail rows under a title row (`  Должен был:`); the selection gutter (`▸ ` or two spaces) on the board sheet |
| md | 4 columns | 32px | Continuation line of a wrapped detail row (row indent 2 + sm 2). Not used for numbered rows (see the rule below). |
| lg | 1 blank row | 16px | Between two explanation blocks; between two sheet situations; before and after a section heading |
| xl | 2 rows (blank + heading) | 32px | Between result sections (headline block → causes → not measured → all failures) |
| frame | 2 columns each side | 16px | Board frame `│ ` … ` │` (existing, unchanged) |

Rules:
- **Hanging indent.** A wrapped continuation line starts at the row's indent + 2 columns. Example: a `said` row at indent 2 continues at column 4. On S1/S2, Pi and the terminal wrap, so no hanging indent is added there.
- **Numbered rows (derived rule).** Let `labelWidth` = `visibleWidth` of the widest label `N.` in the list (`1.` → 2, `13.` → 3). Labels are right-aligned to `labelWidth`. The first row is `gutter + label + one space + text`. Detail rows start at **`detailColumn = gutter + labelWidth + 1`**, so they line up under the text after the label.
  - S1/S2 (gutter 0): 1–9 situations → column 3; 10–20 → column 4.
  - S3 sheet (gutter 2 for `▸ `): 1–9 situations → column 5; 10–20 → column 6.
  - F2 top causes (gutter 0, at most 3 causes, label `1.`): the `Пример:` row starts at column 3 and its detail rows at column 5 (3 + sm 2).
  - Wrapped continuation of any numbered or detail row: its own start column + 2.
- **Precedence.** Where a numbered list is involved, `detailColumn` wins over the md token. md (4 columns) applies only to wrapped continuations of un-numbered detail rows (F1 inside a failure list, F3 rows).
- **No double blank rows.** No trailing blank row at the end of a section.

Exceptions (derived, not free choices): columns 3, 5 and 6 appear only as results of the `detailColumn` rule above. Every other indent is 0, 1, 2 or 4 columns.

## Typography `[BASE]`

A terminal has one font size. The four roles below are emphasis levels. Exactly 2 weights are used: regular and bold (`theme.bold`). No italic, underline or inverse in phase 2. Line height is 1 row.

| Role | Size | Weight | Line Height | Where |
|------|------|--------|-------------|-------|
| Body | 1 cell (terminal font) | regular | 1 row | Detail rows: «Должен был», «Сказал», «Должен», rule rows |
| Label | 1 cell | regular, `muted` or `dim` token | 1 row | Sources, rule rows, «и ещё K», version line, footer key hints (`dim`) |
| Heading | 1 cell, UPPERCASE Cyrillic | bold, `accent` | 1 row | Board section headings: `ИТОГ`, `ГЛАВНЫЕ ПРИЧИНЫ ПРОВАЛОВ`, `ВСЕ ПРОВАЛЫ`, `ЧТО АГЕНТ ДОЛЖЕН СДЕЛАТЬ` |
| Display | 1 cell | bold | 1 row | The headline line (phase 1, unchanged) and each explanation title row (`✗ <title>`) |

On S1/S2 headings are sentence case with a colon (`Главные причины провалов:`), because plain text has no bold.

**Quotes.** Every verbatim quote is wrapped in Russian guillemets `«…»`. It is shown **in full**: no `…`, no `shorten`, no `preview`, no `.slice`. Line breaks and runs of whitespace inside a quote are shown as one space (the check against the source uses the raw text).

## Color `[BASE]`

Colors are Pi `Theme` tokens. They adapt to light and dark themes and 256-color terminals. No hex, no raw ANSI, no chalk. **Color is never the only signal:** every status also has a glyph and a word.

| Role | Value (Pi token) | Usage |
|------|------------------|-------|
| Dominant (60%) | terminal default background + `text` fg | Body rows. No background painting in phase 2. |
| Secondary (30%) | `muted` fg, `dim` fg, `borderMuted` | Source/rule rows, «и ещё K», counts, version line, footer second line, board frame |
| Accent (10%) | `accent` fg | Only the elements listed below |
| Destructive / failure | `error` fg | The `✗` title row of a failed situation; error notices |
| Caution | `warning` fg | The `?` not-measured rows; «объяснение не подтверждено цитатой»; the «ожидание изменено владельцем» marker; the «ожидания не подтверждены» header line |
| Confirmed | `success` fg | The «Ожидания подтверждены» header line and success notice |

Accent reserved for:
1. board section headings (`ИТОГ`, `ГЛАВНЫЕ ПРИЧИНЫ ПРОВАЛОВ`, `ВСЕ ПРОВАЛЫ`, `ЧТО АГЕНТ ДОЛЖЕН СДЕЛАТЬ`);
2. the selected row marker `▸` and the first row of the selected situation on the sheet (with bold);
3. the first footer line (key hints for the current phase; existing behavior);
4. the top-cause name row (`1. <name> — N ситуаций`) — replaces today's `warning` there so that `warning` means only «could not confirm».

Not accent: rule numbers, quotes, the headline, links, every other key hint.

**Row role → token (S3):**

| Row role | Token | Bold |
|----------|-------|------|
| `title` (`✗ <title>`) | `error` | yes |
| `title` inside a top cause (`Пример: <title>`) | `text` | yes |
| `expected`, `said` | `text` | no |
| `rule`, `more`, `violated`, `cut` | `muted` | no |
| `unverified` (any row whose content is replaced by «объяснение не подтверждено цитатой») | `warning` | no |
| not-measured row (`? <title> — <reason>`) | `warning` | no |
| `sheet-head` | `accent` | yes |
| `sheet-goal` (selected) | `accent` | yes |
| `sheet-goal` (not selected) | `text` | yes |
| `sheet-expect` | `text` | no |
| `sheet-rule` | `muted` | no |
| `marker` | `warning` | no |
| `note` (counts, version) | `muted` | no |

The board `Line` type colors a whole row. Phase 2 keeps that model: no mixed colors inside one row.

## Line Formats `[P2]`

All strings below are exact. `<…>` are values. Values are escaped with `safeText` (S2, S3) or `safeLine` (S1).

### F1. Failure explanation block (JUDGE-01)

Full form, in row order. Rows 5–8 appear only when their condition holds.

```
✗ <scenario.title>
  Должен был: <X>
  Сказал (реплика #<seq>): «<Y>»
  Правило <N> · <source name>: «<rule quote>»
  Правило <N> · <source name>, строка <L>: «<rule quote>»
  и ещё <K> <правило|правила|правил>
  Нарушено правило <N> · <source name>, строка <L>: «<rule quote>»
  Оценено до реплики #<D>: дальше симулятор отклонился от диалога.
```

| Row | Condition | Content rule |
|-----|-----------|--------------|
| title | always | `✗ ` + title. Inside a top cause it is `Пример: <title>` (no glyph). |
| expected | always | Depends on what failed (CONTEXT): the situation goal failed → X = `scenario.successCriteria`. Only the rule-compliance check failed (the goal did not fail) → X is the violated rule itself (see the variant `Должен был: соблюдать правило …`). |
| said | always | Y = the judge-cited agent quote, verified as a substring of that event. |
| rule ×≤2 | card has rules | Knowledge-source rules first, then prompt-source rules, each group by ascending N. Unverified rules sort last. |
| more | card has >2 rules | `и ещё K` + plural of «правило». |
| violated | the goal failed **and** the rule-compliance check also failed and quotes exactly one registered prompt rule, verified, and that rule is not already one of the two shown | Same shape as a rule row, word «Нарушено» in front. When X is already the violated rule, this row is not printed (no duplicate). |
| cut | the situation was judged before a cut (`judgedBeforeSeq`) | `D` = the cut event number. |

**Rule row details.**
- `N` is the owner rule number from the rule register (order of materials, then position of the quote inside the material). The judge's own numbering and `requirement.id` are never shown.
- `, строка <L>` is added only when the source has more than one line (knowledge sources are one line, so they never show it).
- `<source name>` is `source.name` as stored.

**Variants (exact text).**

| Situation | Row shown |
|-----------|-----------|
| Judge cited no agent reply; the last agent reply is shown instead | `  Сказал (реплика #<seq>, судья не указал реплику): «<Y>»` |
| The cited quote is not found in the reply text | `  Сказал (реплика #<seq>): объяснение не подтверждено цитатой` (role `unverified`) |
| No agent reply exists in the record | `  Сказал: в записи нет ответа агента.` (role `unverified`) |
| Only the rule-compliance check failed; the violated rule is identified and verified | `  Должен был: соблюдать правило <N> · <source>[, строка <L>]: «<rule quote>»` |
| Only the rule-compliance check failed; the rule cannot be identified uniquely or fails its check | `  Должен был: соблюдать правила из ваших материалов — объяснение не подтверждено цитатой` (role `unverified`) |
| `successCriteria` missing (old record); first card rule text used | `  Должен был (из правила): <requirement.text>` |
| `successCriteria` missing and no rule | `  Должен был: ожидание не записано в ситуации.` (role `unverified`) |
| Rule id unknown, or its quote not found in its source | `  Правило: объяснение не подтверждено цитатой` (no number, no source; role `unverified`) |
| Card has no rules at all | `  Правило: у ситуации нет правила из ваших материалов.` (role `unverified`) |
| Card has more than 2 rules | `  и ещё 1 правило` / `  и ещё 2 правила` / `  и ещё 5 правил` (use `pluralForm`) |

Nothing is invented: a part that fails its check is replaced, not guessed. A block where every part is unverified still shows its title and all rows.

### F5. Expectation sheet (TRUST-10/11)

**S3 (board, section 2, phase `review`, workflow `evaluate`)** replaces the collapsed card detail:

```
ЧТО АГЕНТ ДОЛЖЕН СДЕЛАТЬ
13 ситуаций · номер правила — порядок в ваших материалах

▸  1. Ситуация: <scenario.user.goal>
      Должен: <scenario.successCriteria>
      Правило 7 · <source name>: «<quote>»
      Правило 31 · <source name>, строка 12: «<quote>»

   2. Ситуация: <goal>
      Должен: <expectation>
      Правило 3 · <source name>: «<quote>»
      Ожидание изменено владельцем — с прошлыми прогонами не сравнивается.

  …
Версия ожиданий: <draftHash first 12>
```
- Gutter: 2 columns (`▸ ` for the selected situation, two spaces otherwise), then the label `N.` right-aligned to `labelWidth`, one space, then the text. Detail rows start at `detailColumn = 2 + labelWidth + 1` (Spacing rule). The example above has 13 situations: `labelWidth` = 3, so detail rows start at column 6; with 1–9 situations they would start at column 5.
- **All** rules of each situation are listed, knowledge rules first, then prompt rules, one row each, quotes in full.
- The rule row shape is the same as F1 (`Правило N · источник: «цитата»`), so the owner sees the same number before and after the run.
- Unverified rule: `Правило: объяснение не подтверждено цитатой` (warning).
- Missing expectation: `Должен: ожидание не записано.` (warning).
- The marker row appears only for situations the owner changed.
- ↑/↓ (and `j`/`k`) change the selected situation and scroll so its first row is the first body row (clamped to the scroll range).
- Enter toggles today's expanded card detail (`scenarioLines(…, true)`) for the selected situation; Enter again returns to the sheet.
- The sidebar list (≥110 columns) and the one-line list shows `<title>` and adds ` · ожидание изменено` for changed situations.

## Interaction Flows `[P2]`

### Board (S3)

1. **`y` — confirm all.** The board finishes with `{ type: 'accept', record, section, selected }`. The `/agent-lab` loop calls `acceptDraft(id, draftHash(record))` for all situations and reopens the board on section 2 with the same selection and a notice:
   - done → `Ожидания подтверждены: <n> ситуаций. r — запуск.` (success);
   - already confirmed → `Ожидания уже подтверждены. r — запуск.` (info);
   - the draft changed in the meantime → `Черновик изменился, пока вы смотрели. Проверьте ожидания ещё раз.` (error).
2. **`e` — edit one.** The board finishes with `{ type: 'expect', record, section, selected, scenarioId }`. The loop opens `ctx.ui.editor('Что агент должен сделать в этой ситуации? Своими словами.', scenario.successCriteria ?? '')`.
   - Editor cancelled → board reopens, no notice.
   - Text trimmed is empty or equal to the old one → notice `Ожидание не изменено.` (info).
   - Longer than 3000 characters → notice `Ожидание длиннее 3000 знаков. Сократите и попробуйте снова.` (error). The typed text is not saved.
   - The situation is checked by exact checks, not by the judge → notice `Эту ситуацию проверяют точные проверки, а не судья. Поправьте её словами: a.` (error).
   - Saved → the text becomes the expectation verbatim, the situation gets the marker, confirmation becomes stale, notice `Ожидание изменено: «<title>». Подтвердите ожидания снова: y.` (success). Selection stays on the same situation.
3. **`r` — run.**
   - Confirmed → today's run confirmation (`runPlan`), with its validation block replaced by the compact sheet.
   - Not confirmed → `ctx.ui.confirm('Подтвердить ожидания и запустить?', <compact sheet> + <run plan tail> + 'Да — подтвердить все ожидания и начать прогон.')`. Yes → `acceptDraft` then `start({ requireAccepted: true })`. No → board reopens unchanged.
4. **Start refused** (`requireAccepted` and stale) → notice `Сначала подтвердите ожидания ситуаций: они изменились или ещё не подтверждены. y — подтвердить.` (error).

### Chat (S2), `agent_lab_accept` with more than one situation

The one-situation path stays as today (`ctx.ui.confirm(question, testPlanLines)`).

1. `ctx.ui.confirm('Подтвердить ожидания: <n> ситуаций?', <compact sheet> + '\n\nДа — подтвердить все. Нет — поправить одну ситуацию или отменить.')`.
2. Yes → `acceptDraft` → tool text `Ожидания подтверждены: <n> ситуаций. Можно запускать.`
3. No → `ctx.ui.select('Что сделать с ожиданиями?', ['Поправить ожидание одной ситуации', 'Не подтверждать сейчас'])`.
   - `Не подтверждать сейчас` or dismissed → tool text `Ожидания не подтверждены. Прогон не начнётся, пока они не подтверждены.`
   - `Поправить…` → `ctx.ui.select('Какую ситуацию поправить?', ['1. <title>', '2. <title>', …])` → `ctx.ui.editor(...)` (same title and rules as the board) → save → back to step 1 with the updated sheet. Dismissing either step also returns to step 1.
4. The model never supplies the expectation text or the confirmation. The tool takes the run id only.
5. The tool result text of `agent_lab_accept` and `agent_lab_inspect` for a draft carries the **full** F5 sheet, so the sheet stays in chat history.

`agent_lab_run` on an unconfirmed draft uses the same «Подтвердить ожидания и запустить?» dialog as board `r`.

### CLI (S1)

- `agent-lab accept --id RUN` (more than one situation) prints the full F5 sheet and then `Подтвердить все ожидания: agent-lab accept --id <RUN> --yes`.
- `agent-lab accept --id RUN --yes` prints the sheet and `Ожидания подтверждены: <n> ситуаций.`
- One situation: today's `testPlanLines` output, unchanged.
- The CLI has no edit path for expectations (Pi only). `evaluate` for saved suites is unchanged.

## Width, Wrap and Theme Rules `[BASE]`

1. Every S3 row is wrapped with `wrapTextWithAnsi(text, inner)` **before** the frame. The frame's `truncateToWidth` is a safety net and must never fire on F1/F3/F5 rows at widths 40–160. A test renders F1, F3 and F5 with long Cyrillic quotes at inner widths 36, 56, 76, 106 and 156 and asserts: no row wider than the width, no `…` produced, and the joined text equals the source text with whitespace normalised.

3. No `.slice`, `.substring`, `padStart`/`padEnd` or `.length` on user-visible text in new code. Number alignment uses `visibleWidth`.

6. Every status has glyph + word; the rows read the same with colors off (S1 is the proof).
7. Escaping: all record and model text goes through `safeText` (S2, S3) or `safeLine` (S1). `explain.ts` and `expectationSheet` return unescaped text.
