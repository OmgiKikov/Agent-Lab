## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | `Этот тест действительно проверяет нужное поведение?` |
| Positive acceptance | `Да, принять этот тест` |
| Edit path | `Нет, исправить тест` |
| Accepted state | `Тест принят · версия {hash}. Агент не запускался.` |
| Invalidated after edit | `Тест изменён — подтвердите новую версию.` |
| Empty state heading | `Нет подтверждённой гипотезы` |
| Empty state body | `Сначала подтвердите одну гипотезу о сбое; без неё тест не собирается.` |
| Unsupported-value error | `Тест не собран: значение «{value}» не подтверждено источниками. Уточните материал или исправьте тест; агент не запускался.` |
| Limit error | `Тест не собран: подтверждённых значений {N}, допустимо до 20. Сократите тест; ничего не обрезано, агент не запускался.` |
| Stale-version error | `Тест изменился. Откройте актуальную версию и подтвердите её заново.` |
| Stale review state | `Тест изменён — прежнее принятие относится к другой версии.` |
| Destructive confirmation | Не применяется: фаза ничего не удаляет, не запускает целевого агента и не сохраняет регрессию. |

Тон: короткий и предметный. В основном разговоре сущность всегда называется `тестом`; только сериализованный контракт и техническое описание используют `карточка бизнес-сценария` / `business-scenario card`. Не показывать пользователю термины `user card`, `persona`, `calibration`, `confidence tier` или внутреннюю механику repair, если они не объясняют конкретную ошибку.

## Interaction Contract

### Primary surface and hierarchy

Главная поверхность — текущий разговор Pi. CLI печатает тот же компактный блок в stdout. `/agent-lab` остаётся необязательным доказательным видом: пользователь не должен открывать доску, отдельный редактор или модальное дерево, чтобы принять или поправить тест. Принятие вызывается отдельным `agent_lab_accept` / `accept --id --yes`; `agent_lab_run` / `run` сохраняют однозначный смысл запуска и не требуют acceptance metadata.

После принятой гипотезы показывается ровно один тест и ровно один вопрос:

```text
ТЕСТ
СИТУАЦИЯ
<одна заземлённая цель и только нужные для неё факты>

ВХОД
<точная первая реплика пользователя; необходимые продолжения идут следом в исходном порядке>

УСПЕХ
<полный непустой successCriteria>

НАБЛЮДЕНИЕ
<конкретный доступный канал: ответ агента, результат инструмента или снимок состояния>

Версия: <первые 12 символов draftHash>

Этот тест действительно проверяет нужное поведение?
```

- Все четыре поля и версия показываются до принятия; `successCriteria` и ввод не сокращаются и не скрываются в details.
- `initialState` показывается только когда он непуст и необходим для понимания наблюдаемого результата; пустой объект не рендерится.
- Канал наблюдения называется конкретно. Общие формулировки вроде `проверит судья` без видимого ответа, tool result или state snapshot блокируют принятие и возвращают тест на починку.
- В основном блоке `goal_attainment` не дублирует `УСПЕХ`: сохранённая карточка содержит ровно одну агентскую рубрику `goal_attainment`, дословно выведенную из `successCriteria`. Harness-рубрики в вопрос принятия не входят.
- Внешний код, ответы агента и сохранённые outcomes могут быть источником наблюдения, но никогда не формулируют ожидаемый ответ.

### Accept or edit

1. Pi использует нативный `ctx.ui.confirm` внутри `agent_lab_accept`. Положительный ответ записывает принятие текущего полного `draftHash`; в этой фазе он не открывает `TargetSession`, не запускает симулятор и не сохраняет suite.
2. CLI сначала печатает тот же блок и хеш. Явный `--yes` принимает именно показанный хеш; без `--yes` команда останавливается с подсказкой повторить после проверки. Интерактивный CLI-промпт не добавляется.
3. Отказ оставляет черновик доступным для правки и отвечает `Тест не принят. Напишите, что исправить.` Обычная просьба пользователя преобразуется в существующий `agent_lab_edit` с текущим `expectedHash`.
4. После любой смысловой правки снова показывается весь тест, новый короткий хеш и строка `Тест изменён — прежнее принятие относится к другой версии.` Старый hash сохраняется как stale review fact; `freshDraft` очищает его.
5. Запрос с устаревшим `expectedHash` ничего не меняет и показывает documented stale-version error. Автоматического merge нет.
6. Acceptance не является save/run permission gate. Существующие multi-card regression/validation suites запускаются и сохраняются по прежнему контракту; само сохранение найденного полезного теста в основной продуктовой петле остаётся Phase 5.

Нативное подтверждение — единственная церемония принятия. Не добавлять checkbox, approval status form, второй confirm перед сохранением или самостоятельную команду-редактор. Само accept-действие отдельно от run, чтобы повтор команды не превращался из принятия во внешний запуск.

### Discovery state before the test

Для большой пачки логов до блока теста показывается один компактный exploratory-результат: `Повторяющийся сигнал: {C} из {N} — это отбор, не accuracy`, `Подробно проверено: {K} из {N} ({R} примера + {Q} контроля)`, ссылки на выбранные диалоги, одна гипотеза, `НАБЛЮДЕНИЕ: ответ агента (reply)` для текущего prompt/RAG-only MVP и `Проверим?`. Обычное «да» подтверждает уже показанные гипотезу и канал; модель канал не выбирает. Budget exhausted, partial и validation error показываются раньше hypothesis/insufficient-data copy и сохраняют уже собранные ссылки.

### Grounding and repair

- Сборка допускает `answers[].reply` в `knows` только после детерминированного case-insensitive full-token match с материалами владельца или evidence диалога.
- Неподтверждённое значение, отсутствующее обязательное поле, недоступный канал наблюдения или результат свыше 20 значений не рендерятся как готовый тест: показывается одна конкретная ошибка и черновик возвращается на bounded repair.
- Repair обновляет одну progress-строку `Исправляю тест по источникам…`; прошлые progress-строки не накапливаются.
- Ничего не обрезается молча и никакие неподтверждённые значения не заменяются догадкой. После починки весь тест показывается заново.

### Terminal behavior and accessibility

- Весь внешний текст проходит существующий `safeText()` перед Pi/CLI-рендером; ANSI, управляющие и bidi-символы не исполняются.
- Поля идут одной колонкой и переносятся по ширине терминала без горизонтальной прокрутки. Порядок не меняется на узком терминале.
- Полный `successCriteria`, вход и канал наблюдения остаются видимыми; длинный текст переносится, а не сокращается, потому что принятие связано с точной семантикой.
- Используются нативный фокус Pi, Enter/confirm и Esc/cancel. Новые горячие клавиши, мышиные affordance и модальные формы не добавляются.
- Цвет всегда дублируется заголовком, сообщением состояния и хешем. Вопрос и подписи вариантов доступны как обычный текст экранному считывателю терминала.
