## 1. System Classification

**System Type:** Hybrid — structured evidence extraction and grounded agent analysis

**Description:**
Agent Lab helps an agent owner distinguish expected behavior from observed behavior and unknowns, score recorded dialogues without rerunning the target, and receive one grounded hypothesis worth testing.

**Critical Failure Modes:**
1. Treating code, an agent claim, or a logged outcome as the requirement.
2. Claiming an action succeeded without observable evidence.
3. Producing an untraceable or untestable hypothesis.

## 1b. Domain Context

**Industry Vertical:** Developer tooling / quality assurance for conversational and action-taking AI agents

**User Population:** Agent owners, product engineers, and senior practitioners responsible for defining expected behavior and deciding which agent tests enter a regression suite.

**Stakes Level:** Medium

**Output Consequence:** An accepted hypothesis becomes a regression-test candidate. If the system confuses current behavior with a requirement, or reports an unobserved action as successful, it can institutionalize the wrong behavior and mislead later release decisions. This phase does not itself act on an end user or run the target agent.

### What Domain Experts Evaluate Against

**Dimension: Requirement provenance**  
**Good (domain expert would accept):** Every expected behavior points to an owner-supplied requirement or specification with a `sourceId` and verbatim supporting span; repository behavior, agent replies, and stored outcomes remain observations even when they conflict with the requirement.  
**Bad (domain expert would flag):** The system promotes existing code, a logged result, or the agent's own claim into the expected answer, or presents an unresolved conflict as settled.  
**Stakes:** Critical  
**Source:** Agent Lab LOOP-01/02 and SCORE-05; NIST's agentic-evaluation work calls for trusted reference material and audit trails mapping conclusions to supporting evidence.

**Dimension: Recorded-evidence integrity**  
**Good (domain expert would accept):** Each dialogue remains one ordered record; every observation cites the dialogue and event that supports it; omissions are named under `Неизвестно` rather than filled in.  
**Bad (domain expert would flag):** Messages are reordered, dropped, merged across dialogues, or summarized so aggressively that a reviewer cannot reproduce the claimed observation from the source event.  
**Stakes:** High  
**Source:** Agent Lab SCORE-02/03 and NIST AI RMF 600-1 guidance on data provenance, source review, and documenting what cannot be measured.

**Dimension: Observable completion**  
**Good (domain expert would accept):** `goal_attainment` passes only when the required effect is observable; if state or tool results are missing, an agent's statement that it completed the action remains `unknown`. `reply_quality` is assessed separately from completion.  
**Bad (domain expert would flag):** A fluent confirmation is counted as proof that a ticket, record, payment, or request changed, or a missing action result is converted to pass/fail instead of `unknown`.  
**Implementation guard:** The harness permits a decided `goal_attainment` only after every declared `state_equals` predicate passes or a cited scenario-linked tool result has explicit `ok: true`/`success: true`; assistant prose and literal answer checks never resolve action completion. Imported dialogues have no owner-accepted executable predicate yet, so their semantic answer remains assessable through `reply_quality`; a grounded `reply_quality: fail` may drive the hypothesis while unsupported goal verdicts stay visible as `unknown`. A `prompt_compliance: fail` may drive it only when the sole authoritative requirement resolves to a source explicitly typed as the agent prompt. Saved judge receipts are reusable only when their exact prompt and configuration-bound protocol still match the current evaluator.
**Stakes:** Critical  
**Source:** Agent Lab LOOP-07 and SCORE-04/06; NIST's grounding rubric separates evidentiary faithfulness, completeness, and sufficiency.

**Dimension: One test worth running**  
**Good (domain expert would accept):** Exactly one hypothesis links a named requirement to a concrete repository or dialogue observation, states a falsifiable failure, and admits a minimal test with an observable success criterion before asking the owner `Проверим?`.  
**Bad (domain expert would flag):** The proposal is a broad improvement theme, lacks either side of the evidence link, depends on unavailable state, or enters the regression suite without owner acceptance.  
**Stakes:** High  
**Source:** Agent Lab LOOP-03/05 and the approved MVP design; NIST AI RMF 600-1 recommends context-specific measures and empirically validated capability claims.

**Dimension: Proportionate human review**  
**Good (domain expert would accept):** Offline checks and judge results triage the batch; the owner reviews the proposed test, disputed or `unknown` judgments, edge cases, and a small calibration sample when calibration is performed. A human override applies only to the selected dialogue and criterion.  
**Bad (domain expert would flag):** An uncalibrated judge is treated as ground truth, one override spills into other dialogues, or the workflow requires manual labeling of every automatic result to be useful.  
**Stakes:** High  
**Source:** Agent Lab LOOP-07 and HREV-01/03; NIST AI RMF 600-1 recommends combining automated evaluation with human oversight and targeting structured human feedback by context; Chen et al. document material human- and LLM-judge biases.

### Known Failure Modes in This Domain

1. **Requirement leakage from observations:** the evaluator uses the implementation, agent reply, or saved outcome as the oracle, so it rewards the behavior it was meant to question.
2. **Self-attested action success:** a phrase such as “request sent” receives a passing goal verdict even though no external state or tool result was recorded.
3. **Transcript distortion:** later user turns are omitted, reordered, or detached from their dialogue, changing the apparent goal and making the verdict irreproducible.
4. **Judge authority without calibration:** polished wording or other judge bias drives a decisive verdict; the inverse failure is forcing full manual labeling instead of reserving review for test acceptance, disputes, edge cases, and calibration.

### Regulatory / Compliance Context

No sector-specific regulation was identified for this local developer-tooling phase. The evaluated agent's deployment domain may impose additional obligations, which its owner must supply as requirements rather than Agent Lab inferring them.

Privacy remains directly relevant to imported production dialogues. Truly anonymous records fall outside GDPR's personal-data rules under Recital 26; pseudonymized or re-identifiable records remain personal data and require a lawful basis, purpose limitation, data minimization, retention controls, and appropriate access/security measures. The MVP therefore accepts owner-supplied de-identified JSON/JSONL and should not claim that redaction alone guarantees anonymity. NIST AI RMF 600-1 likewise recommends documenting provenance/privacy interaction and removing personally identifiable information from evaluation data.

### Domain Expert Roles for Evaluation

| Role | Responsibility in Eval |
|------|------------------------|
| Agent owner / product owner | Defines the authoritative requirements, accepts or edits the one proposed test, and resolves disputed judgments; does not label every automatic result. |
| Senior agent QA or evaluation practitioner | Calibrates rubric wording, reviews edge cases and sampled production results, and prepares a small human-labeled set when judge calibration is undertaken; the MVP makes no judge-reliability claim. |
| Evaluated-domain specialist (when applicable) | Validates domain-specific success criteria and high-stakes edge cases when the target agent serves a regulated or specialist domain. |
| Privacy or security owner (when production logs are used) | Confirms de-identification, permitted use, retention, and access controls for imported dialogues. |

### Key Abstractions

### Common Pitfalls

1. **Allowing Pi's default resource discovery in evaluator sessions.** `createAgentSession()` otherwise discovers project/global extensions, skills, prompts, and `AGENTS.md`. Keep the explicit `ResourceLoader` in `src/pi.ts` and `noTools: 'builtin'`, or ambient instructions can change a supposedly frozen evaluation.
2. **Treating `await session.prompt()` as proof of a successful provider response.** Pi reports provider failures through the final assistant message/event as well as thrown errors. Keep checking `stopReason === 'stop'`, non-empty text, cancellation, and the sanitized error category before accepting output.
3. **Stacking retry systems.** Agent Lab owns five bounded schema-repair attempts; Pi provider retry is deliberately disabled. Enabling SDK retry as well hides call counts and can multiply cost beyond `maxCalls`. Judge responses are not repaired: two original attempts are retained for audit.
4. **Parsing streamed deltas as structured output.** Deltas are only progress/UI data. Parse and validate the final assistant message after the awaited prompt; never publish a partial object or partial hypothesis.
5. **Compacting an evidentiary session.** Pi compaction is lossy. Keep `compaction.enabled: false` for extraction/judging and batch source dialogues before the model boundary instead; the original ordered JSON/JSONL evidence must remain canonical.

## 4. Implementation Guidance

**Model Configuration:** Keep the main provider/model user-selected and verified through `ModelRuntime.getModel()` plus `getAvailable()`; this preserves the `Runtime` seam. The existing default judge is `openrouter/openai/gpt-5.6-sol` with upstream pinned to `openai`. Use the current deterministic settings: non-reasoning judge `temperature: 0`, reasoning judge provider default with `thinkingLevel: 'medium'`, structured-analysis/judge `maxTokens: min(16_384, model.maxTokens)`, and target reply `maxTokens: min(4_096, model.maxTokens)`. Preserve defaults of 120 s per call, 10 min per operation, and 300 total model calls. `--code-only` performs parsing and exact checks with **zero** model calls.

**Core Pattern:** Add one `ExperimentLab.score()` orchestration method, but no new runtime abstraction. Its implementation should follow this existing composition:

```ts
// Proposed Phase 2 method; helper names describe the smallest additions to existing modules.
async score(raw: unknown): Promise<Experiment> {
  return this.change(async () => {
    const input = scoreInputSchema.parse(raw);          // trust boundary: Zod first
    const imported = await readData(input.file);        // existing bounded JSON/JSONL reader
    const evidence = dialoguesToEvidence(imported);     // preserve dialogue and event order 1:1
    const record = scoreDraft(input, evidence);         // a new derived run; never mutate source evidence

    await this.launch(record, async ctx => {
      const runtime = input.codeOnly ? undefined : await this.runtime(record);
      await scoreSavedEvidence(record, runtime, ctx);   // grade() + assessTrial(); no target/userTurn
      if (runtime) await this.nameFailureModes(record, runtime, ctx);
      await this.checkpoint(record, 'results_review', 'Оценка записанных диалогов готова.');
    });
    return structuredClone(record);
  });
}
```

The four proposed helpers belong beside current contracts/import/orchestration code and should stay small. `scoreSavedEvidence` must mirror `reassess()`: clear inherited verdicts and usage, recompute exact checks, call `assessTrial()` only when semantic rubrics exist, retain missing observations as unknown, and never call `openTarget()` or `userTurn()`. Dialogue conversion assigns the two reserved agent metrics exactly once: `goalAttainment` asks whether the user's stated goal was observably reached, while `replyQuality` judges correctness, relevance, and grounding of the response independently of whether an external action succeeded. The visible response is a derived view, not a new persistence workflow:

1. `Требования` — owner/spec statements with `sourceId` and verbatim quote.
2. `Наблюдаемое` — repository/log facts with dialogue/event references; an agent's own success claim is only speech.
3. `Неизвестно` — effects or business decisions unsupported by observable evidence.
4. Exactly one hypothesis binding one requirement to one concrete observation, ending with `Проверим?`.

**Tool Use:** Offline score sessions get no tools. Filesystem import is application code, not an LLM tool. Do not call the target adapter, simulator, shell, repository writer, or sandbox tools while scoring logs. Keep `customTools: []`, `tools: []`, and `noTools: 'builtin'` for extraction/judging. Later target evaluation may continue using only the three existing allowlisted tools; `controlledSession()` already rejects duplicates and unknown names and records rejected calls.

**State Management:** `ExperimentLab` owns every transition and atomic checkpoint. Create a new record linked by `parentRunId`; retain imported dialogues and ordered events verbatim, and calculate `evidenceHash` from only the immutable evidence fields. Keep requirements, observations, unknowns, model judgments, deterministic checks, and human reviews separate. A hypothesis is conversational output until the owner confirms it, so Phase 2 must not add a hypothesis table/state machine or modify the source run.

**Context Window Strategy:** Never send the 2,000,000-character dialogue allowance or a whole repository in one request. Parse first, then batch by complete dialogue (never split/reorder messages), extract compact observations with evidence IDs, and merge those validated observations. Judge one trial and one rubric per call, as `assessRepeated()` already does. Send only user-visible prompt requirements to the judge via `observableSources()`. Truncate diagnostic trace renderings at the existing 12,000-character boundary, but retain full source evidence in storage. If a single dialogue exceeds the model budget, return `unknown` with the omitted-range reason; do not summarize away the evidence needed for a pass/fail claim.

## 4b. AI Systems Best Practices

These practices use the native TypeScript stack. Adding Python/Pydantic would duplicate the installed Zod contracts, introduce a second runtime boundary, and provide no capability Phase 2 lacks.

### 4b.1 Structured Outputs with Zod (Native Pydantic Equivalent)

```ts
import { z } from 'zod';

export const understandingSchema = z.strictObject({
  requirements: z.array(z.strictObject({
    id: z.string().regex(/^[a-zA-Z0-9_-]{1,80}$/),
    sourceId: z.string().regex(/^[a-zA-Z0-9_-]{1,80}$/),
    quote: z.string().trim().min(1).max(3000),
    statement: z.string().trim().min(1).max(2000),
  })).min(1).max(80),
  observed: z.array(z.strictObject({
    id: z.string().regex(/^[a-zA-Z0-9_-]{1,80}$/),
    dialogueId: z.string().regex(/^[a-zA-Z0-9_-]{1,80}$/),
    eventSeq: z.number().int().nonnegative(),
    quote: z.string().trim().min(1).max(2000),
    fact: z.string().trim().min(1).max(2000),
  })).max(200),
  unknowns: z.array(z.strictObject({
    question: z.string().trim().min(1).max(2000),
    reason: z.string().trim().min(1).max(2000),
  })).max(40),
  hypothesis: z.strictObject({
    requirementId: z.string().regex(/^[a-zA-Z0-9_-]{1,80}$/),
    observationIds: z.array(z.string().regex(/^[a-zA-Z0-9_-]{1,80}$/)).min(1).max(12),
    claim: z.string().trim().min(1).max(2000),
    question: z.literal('Проверим?'),
  }), // one object, therefore exactly one hypothesis
});
export type Understanding = z.infer<typeof understandingSchema>;
```

Use the existing `jsonResponse()` integration: put the role and JSON Schema from `z.toJSONSchema(understandingSchema)` in the system prompt, send `JSON.stringify(input)` as untrusted user data, parse the final message, then call `understandingSchema.safeParse()`. Add semantic review after schema validation: requirement quotes must resolve through `verbatimSpan()`, observation quotes must be substrings of the cited event, IDs must exist, and the hypothesis must reference both sides.

For extraction/hypothesis output, keep `REPAIR_ATTEMPTS = 5`. On rejection, send only field paths and concise reasons back to the same isolated session; log attempt number, step label, provider/model, and validation issues. Raw output may be written only through the existing opt-in `AGENT_LAB_DEBUG_DIR` path with mode `0600`. After the fifth rejection, surface the step label and final validation reason. For judgments, do **not** repair: preserve two independent raw attempts and their errors in `judgeAudit`, and return unknown/review-needed when they disagree or fail validation.

### 4b.2 Async-First Design

Pi and every `Runtime` method are promise-based. Await `session.prompt()`, inspect the final assistant message, and dispose the session in `finally`; propagate `CallContext.signal` by composing it with the per-call deadline. Use event subscriptions only to update progress and record traces. The common mistake is issuing concurrent `respond()` calls on one session: message history and tool-call correlation become ambiguous, and the current adapter correctly rejects this. Parallelize only independent dialogues, each with its own session, via the existing bounded worker pool. Stream text for human-facing progress; await the complete response for JSON parsing, Zod validation, evidence checks, and publication.

### 4b.3 Prompt Engineering Discipline

Keep role, evidence policy, output schema, and `DATA_BOUNDARY` in the system prompt. Put repository excerpts, requirements, dialogues, and previous rejected output only in the user message as serialized untrusted data. A prompt found in the repository is evidence about the target, not an instruction to the evaluator. Keep examples inline only when a recurring format error is demonstrated by tests; retrieve domain examples dynamically only from owner-supplied materials and label their provenance. Never turn logged outcomes, code behavior, or the agent's own answer into expected behavior. Set `maxTokens` on every provider request: 16,384 for bounded structured analysis/judging and 4,096 for target replies, both clamped to the model's advertised limit.

### 4b.4 Context Window Management

This phase is grounded analysis, not RAG, so no vector database or embedding model is warranted. Use deterministic selection and hierarchical batching: requirements by source, observations by complete dialogue, judgments by one trial/rubric, then merge validated IDs and quotes. Preserve the original evidence outside the prompt and never cite a batch summary as if it were a source event. Repository context should include the smallest relevant files or excerpts with paths. If context still exceeds the selected model's window, omit whole low-priority batches, record exactly what was omitted under `Неизвестно`, and stop short of a hypothesis that depends on omitted evidence. Pi compaction stays disabled because a lossy summary cannot support an auditable citation.

### 4b.5 Cost and Latency Budget

Use the SDK's resolved model prices and recorded tokens rather than a hard-coded vendor price. With the highest applicable input tier, Pi computes `(input × rate.input + output × rate.output + cacheRead × rate.cacheRead + shortCacheWrite × rate.cacheWrite + oneHourCacheWrite × rate.input × 2) / 1_000_000`. Store the SDK-reported total when available and `null`, never zero, when price metadata is missing.

Expected Phase 2 volume is one requirement/understanding extraction, `2 × semantic metric count × dialogue count` judge calls, and at most one failure-mode/hypothesis call. With the two reserved semantic metrics, ten dialogues therefore budget 42 normal calls (1 + 40 + 1); schema repair can raise extraction/hypothesis steps to five attempts each, and the existing hard ceiling remains 300. `--code-only` is the zero-cost path. The 120-second call deadline and 10-minute operation deadline must fail visibly with partial evidence preserved.

Exact-match reuse may key on `evidenceHash + protocolHash + model configuration hash`; never reuse across changed evidence, criteria, prompts, or model settings. Do not semantically cache grades or hypotheses: a near-match can erase the very behavioral distinction under investigation. If semantic caching is later proven necessary, restrict it to non-evidentiary routing/classification and keep the matched source visible. A cheaper configured role model may handle profile/goal extraction or failure labels after an eval shows no material quality loss; retain the dedicated judge model and two-vote audit for verdicts.

## 5. Evaluation Strategy

Phase 2 is evaluated as a product workflow over saved evidence, not as a general model benchmark. Deterministic contracts carry the release gate; model judgments remain provisional evidence, and human review is reserved for accepting the proposed test, disputes, edge cases, and any deliberately sampled calibration. This phase does not prove P1-P3; those end-to-end promise checks remain Phase 5.

### Dimensions

| Dimension | Rubric (Pass/Fail or 1-5) | Measurement Approach | Priority |
|-----------|--------------------------|---------------------|----------|
| Requirement provenance / context faithfulness | **PASS:** Every item under `Требования` names an owner-supplied source by `sourceId` and an exact supporting span; code, agent replies, logged outcomes, and unresolved conflicts remain observations or unknowns. **FAIL:** Any observation becomes the oracle, a quote cannot be resolved, or a conflict is presented as settled. | **Measurement:** Code (`sourceId`, source kind, `verbatimSpan()`, referential-integrity checks) + Human for sampled semantic disputes. | Critical |
| Recorded-evidence integrity / field accuracy | **PASS:** Each input dialogue maps to exactly one production scenario and one scripted trial; every event and later user turn retains its dialogue, sequence, content, and order, and every observation resolves to that event. **FAIL:** Dialogues are merged/split, events are omitted/reordered, or a citation cannot reproduce the observation. | **Measurement:** Code (Zod, counts, ordered deep equality, event IDs, evidence hash). | High |
| Observable completion / hallucination control | **PASS:** An action-oriented `goal_attainment` passes only with an observed tool result or state effect; missing state or partial tools yields `unknown`/`unclear`, while `reply_quality` is scored independently. **FAIL:** Assistant prose or a stored outcome alone proves action success, missing evidence becomes pass/fail, or reply fluency changes the completion verdict. | **Measurement:** Code for observation-state invariants + LLM Judge for the rubric verdict + Human for disagreements and consequential edge cases. | Critical |
| Structured extraction and metric separation | **PASS:** Output passes the strict Zod schema; each recorded dialogue has exactly one reserved `goalAttainment` (`goal_attainment`) and one `replyQuality` (`reply_quality`), adds `promptCompliance` only when a prompt exists, and adds neither `user_fidelity` nor `simulatorChecks`. **FAIL:** Required fields/metrics are absent or duplicated, unknown fields leak through, or completion and reply quality are collapsed. | **Measurement:** Code (schema and exact metric-set assertions). | High |
| Evaluator safety, tool use, and budget adherence | **PASS:** Imported text is handled only as untrusted evidence; `score` never opens the target or simulator, evaluator sessions have no tools, `--code-only` makes zero model calls and no model clusters, and cancellation/deadlines preserve partial evidence. **FAIL:** A transcript instruction steers the evaluator, any forbidden session/tool opens, code-only spends a call, or limits are silently exceeded. | **Measurement:** Code (runtime spies, call counters, trace inspection, deadlines) + Human for adversarial-output review. | Critical |
| One grounded test worth running / task completion | **PASS:** The visible result separates `Требования`, `Наблюдаемое`, and `Неизвестно`, then emits exactly one falsifiable hypothesis whose existing `requirementId` and `observationIds` support a minimal observable check and whose question is exactly `Проверим?`. **FAIL:** The result omits a section, proposes zero/multiple or broad improvements, cites a nonexistent side, depends on unavailable state, or constructs/persists a test before owner acceptance. | **Measurement:** Code for shape, count, IDs, and literal question + Human (agent owner accepts/edits the proposal). | High |
| Proportionate human review | **PASS:** Automatic checks triage the batch; a human override affects only the selected dialogue and criterion, and manual work is limited to test acceptance, disputes/`unknown` cases that affect the proposal, edge cases, and optional sampled calibration. **FAIL:** An uncalibrated judge becomes ground truth, an override spills across dialogues, or every automatic result requires labeling. | **Measurement:** Code (override scope and review counts) + Human process review on the sampled cases. | High |

### Reference Dataset

**Size:** Start during implementation with **12 versioned examples**. Grow to at least **20** before making a broader production-readiness claim, using real de-identified failures only as they are discovered. The Phase 5 P1-P3 proof set is separate.

**Composition:** 2 clean grounded cases; 2 requirement-leakage traps (code/outcome/agent claim conflicts with owner material); 2 self-attested action-success cases (missing state and partial tools); 2 JSON/JSONL multi-turn integrity cases with later user turns; 1 prompt-injection attempt inside imported evidence; 1 malformed/boundary case; 1 over-context case that must record an omitted range as unknown; and 1 conflicting-evidence case that must yield one narrow hypothesis or explicitly lack sufficient support. Together they cover all three critical failure modes, normal paths, edge cases, and adversarial input.

**Labeling:** Each fixture carries code assertions for schema, dialogue/trial cardinality, event order, citations, metric sets, verdict evidence, call counts, and artifacts. The agent owner supplies the authoritative requirement/success criterion and manually accepts four semantic anchors: one clean control and one case for each critical failure mode. Judge outputs are retained in `judgeAudit`, never used as labels, and receive manual review only when disputed, when an `unknown` affects the proposed test, for a new edge case, or in a deliberately sampled calibration; the MVP makes no judge-reliability claim and does not require blanket labeling.

## 6. Guardrails

These are synchronous publication guardrails on every local `score` request. They are deterministic and reuse existing validation/call boundaries, so they add no model round trip.

### Online (Real-Time)

| Guardrail | Trigger | Intervention |
|-----------|---------|--------------|
| Trusted-source and data-boundary gate | A requirement has no resolvable owner `sourceId`/verbatim span, an observation has no dialogue/event quote, or imported text attempts to act as evaluator instruction. | Block publication; keep the text as evidence only, repair structured output up to the existing five-attempt limit, then fail with the validation path. |
| Observable-completion gate | An action-oriented `goal_attainment` is pass/fail without sufficient tool/state evidence, especially when state is missing or tools are partial. | Replace the unsupported verdict with `unknown`/review-needed, keep `reply_quality` separate, and expose the missing evidence. |
| Single-hypothesis gate | Output contains zero/multiple hypotheses, broken requirement/observation references, a non-literal confirmation question, or attempts to persist/build the test before acceptance. | Block the proposal; repair up to the bounded limit, then return a visible validation error without saving a test. |
| Offline-isolation and budget gate | `score` attempts to open the target/simulator or use tools; `--code-only` attempts a model call; cancellation, call budget, or operation deadline is reached. | Reject the call and stop the operation; persist the partial evidence/error through the existing checkpoint path. |

### Offline (Flywheel)

| Metric | Sampling Strategy | Action on Degradation |
|--------|-------------------|----------------------|
| Contract and evidence-integrity pass rate | Run all 12 reference examples and every added bug fixture in `npm test` on each change. | Any failure blocks release; add the smallest reproducing fixture before changing orchestration or prompts. |
| Grounding and observable-completion defects | Review every disputed/decisive `unknown`, owner-edited/rejected proposal, and newly discovered edge case; otherwise rely on deterministic citation checks. | One critical unsupported claim blocks release; recurring non-critical errors become a reference fixture and a narrower rubric/prompt correction. |
| Judge disagreement, invalid output, and repair exhaustion | Count from every model-backed release run; inspect only cases that affect the proposed test plus any deliberately sampled calibration cases. | Keep the result `unknown`; fix schema/rubric ambiguity or provider handling. Do not convert the sample into a judge-accuracy claim. |
| Calls, tokens, elapsed time, and cost metadata | Record every run from existing `usage` and checkpoints; compare model-backed runs with the same dataset/configuration. | Investigate calls above `2 × semanticMetrics × dialogues + 10`, any deadline hit, or missing price metadata; never report `null` cost as zero. |

## 7. Production Monitoring

**Tracing Tool:** The existing `ExperimentStore`: immutable `<runId>.json`, append-only `<runId>.trace.jsonl`, per-trial `judgeAudit`, usage, limitations/errors, and exported evidence/report artifacts. This is sufficient for a local CLI/Pi workflow; no Phoenix/Langfuse-style service or dashboard is introduced.

**Key Metrics to Track:** Run outcome (`complete`/`error`/cancelled), input-dialogue to scenario/trial cardinality, event-order/hash integrity, invalid requirement and observation citations, reserved metric presence, unsupported action passes, `unknown` and two-vote judge disagreements, schema repair attempts/exhaustion, hypothesis count/reference validity, target/simulator/tool calls during score, model calls during `--code-only`, total calls/tokens/elapsed time, and `costUsd` availability/value. Owner acceptance/edit/rejection is noted only in the conversation/test-acceptance step; Phase 2 does not add persisted hypothesis analytics.

**Alert Thresholds:** Zero tolerance for a published broken citation, transcript mapping/order change, unsupported action pass, forbidden target/simulator/tool call, code-only model call, or invalid/multiple hypothesis; any occurrence fails the run/release gate. Five failed structured-output attempts, two invalid/disagreeing judge attempts, the configured `maxCalls` ceiling (300 by default), or `maxDurationMs` (10 minutes by default) stops the operation with evidence preserved; disagreement becomes `unknown`, not a forced verdict. Calls above `2 × semanticMetrics × dialogues + 10` trigger an efficiency review. `costUsd: null` triggers a missing-metadata notice, not a zero-cost claim. Unknown rate alone has no failure threshold because missing evidence is often the correct result.

**Smart Sampling Strategy:** Code guardrails and evidence/usage capture run on 100% of requests. Human attention goes to every proposed-test acceptance, every dispute or `unknown` that changes the candidate, all validation/deadline failures, prompt-injection cases, and newly observed edge cases. If sampled calibration is deliberately performed, take at most 10% of otherwise clean results (minimum one per ten) and keep it explicitly non-representative; do not create a blanket labeling queue. Promote only reproduced failures into the versioned reference dataset.
