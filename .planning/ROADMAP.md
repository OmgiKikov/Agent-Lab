# Roadmap: Agent Lab

## Overview

Путь к MVP строится вокруг одного разговора: Agent Lab изучает требования и доступные логи, предлагает гипотезу о сбое, собирает минимальный тест, запускает настоящего агента, показывает доказательства и сохраняет принятый владельцем тест как регрессию. Честный человеческий разбор остаётся вспомогательной границей для спорных случаев. Задачи исходного плана 1–18 сохраняются как технический backlog, но фазы 2–5 теперь явно собирают этот основной пользовательский цикл.

## Phase Details

### Phase 1: Честный человеческий разбор

**Goal**: Человек может проверить каждый диалог по его событиям, скорректировать конкретный критерий и видеть честное соотношение автоматической и ручной оценки.
**Depends on**: Nothing (first phase)
**Source tasks**: 1–3 (pre-demo cutoff)
**Requirements**: HREV-01, HREV-02, HREV-03, HREV-04, HREV-05, HREV-06
**Success Criteria** (what must be TRUE):

  1. Первый экран одновременно показывает пройденные карточки, карточки без решения, недошедшие карточки и «разобрано человеком K из D диалогов».
  2. Последний человеческий вердикт по выбранному критерию предсказуемо исключает его, заменяет судью или сохраняет `unknown` согласно выбранному значению.
  3. Счётчик полного разбора увеличивается только после вердикта на весь диалог с пояснением и номером события; частичные и legacy-аннотации его не меняют.
  4. Вердикт меняет только текущий диалог и явно выбранный критерий или проверку; другие диалоги той же причины остаются нетронутыми.
  5. Причины на первом экране ведут в очередь диалогов, которые можно открыть и разобрать по одному.

### Phase 2: Понимание агента и гипотеза

**Goal**: Agent Lab отделяет требования от текущего поведения, использует репозиторий и доступные логи как доказательства и предлагает владельцу одну конкретную гипотезу о сбое для проверки.
**Depends on**: Phase 1
**Source tasks**: 4–7 (pre-demo cutoff)
**Requirements**: LOOP-01, LOOP-02, LOOP-03, SCORE-01, SCORE-02, SCORE-03, SCORE-04, SCORE-05, SCORE-06, SCORE-07, SCORE-08
**Success Criteria** (what must be TRUE):

  1. Краткое резюме явно разделяет требования владельца, наблюдаемое текущее поведение и неизвестное; код и ответ агента не становятся эталоном.
  2. JSON/JSONL-логи импортируются без запуска агента или симулятора и сохраняют события в исходном порядке как evidence для гипотез.
  3. Agent Lab предлагает конкретную проверяемую гипотезу, указывает требование и наблюдение, из которых она следует, и просит подтверждение перед сборкой теста.
  4. Ненаблюдавшееся действие остаётся `unknown`/`unclear`, даже если агент заявил об успехе; качество ответа оценивается отдельно.
  5. Существующий `mode: "score"` остаётся способом оценить записанный диалог и получить те же заземлённые артефакты без модельных вызовов в `--code-only`.

### Phase 3: Полезный тест и его принятие

**Goal**: Agent Lab находит в большой пачке логов повторяющийся сигнал, подробно проверяет несколько примеров и контролей, превращает подтверждённую гипотезу в компактный тест с явным способом наблюдения, а владелец принимает или правит точную версию теста до запуска и сохранения.
**Depends on**: Phase 2
**Source tasks**: 8–10 (pre-demo cutoff)
**Requirements**: LOOP-04, LOOP-05, DISC-01, DISC-02, DISC-03, DISC-04, DISC-05, DISC-06, DISC-07, CARD-01, CARD-02, CARD-03, CARD-04, CARD-05, CARD-06
**Success Criteria** (what must be TRUE):

  1. Тест явно показывает ситуацию, входные данные, `successCriteria` и доступный способ наблюдения результата до запуска агента.
  2. Карточка содержит только заземлённые поля и ровно одну агентскую рубрику `goal_attainment`; служебные рубрики добавляет harness.
  3. Выдуманное знание, неподтверждённый ответ или переполнение возвращают тест на починку без молчаливого обрезания.
  4. Владелец может принять одиночный предложенный тест или поправить его критерий; exact acceptance сохраняется как metadata, не блокируя существующие multi-test validation/regression наборы.
  5. Пользовательские поверхности называют сущность «тестом» в основном разговоре и «карточкой бизнес-сценария» / `business-scenario card` в сохранённом контракте.
  6. До подробной оценки 300 логов проходят coarse batch discovery; полный judge применяется не более чем к трём представителям повторяющегося сигнала и двум детерминированным контролям.
  7. Discovery показывает охват и доказательства как exploratory-отбор, никогда не выдаёт выбранную подозрительную подвыборку за accuracy и не скрывает исчерпание бюджета за «недостаточно данных».
  8. Информационная цель может получить решённый `goal_attainment` по принятому каналу `reply`; действие по-прежнему требует успешного tool result или наблюдаемого state effect.

### Phase 4: Настоящий запуск и доказательства

**Goal**: Принятый тест запускается через существующее подключение на настоящем агенте, а пользователь видит короткую цепочку «диалог → автоматическая проверка → доказательство» и обращается к ручному разбору только при споре.
**Depends on**: Phase 3
**Source tasks**: 11–17 (post-cut simplification)
**Requirements**: LOOP-06, LOOP-07, CUT-01, CUT-02, CUT-03, CUT-04, CUT-05, CUT-06, CUT-07, CUT-08
**Success Criteria** (what must be TRUE):

  1. Принятый тест выполняется реальным `TargetSession`; результат содержит исходный вход, полный диалог, автоматический вердикт и ссылку на использованное доказательство.
  2. Действие считается выполненным только по наблюдаемому эффекту; при отсутствии наблюдения итог остаётся `unknown`, независимо от слов агента.
  3. Ручной verdict доступен для спорного диалога или критерия, но не требуется для каждого автоматического результата.
  4. Доска оставляет только путь теста и доказательств; editor, `preview`, `clarify`, аудит судьи и исследовательские статистические поверхности не отвлекают от него.
  5. Старые JSON открываются без миграции, а живые документы описывают этот основной цикл и его границы.

### Phase 5: Сохранённая регрессия и повтор

**Goal**: Принятый владельцем тест сохраняется как регрессия, повторяется после изменения агента без смыслового дрейфа и даёт честную запись результата и обещаний MVP.
**Depends on**: Phase 4
**Source tasks**: 18 (measurable promise validation)
**Requirements**: LOOP-08, PROOF-01, PROOF-02, PROOF-03, PROOF-04, PROOF-05, PROOF-06
**Success Criteria** (what must be TRUE):

  1. Явно принятый одиночный тест получает стабильную идентичность; изменение его определения делает acceptance устаревшим. Эти метаданные не блокируют запуск и сохранение существующих multi-test validation/regression suites.
  2. После изменения агента тот же тест повторяется тем же протоколом, а `diff` перечисляет «починилось», «сломалось» и «несравнимо» без статистических заявлений.
  3. P1 измеряет время от подключения нового агента до доказательства по полезному принятому тесту; P2 — время принятия тестов и ручного разбора только спорных случаев; P3 — результат повтора сохранённых тестов.
  4. `docs/IMPLEMENTATION.md` содержит для каждого обещания критерий, фактические числа, статус «выполнено/невыполнено» и ссылку на сохранённый артефакт.
