# Requirements: Agent Lab

**Defined:** 2026-09-15
**Core Value:** Прочитать агента и его требования, предложить полезный тест, запустить его на настоящем агенте, показать доказательства и сохранить принятый тест как регрессию.

## v1 Requirements

### Core Product Loop

- [ ] **LOOP-01**: Agent Lab изучает репозиторий, явные требования и доступные логи и кратко разделяет ожидаемое поведение, текущее наблюдение и неизвестное.
- [ ] **LOOP-02**: Ожидание для теста выводится из требований и материалов владельца; существующий код, ответ агента и сохранённый outcome используются только как наблюдение, а не как эталон.
- [ ] **LOOP-03**: До построения теста Agent Lab предлагает конкретную гипотезу о сбое, называет её основание и спрашивает, стоит ли её проверить.
- [ ] **LOOP-04**: Для принятой гипотезы Agent Lab собирает минимальный тест с ситуацией, входными данными, критерием успеха и доступным способом наблюдения результата.
- [ ] **LOOP-05**: Пользователь принимает или правит сам тест; только явно принятый тест попадает в сохранённый регрессионный набор.
- [ ] **LOOP-06**: Принятый тест запускается через существующий `TargetSession` на настоящем подключённом агенте, а не на подменённой реализации.
- [ ] **LOOP-07**: Результат показывает диалог, автоматическую проверку и её доказательство; ненаблюдавшееся действие остаётся `unknown`, а ручной вердикт запрашивается только для спорного случая или калибровки.
- [ ] **LOOP-08**: Сохранённый принятый тест повторяется без смыслового изменения после правки агента и попадает в списки «починилось / сломалось / несравнимо».

### Human Review

- [x] **HREV-01**: Последний человеческий вердикт по критерию управляет итогом: `invalid` исключает критерий, `pass`/`fail` заменяет судью, `unknown` сохраняет неопределённость.
- [x] **HREV-02**: Полностью разобранным считается только диалог с явным вердиктом на весь диалог и `reviewedDialogue: true`; вердикты по критерию, проверке и legacy-аннотации счётчик не увеличивают.
- [x] **HREV-03**: Человеческий вердикт применяется только к показанному диалогу и явно выбранному критерию или проверке, никогда не распространяется на другие диалоги той же причины.
- [x] **HREV-04**: Первый экран одновременно показывает число пройденных карточек, карточек без решения, недошедших карточек и «разобрано человеком K из D диалогов».
- [x] **HREV-05**: Причины провалов служат очередью: из причины пользователь открывает входящие в неё диалоги и разбирает каждый отдельно.
- [x] **HREV-06**: Полный человеческий вердикт по диалогу сохраняется с пояснением, содержащим ссылку на номер события этого диалога.

### Recorded Dialogue Scoring

- [ ] **SCORE-01**: Пользователь может передать обезличенные записанные диалоги в JSON или JSONL вместе с задачей и материалами.
- [ ] **SCORE-02**: Каждый записанный диалог становится одной production-карточкой и одной scripted-попыткой со всеми событиями в исходном порядке и всеми последующими репликами пользователя.
- [ ] **SCORE-03**: При импорте записанных диалогов агент и симулятор не вызываются, наблюдение состояния отмечается как missing, инструменты как partial, а `user_fidelity` и `simulatorChecks` не применяются.
- [ ] **SCORE-04**: Production-карточка записанного диалога получает `goal_attainment` и независимую `reply_quality`, а при переданном промпте — также `prompt_compliance`.
- [ ] **SCORE-05**: Цель и критерий записанного диалога заземляются в переданных материалах и репликах пользователя; ответ агента и сохранённый outcome не используются как эталон правильности.
- [ ] **SCORE-06**: Если результат действия не наблюдался, заявление агента о выполнении не считается доказательством: `goal_attainment` остаётся `unknown`/`unclear` по протоколу судьи 8, а качество ответа оценивается отдельно.
- [ ] **SCORE-07**: `reassess` оценивает импортированные трассы и заново строит кластеры провалов; `--code-only` не вызывает модель и не строит кластеры.
- [ ] **SCORE-08**: `agent-lab score --input ... --task ... --yes` и `agent_lab_build` с `mode: "score"` выдают первый экран и пути артефактов оценённой записи; Pi-путь запрашивает подтверждение перед расходом на судью.

### Business-Scenario Cards

- [ ] **CARD-01**: Генерируемая карточка хранит `goal`, `facts`, `knows`, `opening`, `answers`, непустой `successCriteria` и только при необходимости `initialState` с точными проверками.
- [ ] **CARD-02**: Генерируемая внешняя карточка несёт ровно одну агентскую рубрику `goal_attainment`, построенную из её `successCriteria`, без подмены цели рубрикой тона или формата.
- [ ] **CARD-03**: Harness добавляет `prompt_compliance` только при наличии промпта и `user_fidelity` для симуляции; дополнительные рубрики создаёт только владелец через `agent_lab_edit`.
- [ ] **CARD-04**: Все значения из `answers[].reply` добавляются в `knows` без модельного раунда только при полном токенном совпадении с источником без учёта регистра; неподтверждённое значение или переполнение лимита 20 возвращает карточку на починку без молчаливого обрезания.
- [ ] **CARD-05**: Первый экран объединяет каждую зарезервированную рубрику `goal_attainment`, `prompt_compliance` и `reply_quality` в одну строку на прогон, а владельческие рубрики объединяет только при полном совпадении определения.
- [ ] **CARD-06**: Во всех текущих пользовательских строках и документации используется термин «карточка бизнес-сценария» / `business-scenario card`, а не «карточка пользователя».

### MVP Scope Cut

- [ ] **CUT-01**: Роль извлечения observed profiles отсутствует; профили задаёт только владелец, а записанные диалоги питают критерии через `goals`, не генерацию персон.
- [ ] **CUT-02**: TUI-редактор, `agent_lab_preview`, `agent_lab_clarify`, CLI `preview`/`clarify` и соответствующие действия доски отсутствуют; карточки правятся через `agent_lab_edit`, уточнения передаются как материалы.
- [ ] **CUT-03**: Команда и модуль аудита судьи отсутствуют, а текущая документация прямо говорит, что повторяемость и надёжность судьи в MVP не измеряются.
- [ ] **CUT-04**: CLI, отчёты и доска не содержат comparison пользовательских режимов, calibration, simulator-fidelity report, pilot summary, paired-family delta и confidence tier.
- [ ] **CUT-05**: `simulatorSummary`, `modeValue` и `preset: thorough` отсутствуют; на один прогон выбирается один пользовательский режим, а отдельные `simulatorChecks` остаются видны в диалоге.
- [ ] **CUT-06**: Доска содержит ровно три экрана — список прогонов, обзор с карточками и диалоги с индивидуальным вердиктом; после повтора обзор показывает только итоговый заголовок сравнения.
- [ ] **CUT-07**: Старые JSON с `familyId`, `profileId`, `persona`, `characteristics`, `cannotKnow`, `external` и legacy `clarifications` открываются и переоцениваются без миграции; удалённые поля не отвергаются схемой.
- [ ] **CUT-08**: Живые README, REFERENCE, WORKFLOWS, EVALS-METHOD, CONTEXT и skill описывают только текущий MVP, а удалённые исследовательские документы находятся в `docs/archive/` с предупреждением об историческом статусе.

### Repeat and Promise Validation

- [ ] **PROOF-01**: После изменения агента пользователь может повторить сохранённый набор тех же карточек тем же протоколом судьи.
- [ ] **PROOF-02**: `diff` и обзор повтора перечисляют пары «починилось», «сломалось» и «несравнимо» без заявлений о статистической значимости или общем улучшении.
- [ ] **PROOF-03**: P1 проверяется на ранее не подключавшемся агенте: от подключения до доказательства по первому полезному принятому тесту проходит не более 30 минут и не более двух раундов починки сборки либо обещание отмечено невыполненным с фактическими числами.
- [ ] **PROOF-04**: P2 проверяется на ровно 15 реальных диалогах: Agent Lab предлагает заземлённые тесты, владелец принимает или правит их не более 60 минут, а ручной разбор результата требуется только для спорных случаев; иначе обещание отмечается невыполненным с фактическими числами.
- [ ] **PROOF-05**: P3 проверяется повтором тех же принятых тестов с протоколом судьи 8: получены списки исправленных, сломанных и несравнимых пар либо обещание отмечено невыполненным с фактическими данными.
- [ ] **PROOF-06**: Для P1, P2 и P3 в `docs/IMPLEMENTATION.md` записаны критерий, фактический результат, статус «выполнено/невыполнено» и ссылка на артефакт без переформулирования проваленного обещания.

## v2 Requirements

Отдельные v2-обязательства не определены. Исследования и исключённые возможности ниже не считаются обещаниями следующей версии.

## Out of Scope

| Feature | Reason |
|---------|--------|
| Web UI, queue, log-platform connectors | Текущий продукт — локальный CLI/Pi workflow; интеграционная платформа не нужна для проверки обещаний MVP. |
| Automatic agent repair and expansion of `agent_lab_prompt` | MVP проверяет и повторно тестирует, но не исправляет агента автоматически. |
| Judge calibration, reliability claims, statistical significance | Надёжность судьи и репрезентативность малого набора не измеряются этим MVP. |
| Simulation-to-production comparison | Отдельное описательное исследование после MVP. |
| Simulator scorecards, mode-value statistics, user-mode comparison, paired-family delta | Удалены авторитетным срезом 2026-09-15; вариант 2026-09-14 superseded. |
| Rich editor/statistics/comparison surfaces | Доска намеренно оставляет три экрана; карточки правятся в разговоре. |
| Generated `profileId`, `persona`, `characteristics`, `cannotKnow`, `external` | Эти поля сохраняются только для чтения legacy-записей. |
| Third-party agent-evaluation frameworks | Новые зависимости не нужны для текущего ядра и обещаний P1–P3. |
