# Requirements: Agent Lab

**Defined:** 2026-09-16
**Core Value:** Владелец агента и заказчик за 10 секунд понимают, насколько хорош агент и почему он ошибается, и верят этому числу.

Термины: **ситуация** — карточка бизнес-сценария из validation set; **владелец** — человек, который запускает Lab на своего агента; **менеджер** — человек заказчика, который не открывает Pi; **новичок** — человек, который впервые ставит Lab на своего агента.

## v1 Requirements

Всё ниже — к демо заказчику 2026-09-21. Каждое требование проверяется на настоящем агенте эквайринга или на его сохранённых прогонах.

### Доверие к числу (TRUST)

- [ ] **TRUST-01**: Владелец видит одно главное число с одним знаменателем («справился в N из M проверенных ситуаций»). Блок в чате, доска, выжимка и HTML-отчёт показывают одно и то же число, потому что берут его из одного места.
- [ ] **TRUST-02**: Владелец видит «не измерено» отдельно от провалов: количество и главную причину, названную словами (без «прочее»). Такие ситуации не входят в знаменатель.
- [ ] **TRUST-03**: При малом числе ситуаций владелец и менеджер видят словами, насколько число неточно («мало данных: реальная доля где-то от X до Y»). Процент не выдаётся за точный.
- [ ] **TRUST-04**: В результате есть контрольная ситуация, с которой агент справляется. Поэтому «0 из N» нельзя принять за сломанного судью.
- [ ] **TRUST-05**: Владелец может повторить старый прогон внешнего агента и сравнить его с исходным. Значение канала наблюдения по умолчанию не делает ситуации «изменившимися» и не превращает сравнение в «несравнимы».
- [ ] **TRUST-06**: Совпадение id цели у двух диалогов при сборке validation set не роняет всю сборку после оплаченных вызовов модели.
- [ ] **TRUST-07**: Владелец получает одинаковый результат через CLI и через Pi. Одинаковы бюджет вызовов, масштабированный по числу диалогов, судья по умолчанию и таймаут на вызов.
- [ ] **TRUST-08**: Полный аудит судьи хранится отдельно от записи прогона. Запись прогона и отчёт не растут до лимита чтения (50 МБ), а старые записи по-прежнему открываются и переоцениваются.
- [ ] **TRUST-09**: Владелец видит ситуации, результат которых нестабилен. Переоценка сохранённых ответов и сравнение двух прогонов одного набора помечают ситуации, где вердикт меняется.
- [ ] **TRUST-10**: До запуска владелец на одном экране видит, что агент должен сделать в каждой ситуации и по какому правилу, и подтверждает это одним действием.
- [ ] **TRUST-11**: На экране ожиданий владелец может поправить ожидание ситуации своими словами, без ручной правки проверок.

### Судья и согласие человека (JUDGE)

- [ ] **JUDGE-01**: Владелец видит каждый провал в виде «должен был X → сказал Y → правило N (цитата)». N — номер и дословная цитата правила владельца, а не внутренняя нумерация судьи. Цитаты проверены по тексту диалога и требований; если проверка не прошла, объяснение помечено как неподтверждённое.
- [ ] **JUDGE-02**: Владелец видит «без решения» с причиной, названной словами: «нет доказательства» или «судья не уверен: голоса разошлись».
- [ ] **JUDGE-03**: Судья выносит решение везде, где есть доказательство. Доля «без решения» на пилотном прогоне измерена до и после изменений. Протокол судьи меняется не больше одного раза до заморозки 2026-09-18, и после изменения старые прогоны переоцениваются.
- [ ] **JUDGE-04**: Владелец на провале одной клавишей отмечает «согласен», «не согласен» или «не могу сказать». При несогласии он пишет короткую причину. Отметка хранит вердикт судьи и версию судьи, с которыми человек соглашался.
- [ ] **JUDGE-05**: Владелец и менеджер видят согласие человека с судьёй как «N из M проверенных» со списком несогласий. Согласие считается по исходным оценкам судьи; если проверок мало, это указано.
- [ ] **JUDGE-06**: В проверку подмешиваются 2–3 случайные ситуации «справился». Согласие показывается отдельно по провалам и по успехам.

### Экран в Pi (SCREEN)

- [ ] **SCREEN-01**: После прогона владелец видит в чате блок-вердикт:
  - строку-вердикт простым языком;
  - главное число;
  - три главные причины в формате JUDGE-01;
  - «не измерено»;
  - следующий шаг.

  В блоке нет внутреннего жаргона и обрезанного текста.
- [ ] **SCREEN-02**: Блок-вердикт остаётся в истории разговора и снова появляется при переоткрытии сессии. Он выглядит одинаково для прогона, запущенного из разговора, и для прогона из `/agent-lab`.
- [ ] **SCREEN-03**: Владелец открывает полноэкранную доску с вкладками «Итог / Провалы / Диалоги / Сравнение» и управляет ею с клавиатуры.
- [ ] **SCREEN-04**: На доске Enter на провале открывает диалог с подсвеченной репликой, где агент ошибся. Доказательство показано раньше вердикта судьи, и там же отмечается согласие (JUDGE-04).
- [ ] **SCREEN-05**: Вкладка «Сравнение» показывает два прогона одного набора по ситуациям: исправлено, сломано, нестабильно.
- [ ] **SCREEN-06**: Во время прогона владелец видит живой прогресс в строке инструмента, в подвале Pi и на доске:
  - сколько диалогов пройдено;
  - сколько примерно осталось времени;
  - сколько потрачено денег (с пометкой «оценка»).
- [ ] **SCREEN-07**: Все экраны используют единый визуальный язык: цвета темы, полосы, выравнивание. Текст переносится по словам без обрезки. Кириллица, светлая и тёмная темы выглядят правильно на ширине от 40 до 160 колонок.

### Для заказчика (SHARE)

- [ ] **SHARE-01**: Владелец одной командой получает короткую текстовую выжимку до ~15 строк: вердикт, число, три причины, «не измерено», согласие. Выжимка копируется в буфер обмена и сохраняется в файл.
- [ ] **SHARE-02**: Владелец одной командой получает HTML-отчёт для менеджера. Требования к нему:
  - один файл до 200 КБ;
  - открывается без Pi и без интернета;
  - без JavaScript;
  - аккуратно выглядит на экране и при печати;
  - указаны дата, версия агента, размер набора и судья.
- [ ] **SHARE-03**: В версии «для заказчика» (выжимка и HTML) нет сырых реплик клиентов. Номера карт, счета, ИНН, телефоны, почта и внутренние адреса замаскированы.
- [ ] **SHARE-04**: Полный отчёт для аудита остаётся доступен владельцу и явно помечен «не пересылать».

### Старт (START)

- [ ] **START-01**: Новичок одной фразой говорит, какого агента проверить и где логи. Lab сам находит промпт, точку входа и логи и ведёт дальше.
- [ ] **START-02**: Новичок видит подготовку как чек-лист на экране: агент → требования → логи → связь → бюджет → запуск. Пройденные шаги отмечены галочками, текущий шаг выделен.
- [ ] **START-03**: Связь с агентом проверяется до того, как потрачены деньги. Ошибка объяснена, и подсказан следующий шаг.

### Демо (DEMO)

- [ ] **DEMO-01**: Владелец показывает на демо сохранённый прогон эквайринга, записанный на замороженном коде. Все экраны рисуются без вызовов модели.
- [ ] **DEMO-02**: Доказательства демо-прогона скопированы за пределы рабочей папки и не теряются при её удалении.
- [ ] **DEMO-03**: Перед демо пройден чек-лист готовности: баланс OpenRouter, мок-сервер агента, версия Pi, шрифт и тема, HTML открывается офлайн.

## v2 Requirements

Отложено. В текущий план не входит.

### Прод

- **PROD-01**: Настоящий прод-агент (HTTP-адрес с токеном) прогоняется на том же наборе ситуаций, результат сравнивается с тестом по каждой ситуации.

### Старт

- **START-04**: Новичок без своего агента видит полный результат на встроенном примере примерно за минуту.
- **START-05**: Lab сам пишет адаптер подключения к чужому агенту.

### Судья

- **JUDGE-07**: Каппа и отдельные доли верных «провалов» и «успехов» во вкладке владельца, когда проверок станет 20 и больше.

## Out of Scope

| Feature | Reason |
|---------|--------|
| Оценка записанных прод-диалогов | Решение пользователя 2026-09-16: прод сейчас не нужен |
| Агенты с инструментами, проверка `tool`/`state` | Проект оценивает prompt/RAG по наблюдаемому ответу |
| Подсказка правок промпта, исправление агента | Агента сейчас не исправляем; инструмент не должен менять то, что измеряет |
| Исправленная версия агента для «до и после» | Агента не исправляем |
| Реальная среда заказчика (ИФТ, IdP) | Работаем локально с моками |
| Второй агент (инкассация) | Делает другой человек |
| Веб-приложение, ссылки на хостинг | Интерфейс только Pi; данные банка остаются локально |
| Отдельная сессия разметки, очереди разметки, канбан | Согласие собирается на доске, пока человек смотрит результаты |
| Оценки по шкале 1–5 или 0–100 | Бинарные вердикты стабильнее и понятнее менеджеру |
| Каппа и матрица ошибок для менеджера | Непонятны менеджеру и нестабильны на малых выборках |
| Автоподстройка судьи по отметкам человека | Молча меняет протокол и ломает сравнимость прогонов |
| Свободный текст-резюме, написанный моделью | Формулировки плавают и не проверяются; вердикт собирается по шаблону |
| Мониторинг прода в реальном времени | Превращает продукт в платформу наблюдаемости |
| Массовая генерация синтетических сценариев, десятки метрик | Размывают главное число; реальные диалоги важнее |
| CI как центр продукта | Поправка пользователя 2026-09-09 |
| Сторонние фреймворки оценки как зависимости | Решение ревью 2026-09-16 |
