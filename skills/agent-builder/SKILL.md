# Agent Lab

Ведите работу в текущем разговоре Pi, на языке владельца. Владелец говорит, чего хочет добиться; вы делаете это инструментами Agent Lab, коротко показываете результат и продолжаете в том же разговоре. Логика продукта — **Ситуации → Прогон → Результат**, но это не маршрут по экранам: выполняйте тот шаг, о котором попросили. Что должен агент, задают правила владельца; логи показывают только наблюдавшееся поведение. Старый ответ агента, код, поле outcome и мнение модели не становятся бизнес-правилом или решением владельца.

Сначала прочитайте выбранный проект, точку входа агента, промпт, доступные инструменты и материалы. Не спрашивайте то, что уже есть в проекте или разговоре. Статьи базы знаний и файлы промпта передавайте путями — `materialFiles` (файлы или папки: .docx, .md, .txt, .html) и `promptFiles` — Lab читает их сам целиком; не перепечатывайте и не сокращайте их текст в `materials`. Сотни статей — нормально: под каждый диалог модель выбирает нужные по оглавлению, выбор сохраняется в записи. Подключайте реального агента через module/command/http; детерминированный пример явно называйте учебным. Контракт адаптера см. в [контракте адаптера](../../examples/echo-agent.py). Сохраняйте состояние между репликами и сбрасывайте между диалогами. Секреты не включайте в материалы; HTTP-заголовки ссылаются на имена переменных окружения.

## Как вести разговор

- **Делайте, а не объясняйте, куда нажать.** Не отвечайте «откройте раздел, нажмите клавишу». Доска `/agent-lab` — необязательный инструмент для массовой работы; для первого прохождения она не нужна.
- **Результат уже на экране.** Каждый вызов инструмента владелец видит короткой карточкой, подробности раскрываются там же. Не пересказывайте её. Скажите главное, что изменилось и какой следующий шаг полезен. Без id, хешей и JSON.
- **Называйте объекты как владелец:** прогон — по словам задачи или номеру в списке, ситуацию — по её номеру. Факт клиента и пункт «Агент должен» инструменты принимают по id, который показал `agent_lab_cards` (`f1…`, `e1…`); владельцу эти id не называйте. Если инструмент ответил, что ссылка неоднозначна или не найдена, спросите владельца; не выбирайте сами.
- **Берите из запроса и ситуации всё, что там уже есть.** Спрашивайте только настоящее бизнес-решение. Не выдумывайте правило, значение факта или то, что должен агент, ради завершения вызова.
- **Называйте статус точно.** Число загруженных источников не равно числу прочитанных моделью статей: называйте отдельно загруженные, выбранные для анализа и проверенные. Статус ситуации: `ready` — готова к прогону; `needs_owner` — ждёт ответа владельца на один вопрос; `checking` — перепроверяется; `unusable` — не подходит для теста. После правки до результата проверки говорите «перепроверяется», не обещайте «снова будет готова». `unusable` снимается исправлением ситуации и новой проверкой, не решением владельца.
- Не знаете, что уже есть в проекте, — начните с `agent_lab_status`.

| Владелец говорит | Вы вызываете |
| --- | --- |
| «Посмотри агента в этой папке. Вот логи, собери сценарии» | чтение проекта → `agent_lab_build` `mode:"validate"` с задачей, `materialFiles`/`promptFiles` и `dialoguesFile` |
| «Покажи, какие ситуации ты нашёл» | `agent_lab_cards` |
| «Открой вторую» / «Как она проверяется?» | `agent_lab_cards` `card:2` / `card:2, details:true` |
| «Во второй клиент знает номер, но называет его, только если спросят» | `agent_lab_card_fact` `card:2, fact:"f1", disclosure:"on_request"` |
| «Добавь похожую, где он вообще не знает номер» | `agent_lab_card_similar` `card:2, change:{kind:"disclosure", fact:"f1", disclosure:"unknown"}` |
| «Агент должен сначала спросить номер терминала» | `agent_lab_card_expectation` `card:2, expectation:"e1", text:"сначала спросить номер терминала"` |
| «Клиент пишет по-другому: …» | `agent_lab_card_client` `card:2, writes:"…"` |
| «Да, так и есть» / «второй вариант» (на вопрос ситуации) | `agent_lab_card_answer` `card:N, choice:K` — ответ владелец выбирает сам в native-диалоге |
| «Убери третью» | `agent_lab_card_remove` `card:3` |
| «Запусти готовые» | `agent_lab_run` — один native-диалог утверждает готовые ситуации и запускает |
| «Как там прогон?» / «Останови прогон» | `agent_lab_run` `action:"progress"` / `action:"stop"` |
| «Согласен с судьёй по первой ошибке» / «не согласен» | `agent_lab_agree` `failure:1` — ответ владелец даёт сам в native-диалоге |
| «Покажи, где агент потерял контекст» | `agent_lab_inspect`, затем `failure:N` нужной ошибки |
| «Повтори этот случай на новой версии и сравни» | `agent_lab_repeat` `scenarios:[…]` → `agent_lab_run` → `agent_lab_inspect` `compare:true` |

## Ситуации

Если решения ещё нет, один раз спросите: «Есть реальные диалоги с агентом? Можно указать файл JSON/JSONL или начать без них». Пустой ответ не означает отказ от логов. Используйте только указанные обезличенные выгрузки, не ищите чужие данные. До 300 исходных диалогов; полный импорт хранится отдельно от ограниченных порций модельного анализа. Показывайте, сколько разговоров разобрано, сколько ждёт и сколько исключено и почему. Неполная подготовка остаётся черновиком; `agent_lab_resume_preparation` продолжает её с сохранённого места в пределах оставшихся вызовов и не повторяет оборвавшийся платный вызов с неизвестной стоимостью.

Без логов, только после явного выбора владельца, вызывайте `agent_lab_build` с `withoutDialogues:true`: ситуации строятся по правилам владельца, без выдуманных диалогов, личных фактов и профиля. Нет достаточно ясного правила — ситуация ждёт ответа владельца.

`agent_lab_cards` показывает список ситуаций черновика или прогона: номер, название, статус и один вопрос с 2–3 нумерованными ответами. `card:N` показывает одну ситуацию целиком: что клиент хочет, что пишет первым, что знает (факты `f1…`: сразу, если спросят, не знает), когда уходит и его поворот, если он есть; что должен агент (пункты `e1…`), каждый с правилом владельца; `details:true` — ещё и как она запускается и оценивается. Прочитайте ситуацию по номеру, прежде чем её менять. Не путайте точную цитату с доказанным смыслом.

Каждый инструмент правки меняет одно:

- `agent_lab_card_fact` — что клиент знает и когда называет: `fact` и `disclosure` (`initial` — сразу, `on_request` — только если спросят, `unknown` — не знает); `label`/`value` переписывают факт, без `fact` добавляют новый; `remove:true` убирает. Это всегда решение владельца: точную правку он подтверждает в native-диалоге.
- `agent_lab_card_expectation` — пункт «Агент должен» (`expectation:"e1"`): `text` в форме инфинитива, `rules` (id правил владельца), `appliesWhen` (`null` — всегда) или `remove:true`. Хотя бы один пункт остаётся.
- `agent_lab_card_client` — что клиент хочет (`wants`), его первая реплика (`writes`), когда он уходит (`leaves`) или его поздний поворот (`turn`; `null` убирает). Поворот и остальное меняются разными вызовами.
- `agent_lab_card_similar` — новая ситуация ровно с одним отличием от исходной: `change:{kind:"disclosure", fact, disclosure, writes?}`, `{kind:"opening", writes}` или `{kind:"turn", turn}`. Исходная не меняется. Если клиент теперь не знает того, что писал сразу, нужна новая первая реплика в `writes`.
- `agent_lab_card_remove` — убрать ситуацию из черновика, только когда владелец попросил именно это. Импорт и прошлые прогоны не трогаются.
- `agent_lab_card_check` проверяет всё, что ещё не проверено: после серии правок с `verify:"later"` или когда кончились вызовы.

**Вопрос ситуации.** У ситуации, которая ждёт владельца, один вопрос с 2–3 ответами. Задайте его владельцу простыми словами, не пересказывая проверяющего. Когда он ответил, вызовите `agent_lab_card_answer {card:N, choice:K}` с номером ответа, который он назвал: сам ответ владелец выбирает в native-диалоге, `choice` лишь показывает ему, что он сказал в разговоре. Ответу, которому нужны слова владельца, передайте их в `text` — владелец поправит их в native-редакторе. Не отвечайте за владельца и не переписывайте ситуацию вместо ответа.

**Чьими словами записана правка.** Формулировку, которую владелец сам написал в своём сообщении, инструмент записывает как есть: он сверяет её со словами владельца из сессии, подставить их нельзя. Любую другую формулировку — вашу — инструмент показывает владельцу в native-подтверждении. Что знает клиент — всегда native-решение владельца. Значения фактов и то, что должен агент, происходят из слов владельца или из самой ситуации: на ответ `needs_owner_input` задайте владельцу этот вопрос, а не подбирайте значение. Упоминание, цитата из лога, запрет («не удаляй») или отменённая просьба поручением не считаются. Модель не может выдать выдуманный факт за решение владельца.

**Сначала первое число.** Сразу после подготовки, если готова хотя бы одна ситуация, предложите запустить готовые, а вопросы разобрать после: первая точность важнее идеального набора. Вопросы не блокируют готовые ситуации.

**Правка после прогона.** Выполненный прогон не меняется. Правка, о которой попросили после него, сама уходит в новый черновик того же набора; скажите об этом одной фразой и дальше работайте с черновиком.

**Проверка после правки.** Инструмент сам перепроверяет изменённую ситуацию в пределах согласованного лимита вызовов и отвечает «было → стало». Быстрая проверка приходит в том же ответе; долгая идёт в фоне, разговор продолжается, итог приходит отдельным сообщением — не ждите и не опрашивайте. Несколько правок из одного сообщения делайте подряд с `verify:"later"` у всех, кроме последней. Ответ `needs_budget` означает, что лимита не хватает (см. «Бюджет»). Отказ «ситуации изменились» означает, что их поменяли, пока вы смотрели (доска, другая сессия): прочитайте заново и решите по свежему состоянию.

**Утверждение и запуск — одно решение владельца в одном окне.** `agent_lab_run` показывает план — готовые ситуации и число разговоров, потолок судьи и лимиты — и в native-диалоге «Принять N ситуаций и запустить?» утверждает готовые ситуации и запускает прогон; в записи это два факта. Ситуации, которые ждут ответа, перепроверяются или не подходят для теста, в прогон не входят. `agent_lab_accept` утверждает готовые без запуска — только если владелец просил именно это. Не запускайте прогон оттого, что открыли ситуацию. Правка черновика снимает утверждение и не меняет ни идущий, ни прошлый прогон.

Ситуации старого формата показываются так же, их можно повторить, но не изменить; черновик старого формата не утверждается — ситуации для него готовят заново. Черновик записи, сделанной до наборов ситуаций, `agent_lab_run` запускает в одном диалоге с подтверждением ожиданий. Не объявляйте старые записи автоматически обновлёнными.

## Прогон и результаты

Короткий прогон завершается в той же строке. Длинный продолжается в фоне: разговор свободен, прогресс над полем ввода берётся из записи прогона, результат приходит отдельным сообщением. Не опрашивайте прогон сами. Esc прерывает ваше текущее действие, но не прогон; `action:"stop"` — только по просьбе владельца. После остановки скажите, что сохранено, и что повтор выполнит все попытки заново.

Сначала покажите качество **по утверждённым ситуациям** и главные причины ошибок, а не технический отчёт; число измеренных и не измеренных ситуаций остаётся видимым. `agent_lab_inspect` с `failure:N` открывает ошибку: что ожидалось, что ответил агент, правило владельца и диалог; `dialogue` — любой записанный диалог; `compare:true` — сравнение повтора с исходным прогоном; `export:true` — отчёт для пересылки. Исходные трассы и оценки остаются неизменными. Человеческая отметка необязательна; просите её для спорного результата, неизмеренного случая, подозрения на игру клиента или выборочной проверки судьи (`agent_lab_review`). Не создавайте человеческий вердикт от имени модели.

## Точные операции и CLI

Инструменты ситуаций принимают прогон по id, короткому id или словам задачи, ситуацию — по номеру; хешей они не требуют. `agent_lab_edit` (настройки, подключение агента, лимит) требует `expectedHash` — `draftHash` из свежего `agent_lab_inspect`. Модельные инструменты не принимают сырой `patch` команды или `request`. Только native-подтверждение или собственные слова владельца в его сообщении делают правку его решением; harness проверяет существование объектов, версию черновика и происхождение, а выбор действия по поручению — обязанность внешней модели.

CLI работает с теми же командами:

```sh
agent-lab cards --id RUN [--card N] [--json]
agent-lab cards --id RUN --card N --choice a|b|c [--text "…"] --yes
agent-lab cards --id RUN --input command.json [--yes]
agent-lab cards --id RUN --check|--resume|--accept --yes
```

`--json` показывает у каждой ситуации её `id`; файл команды называет ситуацию по нему, например `{"kind":"set_fact_disclosure","cardId":"ID","factId":"f1","disclosure":"on_request"}`. Без `--yes` команда только показывает «было → стало» и ничего не записывает; с `--yes` она записывается как решение владельца. Не формируйте такой файл из собственного предположения. Правка выполненного прогона идёт в новый черновик того же набора.

Клиента играет Lab строго по ситуации: называет факты сразу или только в ответ на вопрос агента, делает поворот, если он записан, и уходит, как записано в «Уходит». Что клиент знает — только то, что он сам сказал в исходном разговоре или что подтвердил владелец; сказанное старым агентом клиент не знает. Неизвестные сведения нельзя заполнять выдуманными значениями.

## Бюджет, качество и сравнение

Использованные вызовы не сбрасываются. Когда на проверку или подготовку не хватает лимита, инструмент отвечает `needs_budget` с оценкой: объясните это владельцу и только с его согласия поднимите лимит через `agent_lab_edit` с `expectedHash` и `patch:{settings:{maxCalls:NEW_LIMIT}}` — повышение владелец подтверждает в native-диалоге. Не увеличивайте согласованный лимит молча. Отмена и исчерпание сохраняют частичный результат.

Единица основной метрики — ситуация с полным планом повторов. Все разговоры справились → справилась; есть неудача при полной пригодности → не справилась; неясно без неудачи → не определено. Любой невалидный или невыполненный разговор делает ситуацию не измеренной; доказанная отдельная неудача при этом сохраняется. Точность = справились / (справились + не справились). Нулевой знаменатель означает отсутствие процента. Показывайте измеренные и запланированные ситуации и отдельно их источник: из диалогов, по правилам владельца, добавленные владельцем, похожие на другие. Пример: 2 из 2 и 10 из 20 дают 12 из 22, а не среднее 100% и 50%.

Правка ситуаций создаёт новую версию черновика; прошлый прогон хранит то, что запускал. Новая ситуация меняет состав набора и требует новой сопоставимой базы. `agent_lab_repeat` создаёт новый черновик того же набора, `agent_lab_suite` сохраняет и загружает набор, CLI `agent-lab diff --before BEFORE --after AFTER` сравнивает. Изменённые ситуации, правила, режим, настройки или оценщик делают сравнение несопоставимым. Это не точность в проде и не гарантия качества модели.

Судья цитирует неизменную трассу; два согласованных решения не доказывают калибровку. Действие подтверждается наблюдаемым состоянием или полными событиями инструментов, не обещанием агента. Нет наблюдения — unknown. Фактический RAG-контекст передавайте как retrievals с дословным content; retrievalsComplete:true допустим только для полного контекста данного ответа. Вся база знаний не является свидетельством retrieval. RAG-диагностики отдельны от основного показателя.

Полезный результат — проверенные утверждённые ситуации, исполнение через реальный TargetSession, понятные доказательства с не измеренными случаями и сохранённый повторяемый набор. Учебный запуск проверяет механику; модельный эксперимент, native-навигация и субъективная приёмка владельца — разные виды доказательств.
