# Agent Lab

Agent Lab помогает проверить AI-агента по требованиям владельца: собрать библиотеку сценариев, проверить источники и факты, принять набор, выполнить его и сохранить доказательства проблем. Основной путь: **Логи → Сценарии → Прогон → Результаты**.

Ожидания берутся из требований владельца. Логи, прежние ответы агента и поле `outcome` описывают наблюдения и не заменяют требования. Несколько разговоров с одной бизнес-целью образуют группу; отдельные варианты отличаются фактами, условиями или поведением пользователя.

Вариант имеет источник фактов, конечную политику пользователя и контрольные точки. Контроллер отправляет только разрешённые реплики, раскрывает известные факты по запросу, соблюдает смену намерения и предел повторов. Смысловая проверка и точные цитаты проверяются отдельно. Готовность не означает принятие: владелец выбирает варианты и фиксирует неизменный снимок, затем отдельно подтверждает запуск.

Можно начать без логов: явно скажите это Pi. Получится та же библиотека с вариантами по требованиям (`curated`), без выдуманных диалогов и личных фактов. `e → Добавить факт владельца` записывает ваш явный ввод и его историю. Принятие не превращает модельное предположение в подтверждённый факт.

Для обычного prompt/RAG используется наблюдаемый ответ. Проверка действий по инструментам или состоянию требует объявленной возможности адаптера, подтверждённого сброса и достаточного наблюдения. Обещание агента изменить данные не доказывает само изменение. Полностью замаскированные или неподтверждённые данные остаются исключёнными/не измеренными с причинами. Старые карточки читаются и повторяются без переписывания; новый формат не меняет их хеши задним числом.

### Наблюдение RAG

Адаптер может вернуть вместе с `reply` фактически переданные модели фрагменты:

```json
{"reply":"Возврат оформляется через терминал.","retrievals":[{"source":"refunds.md#return","documentId":"KB-17","version":"4","section":"Возврат","content":"Возврат оформляется через терминал.","score":0.9}],"retrievalsComplete":true}
```

`retrievalsComplete:true` означает полную запись указанной стадии для этого ответа; `retrievals:[]` — подтверждённое отсутствие фрагментов, отсутствующее поле — неизвестность. `retrievalStage:"model_context"` (значение по умолчанию для старых адаптеров) означает фактический контекст отвечающей модели. Если адаптер видит только ответ поиска, укажите `retrievalStage:"retrieved"`: Lab проверит достаточность и релевантность выдачи, а обоснованность ответа по контексту модели останется неизвестной. Не подставляйте всю базу знаний вместо наблюдаемой выдачи. До 20 фрагментов, по 12 000 символов, суммарно до 60 000; большие контексты нельзя молча обрезать и объявлять полными.

Поля documentId, version, section и score необязательны; текст сохраняется дословно. Метаданные версии сообщает адаптер, Lab не подтверждает их подлинность автоматически. Материалы владельца хранятся отдельно и передаются проверке правильности ответа; их текстовый хеш входит во вход судьи.

У RAG-проверок разные входы:

| Проверка | Доступные свидетельства |
|---|---|
| Достаточность контекста | Доставленные вопросы, фактический контекст, приложенные эталонные материалы и ожидания карточки |
| Релевантность | Доставленные вопросы и фактический контекст; ответ агента и эталон скрыты |
| Обоснованность ответа | Доставленные вопросы, фактический контекст и ответы; эталонные статьи, ожидаемый результат, планы симулятора и состояние стенда скрыты |

Контекст связан с конкретным ответом. Для положительной оценки обоснованности нужны цитаты каждого ответа и его собственного контекста; поздняя статья не может служить цитируемым основанием раннего ответа. Неполная запись оставляет диагностику неизвестной. При отсутствии эталонных материалов достаточность знания также неизвестна. Эта модельная оценка не измеряет полноту поиска по всей базе: для этого нужны независимо проверенные релевантные документы. Обоснованность проверяет утверждения о правилах и процедурах; текущее состояние конкретной заявки и результаты инструментов относятся к другим проверкам. Дословные цитаты из фрагментов могут содержать исходные переносы строк.

Большая база хранится целиком, но генератор и судья читают статьи по конкретному случаю. Отбор ограничен и символами, и размером JSON в UTF-8; исходные тексты не обрезаются. Требования извлекаются отдельно под каждый вопрос, даже если два вопроса используют одну статью. Судья получает статьи, на которые ссылаются требования карточки; доступ испытуемого к базе от этого не меняется. При выборе оснований Lab передаёт только сообщения клиента: старое решение агента не определяет выбор статьи. После выбора по оглавлению выполняется один пересмотр по текстам выбранных статей, которые помещаются в запрос; непрочитанные статьи обозначаются явно. Модель может заменить статью или добавить связанную инструкцию. Статьи, название которых содержит все содержательные слова исходного вопроса, сохраняются как альтернативные основания (не более двух); это не подтверждает применимость их условий. При передаче материалов генератору сохраняется приоритет выбранных статей. Отсутствие подходящей выборки не считается доказательством отсутствия правила в базе. Одна цитата с разными условиями или смыслом требования не объединяется автоматически.

До шести дополнительных вызовов судьи на диалог в пределах бюджета, без учёта повторов при некорректном формате ответа. Эти диагностики не меняют основную accuracy. Старые оценки сохраняются; проверка по новой версии протокола требует переоценки. [Контрольный аудит разделения свидетельств](docs/rag-evidence-audit-2026-09-22.md).

Платные контроли на вымышленных материалах через настоящий адаптер и судью запускаются в отдельной копии проекта:

```sh
npx tsx test/live/rag-evidence.ts --run --max-calls 13
```

Скрипт заранее сохраняет входы и ожидаемые результаты, затем сырые ответы судьи, контекст каждого ответа и расход. Он проверяет оценщик на заданных ответах; реальный поиск по вашей базе этим не измеряется.

### Основной путь — разговор

Работайте с Lab как с Claude Code или Codex: напишите, чего хотите добиться, — Lab сам вызовет нужные операции, покажет короткий результат и будет ждать следующей фразы в том же разговоре. Команды и клавиши знать не нужно.

> Посмотри агента в этой папке. Вот логи: `dialogues.jsonl`, собери сценарии.
> Покажи, какие ситуации ты нашёл. Открой источник второй карточки.
> В этом сценарии клиент знает номер, но сообщает его только по запросу.
> Добавь вариант, где он вообще не знает номер.
> Эти две группы про одно и то же, объедини.
> Прими готовые сценарии, спорные пока оставь. Запусти принятый набор.
> Покажи, где агент потерял контекст. Повтори этот случай на новой версии и сравни.

Четыре этапа **Логи → Сценарии → Прогон → Результаты** остаются логикой продукта, но больше не являются маршрутом по четырём экранам: Lab выполняет тот шаг, о котором попросили. Это намеренное изменение прежней UX-спецификации; правила корректности измерений не менялись.

- **Лента.** Каждое действие — короткая строка: что сделано, что найдено, что изменилось («было → стало»). Подробности — карточка, исходный диалог с цитатами, трасса, правила — раскрываются там же (`Ctrl+O`), без ухода из разговора и без потери набранного текста. JSON, хеши и аргументы инструментов на экран не попадают.
- **Ссылки словами.** Прогон, карточку, группу и провал можно называть по названию или номеру в списке. Если ссылка неоднозначна, Lab спросит, а не угадает.
- **Чьими словами записана правка.** Правка черновика записывается под вашим сообщением из разговора — Lab читает его из сессии сам. Значение факта или ожидание, которых вы не называли, не записываются: Lab задаёт конкретный вопрос. Формулировку, которой вы не произносили, он покажет в отдельном подтверждении.
- **Проверка после правки.** Смысл изменённых карточек Lab перепроверяет сам в пределах согласованного лимита вызовов. Быстрая перепроверка приходит сразу; долгая идёт в фоне, разговор при этом свободен. Если лимита не хватает — Lab объяснит это и попросит отдельное разрешение.
- **Принятие и запуск — два разных решения.** Принятие показывает точный список карточек и не запускает агента. Перед запуском — компактный план: агент и версия, набор, число попыток, модели и лимиты; подтверждение относится именно к нему. Правка черновика снимает принятие и не меняет ни идущий, ни прошлый прогон; правка после прогона сама уходит в новый черновик того же набора.
- **Прогон не держит разговор.** Короткий завершается в той же строке, длинный продолжается в фоне: прогресс над полем ввода берётся из записи прогона, результат приходит сообщением. `Esc` прерывает текущее действие, но не прогон; остановка — отдельная просьба. После остановки Lab говорит, что сохранено и что придётся выполнить заново.
- **Результаты.** Сначала итог по принятому набору и главные причины; число измеренных и не измеренных вариантов видно всегда. «Покажи второй провал» открывает ожидание, реплику агента, правило владельца и диалог.

Agent Lab принимает до 300 обезличенных диалогов JSON/JSONL, показывает потолок расхода до начала работы и сам не забирает данные из внешних систем.

### Доска `/agent-lab` — для массовой работы

Доска не обязательна: всё перечисленное выше доступно из разговора теми же операциями Lab. Она удобна, когда нужно быстро пройти много карточек или отметить согласие с судьёй. `/agent-lab` открывает историю проверок, `n` начинает новую. Разделы: **1 Логи → 2 Сценарии → 3 Прогон → 4 Результаты**.

1. **Логи:** видно, сколько источников обработано, ожидает обработки или исключено и почему. Смысловая перепроверка не выдаётся за импорт ещё не обработанных логов.
2. **Сценарии:** варианты сгруппированы по бизнес-ситуациям. Здесь показаны готовность, факты пользователя, исходная цитата, происхождение синтетических вариантов и нерешённые решения. `Space` выбирает варианты, `e` обычным текстом исправляет первую реплику, цель, ожидаемый результат, правило проверки или факт владельца, `v` добавляет целевой вариант, `m` / `s` объединяют или разделяют группы, `g` продолжает смысловую проверку. Цитата требования при таких правках сохраняется, а изменённый вариант требует новой смысловой проверки. `y` или Enter принимает выбранные варианты одной ревизией и не запускает агента. Если после принятия изменить выбор, доска попросит принять его заново. «Карточка 1 из 2» означает положение курсора; галочка и «выбрано для прогона» показывают выбранный набор.
3. **Прогон:** после принятия показаны число выбранных вариантов, ревизия, агент, число диалогов и накопительный бюджет: использовано, максимум и остаток. `b` позволяет осознанно увеличить максимум без сброса уже учтённого расхода. `r` открывает отдельное подтверждение запуска и использует свежий hash черновика, созданного после компиляции принятой ревизии.
4. **Результаты:** `i` открывает постоянные проблемы с точными оценками и событиями. Итог показывает оценочную accuracy, «не измерено» и главные причины. Enter ведёт к разбору провала и разговору. `y` / `n` / `s` отмечают согласие с судьёй, несогласие или сомнение.

Esc возвращает в историю, `q` закрывает только доску — начатый прогон продолжается, пока открыт Pi, а прогресс виден над полем ввода. Для остановки нажмите `c` на доске или напишите об этом в разговоре. `r` в завершённом прогоне создаёт новый черновик принятого набора; исходный результат остаётся в истории.

`Tab` переключает разделы, `PgUp` / `PgDn` прокручивают текст, `?` открывает справку. Главное действие всегда написано внизу экрана.

История и `agent_lab_inspect` доступны и во время работы другой сессии: для чтения не нужна блокировка записи. Изменять или останавливать чужой активный прогон из этого окна нельзя; экспорт сохранённого снимка доступен.

Сохранить и повторить набор:

```sh
agent-lab save-suite --id RUN --output .evals/validation.json
agent-lab evaluate --input .evals/validation.json --yes --parallel 8
agent-lab diff --before BEFORE_RUN --after AFTER_RUN
```

`unknown`, invalid и not reached не входят в знаменатель accuracy. Автоматические решающие pass/fail не требуют ручной разметки; человек нужен только для спорных случаев или выборочного аудита.

## Учебный пример и безопасная отдельная копия

Новый пример использует два вымышленных русских диалога: одна группа, один готовый вариант и один заблокированный из-за спорного личного факта. У позднего номера через `e` подтвердите исходное знание (`initial`), затем `g` перепроверьте библиотеку. После принятия оба варианта проверяют инструкцию по возврату; во втором пользователь действительно сообщает номер по просьбе. Подготовка примера детерминированная; в открытом Pi смысловая перепроверка и исполнение используют вашу настроенную модель. Исходный агент примера — маленький модуль с намеренной ошибкой повторного запроса номера.

Явная правка факта владельцем — отдельное основание для сценария: исходный лог при этом сохраняется. Смысловая проверка учитывает подтверждённую правку и продолжает искать противоречия в текущем сценарии. Принятие не происходит автоматически; если повторить проверку старого черновика после обновления контекста оценки, потребуется новый модельный бюджет.

В новой копии проекта:

```sh
npm ci
npm run build
node examples/scenario-lab-demo.mjs
```

Команда создаст новую приватную папку в системном temp и напечатает команду запуска Pi с абсолютными путями, отдельной `.agent-lab` и ID для `/agent-lab RUN`. При необходимости задайте `AGENT_LAB_PROVIDER` и `AGENT_LAB_MODEL` перед созданием примера. Реальные данные проекта не копируются. Расширение Pi читает исходники из `src/`, поэтому сборка `dist/` работающий Pi не затрагивает. Не добавляйте секреты или частные `.agent-lab` в git. Полный учебный процесс без модели, включая повтор, парную диагностику и отдельного кандидата:

```sh
node examples/scenario-lab-demo.mjs --verify
```

Отчёт сохраняется в новой временной папке. Это проверка механики, не качества модели. Отдельный ограниченный модельный smoke-запуск (до 40 вызовов и 10 минут, вымышленные данные):

```sh
AGENT_LAB_PROVIDER=openrouter AGENT_LAB_MODEL=openai/gpt-5.6-sol npx tsx test/live/scenario-lab.ts --run
```

Используйте реально доступные вам provider/model; команда не устанавливает провайдера и не читает чужие логи. Неготовые предложения сохраняются для проверки, не принимаются автоматически.

## Как считается результат

Единица — вариант в принятом наборе, а не отдельная попытка. Все запланированные попытки должны быть пригодны и выполнены. Все pass дают pass; наличие fail при полном пригодном плане даёт fail; unknown без fail оставляет решение неопределённым. При любой invalid или невыполненной попытке вариант не измерен; отдельный доказанный fail остаётся в подробностях.

Accuracy = pass / (pass + fail), рядом измерено/запланировано. Нулевой знаменатель не превращается в 0%. Группы 2/2 и 10/20 дают общий результат **12/22**, а не среднее процентов. Происхождение показано отдельными срезами: из диалогов, по требованиям владельца, синтетические. Добавление варианта создаёт новую ревизию и меняет состав набора; старые результаты не меняются. Статистическое сравнение семейств — отдельный расчёт.
