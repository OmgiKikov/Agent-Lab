# Agent Lab

Agent Lab проверяет ИИ-агента поддержки на его настоящих разговорах с клиентами. Вы загружаете выгрузку диалогов
и правила, по которым агент должен отвечать, а Lab находит разговоры с ошибками и показывает каждую ошибку вместе
с репликой агента и пунктом правил, который она нарушает.

## Что умеет

- **Tone of voice.** Проверяет разговоры по правилам общения: документу в `.docx`, `.txt` или `.md`.
- **Точность.** Проверяет разговоры по требованиям из кода агента: его промптов и инструментов.
- **Ответы людей.** Каждую найденную ошибку можно подтвердить или отклонить, итог это учитывает.
- **Серьёзность ошибок.** Модель предлагает, какие ошибки серьёзные, человек подтверждает или меняет.
- **Бизнес-сценарии.** Каждый разговор выгрузки читается целиком, и задачи клиентов собираются в каталог: категории
  (например, «QR-оплата») и сценарии внутри них («Не работает QR», «Подключить QR»), с описанием, примерами и долей
  разговоров.
- **Профиль агента.** Домен агента, что в него входит и что нет, примеры задач и какие номера называют его клиенты.
  По профилю читаются разговоры, строятся каталог и карточки, поэтому тот же конвейер подходит любому агенту
  поддержки. Для агента эквайринга профиль поставляется с Lab, для другого его задают в разделе «Агент».
- **Сценарии и симуляции.** Карточка сценария — это профиль клиента настоящего разговора: задача эпизода из каталога,
  что он знает и когда это говорит (в первом сообщении, когда к месту, только если спросят), чего не знает, что уже
  пробовал и что выходит, если попробовать, как реагировал на агента и как пишет. Каждый пункт подтверждён цитатой из
  лога. Номера и реквизиты клиент берёт у того банка, который видит агент. Карточка собирается на каждый разговор
  выгрузки по теме агента: сколько разговоров в бизнес-сценарии, столько у него разных клиентов. Редкие случаи
  помечены как стрессовый набор: только их играют типы клиентов, и считаются они отдельно. Синтетические клиенты
  разыгрывают карточки с агентом, разговор заканчивается с причиной. Для этого нужно подключение к агенту. Каталог и
  карточки можно собрать и до проверки, сразу после загрузки выгрузки: тогда в карточках нет критериев, и чтобы
  сыграть их, нужно проверить разговоры и собрать сценарии заново.
- **Сравнение.** Новая проверка сравнивается с предыдущей по тем же критериям.
- **Отчёты.** Текст для письма команде и сводка на одну страницу для руководителя.

Агентов может быть несколько. У каждого свои разговоры, правила и результаты, они не смешиваются.

## Быстрый старт

Понадобятся Python 3.11+, [uv](https://docs.astral.sh/uv/) и Node.js 22.13+ с npm.

В корне репозитория:

```bash
OPENROUTER_API_KEY=sk-or-... sh bin/start.sh
```

Скрипт поставит зависимости, соберёт интерфейс и запустит Lab. Откройте http://127.0.0.1:5899. Дальше всё делается
в интерфейсе: создайте агента, загрузите выгрузку разговоров (`.xlsx` или `.jsonl`) и правила общения, запустите
проверку. Адрес агента на стенде и путь к его коду задаются в разделе «Агент».

Остановить Lab можно через Ctrl+C.

## Модели

Lab может работать с моделями тремя способами. При запуске он берёт первый из настроенных:

1. Свой OpenAI-совместимый endpoint, если задан `LAB_MODEL_URL`.
2. Шлюз моделей банка, если в папке `certs/` лежат его настройки.
3. OpenRouter с ключом из `OPENROUTER_API_KEY`.

По умолчанию используется `z-ai/glm-5.3`. Другую модель можно задать через `LAB_MODEL`:

```bash
LAB_MODEL=<id модели> OPENROUTER_API_KEY=sk-or-... sh bin/start.sh
```

### Шлюз банка

На рабочем компьютере модели идут через шлюз банка с клиентским сертификатом. Положите в `certs/`:

- `url.txt` с адресом шлюза (с портом, если он не 443);
- сертификат и ключ или один файл `.p12`/`.pfx`, а пароль к нему в `password.txt`;
- корневой сертификат банка, если шлюз его требует: имя файла начинается с `ca` или `root`, например
  `ca-chain.cert.pem`.

Сертификат и ключ в PEM Lab узнаёт по содержимому, а не по расширению, поэтому файлы вида `new_cert.c-r-t` и
`key.k-e-y` переименовывать не нужно. Если сертификат шлюза нечем проверить (на тестовом контуре так бывает),
запустите Lab с `AGENT_LAB_GATEWAY_INSECURE=1`: проверка сертификата шлюза отключится, клиентский сертификат
по-прежнему будет предъявлен.

Если `LAB_MODEL` не задан, Lab берёт самую новую GLM из каталога шлюза. Если шлюз настроен с ошибкой, Lab всё равно
запустится, но не будет отправлять разговоры в OpenRouter вместо шлюза. Причину он покажет в разделе «Настройки»:
там же кнопка проверки связи с моделью. Шлюз может ограничивать число запросов, поэтому на нём лучше начинать с
`LAB_MODEL_CONCURRENCY=3`.

## Настройки

Все настройки задаются переменными окружения и читаются один раз при запуске. Полный список с комментариями лежит
в `backend/lab/config.py`.

| Переменная | Что задаёт | По умолчанию |
|---|---|---|
| `OPENROUTER_API_KEY` | ключ OpenRouter | нет |
| `LAB_MODEL` | модель | `z-ai/glm-5.3`, для шлюза самая новая GLM |
| `LAB_MODEL_URL`, `LAB_MODEL_KEY` | свой endpoint и ключ к нему | нет |
| `LAB_SECOND_MODEL` | вторая модель, которая независимо перепроверяет разговоры | выключена |
| `LAB_SECOND_URL`, `LAB_SECOND_KEY` | endpoint и ключ второй модели | как у основной |
| `LAB_MODEL_CONCURRENCY` | сколько запросов к модели идёт одновременно | 6 |
| `LAB_AGENT_TIMEOUT` | сколько секунд ждать ответа агента | 180 |
| `LAB_PORT` | порт | 5899 |
| `LAB_DATA` | папка с данными | `data/` |
| `LAB_CERTS` | папка с настройками шлюза | `certs/` |
| `AGENT_LAB_GATEWAY_INSECURE` | `1` отключает проверку сертификата шлюза (только тестовый контур) | выключено |

## Данные

Всё, что вы загружаете и получаете в Lab, хранится на вашем компьютере в `data/`. У каждого агента своя база SQLite:
`data/agents/<id>/lab.sqlite3`. Удалённый агент не стирается, а переносится в `data/deleted/`.

Папки `data/` и `certs/` в Git не попадают. С одной папкой данных может работать только один запущенный Lab.

Долгая работа (проверка, прогон) сохраняется по ходу в той же базе. Если Lab перезапустить или он упадёт посреди
работы, после старта он сам продолжит с того же места и не оплатит заново уже проверенное. «Остановить» сохраняет
проверенное, а тот же запуск продолжает его. Прерванный разговор с агентом играется заново, как новый.

## Разработка

Бэкенд и интерфейс удобно запускать по отдельности, с перезагрузкой при изменениях:

```bash
# бэкенд на :5901
uv run --directory backend uvicorn lab.app:create --factory --reload --port 5901

# интерфейс на :5900, в другом терминале
npm --prefix frontend ci
npm --prefix frontend run dev
```

Интерфейс открывается на http://127.0.0.1:5900, запросы к `/api` Vite передаёт бэкенду.

Перед коммитом прогоните линтеры, тесты и сборку. Тесты не обращаются к настоящим моделям.

```bash
sh bin/check.sh
```

Чтобы посмотреть, насколько оценки модели совпадают с ответами людей:

```bash
uv run --directory backend python -m lab.eval judge
```

### Структура

```
backend/
  lab/
    api/        HTTP API, по модулю на раздел продукта
    flows/      процессы: проверки, сценарии, прогоны
    roles/      запросы к моделям и их инструкции (prompts/)
    models/     подключение к моделям: OpenRouter, свой endpoint, шлюз банка
    agents/     подключение к проверяемому агенту
    storage/    хранение в SQLite
    domain/     правила подсчёта, без ввода-вывода
    config.py   настройки
  tests/
frontend/
  src/
    app/        оболочка: навигация, адреса, поиск
    sections/   экраны, по папке на раздел
    product/    общие части экранов
    ui/         базовые компоненты
    lab/        запросы к API и типы данных
bin/
  start.sh      установка, сборка и запуск
  check.sh      проверки перед коммитом
```

Слои бэкенда импортируют друг друга только сверху вниз: `api → flows → roles → models → storage → domain`. За этим
следит тест `backend/tests/test_architecture.py`.
